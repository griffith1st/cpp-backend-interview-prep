## 2. 网络分层、封装与时延

### 2.1 五层模型

| 层 | 解决的问题 | 常见协议/设备 | 面试关键词 |
|---|---|---|---|
| 应用层 | 进程使用的网络服务 | HTTP、DNS、DHCP、Kafka | 报文、语义、状态 |
| 传输层 | 进程到进程 | TCP、UDP、QUIC | 端口、可靠性、流控 |
| 网络层 | 主机到主机、跨网段 | IPv4/IPv6、ICMP、路由协议 | IP、TTL、路由 |
| 链路层 | 相邻节点一跳传输 | Ethernet、Wi-Fi、CAN | 帧、MAC、CRC、仲裁 |
| 物理层 | 比特在介质上传输 | 双绞线、光纤、无线 | 编码、速率、信号 |

发送时逐层加首部，接收时逐层解封装。TCP 看到的是字节流，IP 看到的是数据报，Ethernet 看到的是帧。

### 2.2 四类时延

`总时延 = 处理时延 + 排队时延 + 传输时延 + 传播时延`。

- 处理：校验首部、查路由、协议栈处理。
- 排队：等待输出链路或线程/连接池资源。
- 传输：把 L 个比特推到链路上，约为 `L/R`。
- 传播：信号在介质中传播，约为 `距离/传播速率`。

排查高延迟时不要只看 ping：应用耗时还可能包括 DNS、连接建立、TLS、服务端排队、数据库等待和响应传输。

### 2.3 必会的封装题

浏览器发送 HTTPS 请求时，典型封装路径为：

`HTTP 数据 → TLS 记录 → TCP 段 → IP 包 → Ethernet 帧 → 物理比特`。

每经过一个路由器，二层帧通常重新封装；IP 源/目的地址通常保持不变，MAC 地址按下一跳变化。

### 2.4 OSI 七层与 TCP/IP 四层如何对应

OSI 七层从下向上为物理、数据链路、网络、传输、会话、表示、应用。TCP/IP 四层通常是网络接口、网际、传输、应用，教学五层把网络接口再分为物理与链路。模型划分是认识问题的工具，TLS 不必强行塞入一个唯一的 OSI 层。

**面试例子：**JSON 是应用层数据表示；TCP 负责字节传输；TLS 在应用与传输之间形成保护层；以太网在当前链路发送帧。Socket 是编程接口，并非一种与 TCP 并列的网络协议。

### 2.5 带宽、吞吐、RTT、抖动与 BDP

- 带宽描述链路名义传输能力；吞吐描述实际完成的传输速率；goodput 只统计有效应用数据。
- RTT 是往返时间，单向时延并不总等于 RTT/2，因为路径和排队可能不对称。
- 抖动是时延变化，实时通信往往同时关心低时延和低抖动。
- 带宽时延积 `BDP = 带宽 × RTT` 表示填满往返路径所需的在途数据量。单位统一成 bit 或 byte。
- 大带宽高 RTT 链路，窗口太小会限制吞吐；单纯扩容服务器 CPU 对这个瓶颈帮助有限。

### 2.6 物理层和交换方式补全

比特率单位是 bit/s，码元率单位是 Baud；一个码元可携带多个比特。理想无噪声低通信道的奈奎斯特关系为 `最大比特率 = 2B log2(M)`；有噪声信道的香农容量为 `C = B log2(1 + S/N)`，S/N 用线性值而非 dB。

FDM 按频率分配、TDM 按时间片分配、WDM 按光波长分配、CDM 按码区分。电路交换先保留资源，时延相对稳定但空闲时仍占资源；分组交换统计复用、利用率高，但会排队、乱序和丢包。报文交换把整个报文存储转发，缓存与等待更大；分组交换把报文拆成小块，可在多跳链路形成流水线。

## 3. 链路层、以太网与 ARP

### 3.1 以太网与交换机

- MAC 地址用于本地链路寻址，不等于 IP 地址，也不等于设备业务身份。
- 交换机通过源 MAC 学习端口；目的 MAC 未知时泛洪，广播帧在广播域内传播。
- VLAN 将一个物理交换网络划分为多个逻辑广播域；跨 VLAN 需要三层设备转发。
- CSMA/CD 是传统共享式、半双工以太网机制；现代交换式全双工网络通常不依赖碰撞检测。

### 3.2 ARP

ARP 把同一链路上的 IPv4 地址解析为 MAC 地址。主机发现目标不在本地子网时，ARP 的目标是默认网关 MAC，而不是远端服务器 MAC。

流程：查 ARP 缓存 → 广播 ARP Request → 目标或网关单播 Reply → 缓存映射 → 发送 IP 包。

易错点：ARP 只解决一跳的 MAC 解析；ARP 请求通常广播、响应通常单播；缓存会过期，ARP 欺骗属于典型局域网攻击。

### 3.3 CAN 与以太网的区别

CAN 是共享总线上的消息广播协议，使用消息 ID 参与仲裁；以太网通常基于交换机和 MAC 帧转发。CAN 的 ID 越小通常优先级越高，但 ID 不是设备地址。

### 3.4 帧定界、透明传输与 CRC

帧定界回答“从哪里开始、在哪里结束”；透明传输回答“数据恰好含有定界标记时怎么办”。字节填充和比特填充均通过转义避免把数据误认成控制信息。这个问题与 POP3 单点结束行、SMTP dot-stuffing 具有相同的设计思路，但所在协议层不同。

CRC 将比特串视为多项式，用生成多项式做模 2 除法，附上余数，接收端检查余数。CRC 主要检测意外差错，不是密码学签名，也不负责重传；检测后的处理由链路协议决定。以太网出错帧一般丢弃，可靠性可由更高层恢复。

### 3.5 Wi-Fi、PPP 与广播域

Wi-Fi 使用 CSMA/CA 尝试避免碰撞，结合退避、链路 ACK，必要时使用 RTS/CTS 缓解隐藏节点问题。无线中边发边可靠检测碰撞困难，因此与经典 CSMA/CD 机制不同。

PPP 是点到点链路协议，涉及封装、LCP 链路配置、NCP 网络层配置，可带认证机制。交换机每个端口可形成独立碰撞域，同一 VLAN 内仍属同一广播域；路由器隔离广播域。VLAN 标签是逻辑隔离标识，不等于数据加密。

## 4. 网络层：IP、子网、路由与 NAT

### 4.1 IPv4 首部重点

- `TTL` 每经过一个三层转发设备通常减 1，降为 0 时丢弃并可能返回 ICMP 超时报文。
- `Protocol` 指示上层协议，如 TCP、UDP、ICMP。
- 分片相关字段为标识、标志、片偏移；现代工程通常通过路径 MTU 发现尽量避免分片。
- IPv4 只提供尽力而为的数据报服务，不保证可靠、顺序或不重复。

### 4.2 子网、CIDR 与最长前缀

`192.168.1.0/24` 表示前 24 位为网络前缀，剩余 8 位为主机部分。路由查找若有多个匹配项，选择最长匹配前缀。

面试计算步骤：

1. 将 IP 与掩码按位与得到网络地址。
2. 根据前缀长度确定地址范围和广播地址。
3. 判断两个地址是否同网段。
4. 不同网段时，下一跳是默认网关。

### 4.3 ICMP、Ping、Traceroute

- Ping 通常使用 ICMP Echo Request/Reply，测的是往返连通性和 RTT，不等于应用端口可用。
- Traceroute 递增 TTL，利用中间路由器返回 ICMP 超时报文推断路径。
- 防火墙可能丢弃或限速 ICMP，因此“ping 不通”不能直接推出 TCP 服务不可用。

### 4.4 NAT/NAPT

NAT 改写网络地址，常用于私网与公网之间；NAPT 进一步改写传输层端口，使多个内网连接共享公网 IP。连接跟踪常依据五元组识别流：协议、源 IP、源端口、目的 IP、目的端口。

NAT 带来的面试点：入站连接需要端口映射或打洞；长连接、超时、连接跟踪表和端口耗尽都可能成为故障来源。

**细化：**五元组常用于识别流和连接跟踪，但 NAT 映射、入站过滤的规则依实现而异，不必都绑定完整五元组。不要从“用过 NAT”直接推导它拥有完整防火墙能力。

### 4.5 IPv6 基础

IPv6 使用 128 位地址，取消传统 IPv4 首部校验和，邻居发现由 NDP 完成；面试通常要求知道地址更大、自动配置、扩展首部和不依赖广播即可，不必把未使用过的内容说成项目经验。

IPv6 基本首部 40 字节，使用 Hop Limit；路由器不做 IPv6 分片，由源节点处理，路径过小时通常返回 ICMPv6 Packet Too Big。NDP 基于 ICMPv6、多播和邻居缓存，与 IPv4 ARP 的报文格式不同。全球单播、链路本地地址、回环 `::1` 要能区分。

### 4.6 MTU、MSS、分片与大包黑洞

MTU 是链路允许承载的最大 IP 包大小，常见以太网值为 1500，但隧道和具体网络会改变它。MSS 是一个 TCP 段中的最大 TCP 数据长度；IPv4 无选项时常用 `1500 - 20 - 20 = 1460` 字节举例，带选项后实际数据载荷需相应调整。

IPv4 超过下一跳 MTU 且允许分片时可以分片；若 DF 置位，则丢弃并反馈所需 MTU。接收端 IP 层重组，TCP 分段与 IP 分片不是同一过程。小请求成功而大响应停滞时，应怀疑 PMTU、隧道开销和 ICMP 被过滤，而不是直接归因数据库慢。

### 4.7 路由转发与路由选择

转发是逐包执行数据平面规则，路由选择是控制平面计算或学习规则。转发时做最长前缀匹配，确定出口和下一跳，解析邻居地址并封装下一跳帧；IPv4 TTL 和首部校验和也随转发更新。

| 协议 | 思路 | 典型追问 |
|---|---|---|
| RIP | 距离向量，常以跳数计价 | 最大可达跳数 15，16 表示不可达；计数到无穷如何缓解 |
| OSPF | 链路状态，区域内链路信息传播和最短路计算 | Dijkstra、区域、收敛和链路开销 |
| BGP | 自治系统之间的路径向量和策略选择 | AS_PATH 防环，策略可能优先于几何最短路径 |

静态路由由人工配置；默认路由 `0.0.0.0/0` 是最长前缀匹配的兜底。你的交通路线 Dijkstra 可用于解释图最短路思路，但不等于实现过 OSPF 或 BGP。

## 5. 传输层：UDP 与 TCP

### 5.1 对比表

| 项目 | UDP | TCP |
|---|---|---|
| 连接 | 无连接 | 面向连接 |
| 语义 | 面向报文 | 面向字节流 |
| 可靠性 | 尽力而为 | 序号、ACK、重传、校验 |
| 流量/拥塞控制 | 协议本身不提供 | 提供 rwnd/cwnd 机制 |
| 通信模式 | 一对一、一对多等 | 通常一对一 |
| 典型场景 | DNS、实时媒体、简单请求 | HTTP/1.1、数据库连接、Kafka |

选择依据不是“TCP 一定好、UDP 一定快”，而是是否需要可靠有序字节流、是否允许应用自行处理丢包和顺序、对时延和广播的要求。

### 5.2 TCP 首部与序号

- 序号按字节编号；一个携带 N 字节的报文段，下一字节序号增加 N。
- 确认号表示“期望收到的下一个字节序号”，通常是累计确认。
- SYN 和 FIN 各自消耗一个序号；ACK 在连接建立后通常置 1。
- 窗口字段反映接收方可接收空间；窗口扩大、SACK、时间戳属于常见选项。

### 5.3 为什么 TCP 是字节流

TCP 不保留应用层 `send()` 的消息边界。一次发送可能被拆成多次接收，多次发送也可能合并成一次接收。因此应用协议必须设计 framing：

1. 固定长度：适合结构固定的消息。
2. 分隔符：如每条命令以 `\n` 或 `\0` 结束。
3. 长度前缀：先读固定长度的 length，再读 body。
4. 自描述格式：例如 HTTP 的 `Content-Length` 或 chunked encoding。

### 5.4 UDP 细节与选型陷阱

UDP 首部 8 字节，包含源端口、目的端口、长度、校验和。接收 API 保留数据报边界，但接收缓冲区太小可能截断数据报，底层 IP 仍可能分片。IPv4 UDP 校验和可按协议规则省略，IPv6 通常要求校验和，少数隧道规范有例外。

UDP `connect()` 只是设置默认对端并影响报文过滤/错误处理，不执行 TCP 三次握手。DNS 小查询适合较低握手开销；实时音视频常宁愿处理少量缺失也不等过期数据重传；文件和 SQL 结果通常更适合可靠传输。基于 UDP 的 QUIC 自己实现可靠性与拥塞控制，不能把底层 UDP 特征直接套给 QUIC。

## 6. TCP 可靠性、流控、拥塞与状态机

### 6.1 三次握手

1. 客户端发送 `SYN=1, seq=x`。
2. 服务端返回 `SYN=1, ACK=1, seq=y, ack=x+1`。
3. 客户端发送 `ACK=1, ack=y+1`。

三次握手的核心不是一句“建立可靠连接”，而是同步双方初始序列号、确认双向收发能力，并避免历史失效连接请求造成错误建立。SYN Flood 利用半连接资源，可通过 SYN Cookie、限速、扩大 backlog 和防火墙策略缓解。

```text
客户端                                      服务端
CLOSED                                      LISTEN
SYN-SENT       -- SYN seq=x ---------------->
               <- SYN+ACK seq=y ack=x+1 ---- SYN-RECEIVED
ESTABLISHED    -- ACK seq=x+1 ack=y+1 ------>
                                            ESTABLISHED
```

第三次 ACK 可以携带应用数据。第一包丢失由客户端按策略重传 SYN；第二包丢失，客户端或服务端的计时器会促成重传；纯第三次 ACK 丢失时，并非客户端专门为该纯 ACK 启动重传定时器，服务端重发 SYN+ACK 后可再次得到 ACK，后续带有效 ACK 的数据也可能使握手完成。

### 6.2 四次挥手与 TIME_WAIT

TCP 全双工，两个方向可以独立关闭，因此常见流程是 FIN、ACK、FIN、ACK。主动关闭方进入 TIME_WAIT，等待 2MSL：

- 确保最后 ACK 丢失时仍能重发确认。
- 让旧连接中的延迟报文离开网络，避免污染后续同四元组连接。

CLOSE_WAIT 过多通常说明应用没有及时关闭连接；TIME_WAIT 多常见于主动关闭、短连接过多或高并发客户端，不应简单当作服务端 bug。

```text
A 主动关闭                                  B 被动关闭
FIN-WAIT-1   -- FIN seq=u ------------------>
             <- ACK ack=u+1 --------------- CLOSE-WAIT
FIN-WAIT-2                                  业务继续发剩余数据
             <- FIN seq=v ----------------- LAST-ACK
TIME-WAIT    -- ACK ack=v+1 ---------------->
等待 2MSL                                   CLOSED
CLOSED
```

ACK 和 FIN 可以合并，所以关闭不必严格对应四个独立报文。双方同时关闭时状态路径也不同。TIME_WAIT 通常落在主动关闭方，并非固定在客户端；协议以 2MSL 解释，具体时长取决于系统实现，不是所有机器都等 120 秒。

### 6.3 可靠传输

- 校验和发现传输错误。
- 序号和 ACK 处理乱序、丢失和重复。
- 超时重传使用 RTO，RTO 应根据 RTT 和偏差动态估计。
- 三个重复 ACK 通常触发快速重传；SACK 可更精确报告已收到的非连续块。

ACK 表示对端 TCP 已接收相应字节，不代表对端应用读取、SQL 提交或邮件成功入库。连续字节中的空洞会阻止正常有序交付；SACK 告诉发送端哪些非连续区间已经收到，减少无谓重传。

RTT 样本存在波动，RTO 需要包含平滑 RTT 和偏差。RFC 6298 的典型更新系数为 alpha=1/8、beta=1/4，形式为 `RTO = SRTT + max(G, 4*RTTVAR)`。重传后缺乏明确时间戳区分的 ACK 会造成样本歧义，Karn 算法避免用这类样本更新估计；连续超时采用退避。

### 6.4 流量控制与拥塞控制

- 流量控制：接收方通过 `rwnd` 限制发送，防止接收缓存溢出。
- 拥塞控制：发送方通过 `cwnd` 感知网络容量，减少网络拥塞。
- 实际可发送窗口近似为 `min(rwnd, cwnd)`。
- 经典算法包括慢开始、拥塞避免、快速重传、快速恢复；现代 Linux TCP 还可能使用 CUBIC 等算法。

**经典 Reno 教学模型：**慢开始每轮 RTT 近似翻倍，而非每个 ACK 都翻倍；拥塞避免每 RTT 近似增加 1 MSS。达到 ssthresh 后增长放缓。超时时，门限通常按在途数据的一半并设下限，拥塞窗口降低并重新慢开始；三个重复 ACK 的快速恢复路径和超时路径不同。Reno 进入快恢复时有 `ssthresh + 3*MSS` 的临时窗口膨胀，收到覆盖恢复点的 ACK 后再回落。现代系统的初始 cwnd 和算法可能不同，不要把“初始窗口总是 1 MSS”作为定律。

**零窗口：**接收方通告 rwnd=0 后，发送方停止普通新数据发送，并按持久计时器发送零窗口探测，避免“窗口重新打开的通知丢失”造成双方永久等待。它与探测闲置连接的 TCP keepalive 不同。

### 6.5 状态排查

常见状态：`LISTEN → SYN-SENT/SYN-RECV → ESTABLISHED → FIN-WAIT/CLOSE-WAIT → TIME-WAIT → CLOSED`。

命令示例：

```bash
ss -tanp
ss -s
netstat -an | findstr 8765
```

### 6.6 三种保活、Nagle 与延迟确认

| 名称 | 所在层 | 实际目的 |
|---|---|---|
| HTTP keep-alive | 应用层连接管理 | 复用一个连接处理多个请求，减少建连 |
| TCP keepalive | 操作系统 TCP | 可选的闲置连接探测，默认周期常不适合秒级业务 |
| WebSocket/业务心跳 | 应用层 | 感知业务路径是否响应，定义更短失效时间 |

Nagle 在有未确认的小报文时倾向合并后续小数据，减少小包；延迟 ACK 为减少 ACK 数量可能稍作等待，两者在小包交互场景可能增加等待。`TCP_NODELAY` 可以关闭 Nagle，但会增加小包开销，应根据延迟分位数和报文模式验证，而不是一概打开。

### 6.7 RST、shutdown、close 与连接数量

FIN 表示该方向有序结束，缓冲中的已有数据仍可读出；RST 表示连接异常终止，常见于未监听端口或连接状态不匹配。`shutdown(SHUT_WR)` 关闭发送方向，仍可接收对端数据；`close` 释放一个 fd 引用，实际 TCP 生命周期还受其它引用与协议状态影响。

已建立 TCP 连接由两端 IP 和端口区分，单台服务器的同一个监听端口可以服务大量客户端。客户端连接同一目的地址/端口时会受临时源端口等资源限制；它不意味着整个服务器最多只接受 65535 个连接。

## 7. DNS、DHCP 与 URL 全链路

### 7.1 DNS

DNS 是分层、分布式命名系统。解析过程涉及本地缓存、递归解析器、根、顶级域和权威服务器。递归查询由服务器替客户端继续查询；迭代查询返回下一步应访问的服务器信息。

常见记录：A、AAAA、CNAME、MX、NS、TXT、SRV。TTL 决定缓存有效期，缓存旧记录会造成“改了 DNS 但客户端仍访问旧地址”。

DNS 通常使用 UDP 53；大响应、区域传送或特定实现可能使用 TCP。不要把“DNS 永远只用 UDP”当作绝对结论。

传统 DNS 不带 EDNS 时的 UDP 消息大小上限为 512 字节，这不是 UDP 协议的最大载荷。EDNS 可协商更大的 UDP 响应；出现 TC 截断标志时可重试 TCP。DoT 通常在 TLS 上运行 DNS，DoH 在 HTTPS 上传递 DNS，DNSSEC 则验证 DNS 数据来源与完整性，三者功能不同。

解析链通常是 stub resolver 向递归解析器提问，后者先看缓存，未命中再迭代询问根、TLD、权威节点；不是每次页面请求都访问根服务器。`NXDOMAIN` 表示名称不存在，`SERVFAIL` 是解析过程失败，排查方向不同。

### 7.2 DHCP DORA

`Discover → Offer → Request → ACK`。客户端可通过 DHCP 获取 IP、掩码、默认网关和 DNS。跨网段时依赖 DHCP Relay。

### 7.3 浏览器输入 URL 的完整链路

1. 读取浏览器、系统和 DNS 缓存。
2. DNS 解析域名得到 A/AAAA。
3. 判断目标是否同网段，必要时 ARP 获取网关 MAC。
4. 建立 TCP；HTTPS 还要执行 TLS 握手。
5. 发送 HTTP 请求，服务端经过网关、负载均衡、应用、缓存和数据库。
6. 返回响应，浏览器处理压缩、缓存、重定向、HTML/CSS/JS 子资源。
7. 连接可能通过 keep-alive、HTTP/2 或 HTTP/3 复用。

面试追问要主动指出：域名解析、连接建立、TLS、服务端排队和数据库耗时都可能贡献最终 TTFB。

## 8. HTTP/1.1、HTTP/2、HTTP/3 与 WebSocket

### 8.1 HTTP 基础

请求由方法、目标、版本、首部、空行和可选 body 组成；响应由版本、状态码、首部和 body 组成。

常见方法：

- GET：获取资源，通常安全、幂等、可缓存。
- POST：提交或触发处理，通常不保证幂等。
- PUT：整体替换，语义上幂等。
- PATCH：部分修改，是否幂等取决于设计。
- DELETE：删除，语义上通常幂等，但响应不必完全相同。

状态码：2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务端错误。`401` 表示缺少/无效认证，`403` 表示已识别但无权限，不能混为一谈。

### 8.2 HTTP/1.1

支持持久连接、Host、分块传输、范围请求和缓存协商。keep-alive 减少重复握手，但连接池过大可能造成服务端连接数、文件描述符和线程压力。

### 8.3 HTTP/2

使用二进制分帧、同一连接多路复用、HPACK 首部压缩和流优先级。它减少了应用层队头阻塞，但底层 TCP 丢包仍可能阻塞同一连接上的所有流。

### 8.4 HTTP/3/QUIC

QUIC 基于 UDP，自己实现可靠传输、流、多路复用和 TLS 1.3 集成，避免 TCP 连接级队头阻塞，并支持连接迁移。面试重点是“概念和权衡”，不要把 QUIC 说成没有丢包或没有拥塞控制。

准确边界：QUIC 每条流内部仍是有序字节流，缺字节时该流仍会等待；跨独立流不再由 TCP 的同一个字节序列牵连。一个丢失包若承载多个流的数据，这些流都会受影响，连接级拥塞控制也会共同限制流。连接迁移依赖连接 ID、路径验证和具体协商条件。

### 8.5 WebSocket

经典 WebSocket 通过 HTTP/1.1 Upgrade 完成握手，成功响应通常为 101，之后在 TCP 连接上使用帧双向通信；WSS 还使用 TLS。HTTP/2、HTTP/3 下的 WebSocket 使用扩展 CONNECT，不能一概套用 HTTP/1.1 升级流程。

项目答题点：

- 心跳检测半开连接。
- 断线重连要退避并避免重复订阅。
- 服务端要限制发送队列，处理慢客户端造成的背压。
- 多实例部署时，广播通常需要 Redis/Kafka 等共享通道。

### 8.6 缓存的完整判断顺序

浏览器先判断本地响应是否可直接复用，若新鲜则无需发起验证请求；不新鲜时可带校验器向服务端验证。响应未修改时返回 304，客户端复用已有响应体；修改过则返回 200 和新内容。

| 字段 | 含义 | 常见误区 |
|---|---|---|
| Cache-Control: max-age=60 | 以响应年龄判断的新鲜期 | 不是数据库缓存 TTL |
| no-cache | 允许存储，复用前必须成功验证 | 与“完全不缓存”不同 |
| no-store | 要求缓存不存储本次请求/响应 | 不等于清除之前全部缓存，也不是防泄露承诺 |
| private / public | 约束共享缓存能否存储 | 私有缓存指用户侧缓存，不是加密 |
| ETag / If-None-Match | 表示的版本校验器及条件请求 | ETag 不要求一定是文件 MD5 |
| Last-Modified / If-Modified-Since | 基于修改时间验证 | 秒级精度与服务器时钟会影响判断 |
| Vary: Accept-Encoding | 缓存键需考虑该请求头 | 遗漏可能返回不匹配的表示 |

如果请求同时包含 If-None-Match 和 If-Modified-Since，前者优先用于相关条件判断。接口含用户私有信息时要谨慎设计缓存键、共享缓存和认证响应策略，避免用户间串数据。[S2]

### 8.7 状态码与重定向

| 状态 | 常见语义 | 面试时的行动 |
|---|---|---|
| 200 / 201 / 204 | 成功 / 资源创建 / 成功但无内容 | 区分返回实体和空响应 |
| 206 / 304 | 部分内容 / 缓存条件满足而无需传实体 | Range 与条件缓存不是一回事 |
| 301 / 302 | 永久 / 临时重定向 | 历史客户端可能将 POST 改成 GET |
| 303 | 通常改用 GET 获取另一资源 | 表单提交后跳转可使用 |
| 307 / 308 | 临时 / 永久且保留方法与内容 | 关注敏感请求是否被重定向到另一站点 |
| 400 / 404 / 405 | 请求错误 / 资源未找到 / 方法不支持 | 检查参数、路径、方法 |
| 409 / 429 | 状态冲突 / 请求过多 | 使用业务冲突语义或退避，尊重 Retry-After |
| 500 / 502 / 503 / 504 | 内部异常 / 上游异常响应 / 暂不可用 / 网关等待超时 | 区分网关和应用日志 |

HTTP 的“安全方法”指预期不改变资源业务状态，不是“不会泄露”；幂等指重复相同操作的预期效果与一次相同，不要求每次响应码相同。DELETE 首次 204、再次 404 仍可符合幂等。GET 与 POST 的安全性不取决于参数放 URL 还是 body，二者都需要 TLS 和应用授权。

### 8.8 报文边界、压缩与常用首部

HTTP/1.1 首部以 CRLF 分行，空行后是消息体；body 长度按 Content-Length、合法的 Transfer-Encoding 及状态/方法等规则确定。chunked 将 body 分成长度块，最后以零长度块结束；它是传输分帧方式，不是 gzip 压缩。HTTP/2、HTTP/3 以各自帧和流结束机制处理边界，不使用 HTTP/1.1 的 chunked 语法。

`Content-Type` 描述媒体类型，`Content-Encoding` 描述压缩等内容编码，`Accept` 和 `Accept-Encoding` 是客户端接受范围。Host 用于 HTTP/1.1 虚拟主机，Origin 表示请求发起源。代理和后端要一致解释报文长度，使用成熟解析器，避免不一致造成请求串位。

### 8.9 Cookie、跨域、CORS 与 CSRF

Cookie 是浏览器保存并按域、路径、有效期等规则发送的数据；Session 是跨请求维持用户状态的机制，两者不是同一概念。HttpOnly 限制脚本读取 Cookie，Secure 要求安全传输，SameSite 控制部分跨站附带行为；这些属性各有作用，彼此不能替代。

同源由 scheme、host、port 共同决定；跨源不等于跨站。CORS 是浏览器对跨源响应读取的约束，不是服务端身份认证。非简单请求可能先发 OPTIONS 预检；携带凭据的跨源请求通常要返回明确允许的 Origin 和凭据头，而非使用通配符 `*`。

CSRF 借助浏览器自动附带的认证信息触发用户未预期的操作，可结合 SameSite、CSRF token、Origin 校验防范。XSS 是恶意脚本在站点上下文运行，重点在输出转义、避免危险 DOM 注入、CSP 和依赖治理。Bearer token 的存储位置改变攻击面；把它放 localStorage 并不自动更安全。

### 8.10 轮询、长轮询、SSE 与 WebSocket

轮询实现简单但有空请求和延迟；长轮询让服务器挂住请求等待事件；SSE 通过 HTTP 长响应单向推送，原生事件模型含重连与 Last-Event-ID；WebSocket 适合双向频繁交互。单向交通监控刷新不一定必须使用 WebSocket，应按双向性、频率、代理兼容和重连补偿成本选择。

原生浏览器 WebSocket API 不像普通 HTTP 客户端那样任意设置 Authorization 请求头，因此需要明确实际认证路径，例如 Cookie、握手参数、或 STOMP CONNECT 的鉴权；token 出现在 URL 时要防止日志记录。WebSocket 握手成功也不等于每条业务消息都有权限。

## 9. HTTPS/TLS 与认证安全

### 9.1 TLS 提供什么

- 机密性：对称加密保护应用数据。
- 完整性：MAC/AEAD 防止篡改。
- 身份认证：证书链和主机名校验确认服务端身份。

非对称密码主要用于身份认证和密钥协商，对称密码承担大量数据加密，因为性能更高。

### 9.2 TLS 1.3 面试时序

以证书认证、(EC)DHE、没有 HelloRetryRequest 的完整 TLS 1.3 握手为例：ClientHello 携带支持版本、密码套件与 key_share；ServerHello 选定参数并给出服务端 key_share。此时双方已能派生握手流量密钥。ServerHello 之后的 EncryptedExtensions、Certificate、CertificateVerify 和 Finished 由握手密钥加密。客户端校验证书链、主机名、握手签名与 Finished，再发送自己的 Finished；应用数据使用单独派生的应用流量密钥保护。[S3]

```text
Client                          Server
ClientHello + key_share ------>
                       <------ ServerHello + key_share
         双方派生握手流量密钥
                       <------ {EncryptedExtensions}
                       <------ {Certificate, CertificateVerify}
                       <------ {Finished}
{Finished} ------------------->
[Application Data] <----------> [Application Data]
```

普通完整 TLS 1.3 握手约 1 RTT，不计 TCP 建连；HelloRetryRequest 会增加往返。TLS 1.2 的常见完整握手通常需要更多往返。TLS 1.3 恢复可使用 PSK，证书消息可能省略；0-RTT 依赖已有会话材料，早期数据有重放风险，不适合直接承载会产生不可重复副作用的操作。

必须提到：证书校验失败、主机名不匹配、过期、信任根不可信、私钥泄露都会破坏安全性；HTTPS 不等于应用层授权正确。

### 9.3 JWT 与 Session

JWT 通常放在 `Authorization: Bearer <token>` 中。JWT 的签名保证完整性，但默认不加密 payload；泄露 token 就可能被重放，通常需要短 access token、refresh token、轮换和撤销策略。

Session 不限定状态存储位置。传统服务端 Session 常在 Cookie 中保存会话 ID，状态放服务端；你的族谱项目使用 Flask 默认签名 Cookie session，序列化状态存客户端，签名检测篡改而非加密。JWT 是令牌格式，是否真正无状态取决于撤销和会话管理设计。两者都应配合 HTTPS、合理过期时间、最小权限和日志脱敏。[S7]

### 9.4 面试常见密码学混淆

- 哈希不是加密：通常用于摘要，密码存储要使用适合密码的慢哈希/KDF 与盐。
- 数字签名不是“用私钥加密全部内容”的泛化说法，它验证来源与完整性；证书把身份与公钥关联，由证书链建立信任。
- 现代 TLS 1.3 不再使用旧式 RSA 密钥传输，证书可用于签名认证，而会话密钥通过 (EC)DHE 或 PSK 派生。
- 前向保密指长期私钥后来泄露也不应使之前被记录的会话全部可解密；它与密码定期修改不是同一概念。
- SNI 帮服务端选择站点证书，ALPN 协商 h2/http1.1 等应用协议；SNI 是否明文还与 ECH 部署有关，不要一概说“HTTPS 隐藏所有域名信息”。

### 9.5 TLS 终止、mTLS 与内部链路

TLS 终止在网关时，浏览器到网关加密不代表网关到应用也加密。应画出每一段链路并说清证书与认证边界。mTLS 除验证服务端也验证客户端证书，可用于服务间身份认证，但资源授权仍需业务规则。证书续期、时钟误差、信任根和 TLS 版本不匹配是常见运维故障。

## 10. Socket 编程、粘包拆包与 I/O 多路复用

### 10.1 TCP 服务端生命周期

```text
socket
  -> setsockopt(SO_REUSEADDR)
  -> bind
  -> listen
  -> accept
  -> recv/read + send/write
  -> shutdown/close
```

客户端通常为 `socket → connect → send/recv → close`。`accept` 返回的是已建立连接的新 fd，监听 fd 继续接受新连接。

### 10.2 部分读写与错误处理

- `read/recv > 0`：读取到部分数据，不代表一条完整消息。
- 对长度大于 0 的 TCP 读取，返回 `0`：对端关闭发送方向，且此前数据已读完；本端仍可能继续发送。
- `EINTR`：可重试；非阻塞 fd 遇 `EAGAIN/EWOULDBLOCK` 应等待下一次事件。
- `write/send` 可能短写，必须循环发送剩余数据。
- Linux 服务端要处理 SIGPIPE，避免对已关闭连接写入导致进程异常终止。

### 10.3 粘包/半包解决方案

推荐的长度前缀协议：

```text
[4-byte network-order length][payload bytes]
```

接收端先循环读取 4 字节，再校验长度上限，最后循环读取 body。若使用换行或 NUL 分隔符，仍要维护接收缓冲区并处理一批数据中包含多条消息的情况。

### 10.4 select、poll、epoll

| 机制 | 典型问题/特点 |
|---|---|
| select | fd 集合有大小限制，每次调用需要拷贝并扫描 |
| poll | 没有固定 fd 数组上限，但仍可能线性扫描 |
| epoll LT | 就绪状态持续通知，编程相对简单 |
| epoll ET | 通常配合非阻塞 fd，处理到 EAGAIN，保留尚未发送的数据 |

epoll 不是任何场景都更快；连接数、活跃度、事件比例、线程模型和数据结构都会影响结果。

事件就绪不等于 I/O 已经完成，更不保证有完整业务消息；多个线程竞争同一 fd 时，醒来再读也可能遇到 EAGAIN。ET 不保证 fd 保持就绪时重复提醒，事件也可能被合并，应将 read/accept 处理到 EAGAIN 或妥善安排后续继续处理。写队列空时取消 EPOLLOUT 关注，避免 socket 长期可写造成忙循环。[S6]

### 10.5 线程模型

- 一连接一线程：实现直观，但线程数、栈内存和上下文切换可能成为瓶颈。
- 线程池：控制并发上限，减少创建销毁。
- Reactor + epoll：事件循环处理 I/O，业务投递线程池。
- Proactor：由系统/运行时完成异步 I/O 后通知应用。

### 10.6 接收状态机与发送队列伪代码

以下是设计伪代码，不是已合入 RMDB 的修改。它演示累积缓冲、长度检查、部分消息和多消息处理；真正实现还要处理内存分配、状态所有权、超时和测试。

```text
on_readable(connection):
    loop:
        n = recv(fd, temporary_buffer)
        if n > 0:
            append received bytes to connection.input
            while input contains at least 4 header bytes:
                length = decode_uint32_big_endian(header)
                if length > MAX_MESSAGE: close with protocol error
                if input contains fewer than 4 + length bytes: break
                extract one message; retain the remaining bytes
                dispatch complete message
        else if n == 0:
            mark peer write-half closed
            reject an unfinished message if protocol requires completeness
            break
        else if errno == EINTR: continue
        else if errno == EAGAIN: break
        else: close and report error

on_writable(connection):
    while pending output exists:
        n = send(fd, pending bytes)
        if n > 0: advance output offset
        else if errno == EINTR: continue
        else if errno == EAGAIN: retain output and wait
        else: close and report error
    if output is empty: stop watching writable events
```

TCP 字段通常用网络字节序，大端 32 位长度可通过 htonl/ntohl 处理；不要把 C++ 结构体裸内存直接当跨平台协议，填充、字节序和整数宽度可能不同。Qt/Java/Python 客户端也必须遵守同一线格式。

### 10.7 背压、超时与零拷贝

当下游慢于上游时，应限制每连接输入/输出缓冲、业务队列和并发数，必要时暂停读取或拒绝新请求。无限堆积任务只是把拥塞转为内存耗尽。区分连接超时、单次读写超时、闲置超时和整次业务 deadline；收到一小段数据不应自动让恶意慢连接永不超时。

sendfile、splice 等可减少部分用户态/内核态拷贝，适合文件或管道转发，但不等于传输过程没有任何拷贝。TLS、压缩、序列化和数据来源会改变收益。Java NIO 的 Selector/Channel/ByteBuffer 与事件驱动思想相关，具体实现依平台；了解 Netty 的 EventLoop 和解码器可作拓展，不要宣称项目已经使用 Netty。

## 11. 简历项目网络专题

### 11.1 RMDB TCP 客户端/服务端

已知证据：客户端使用 `AF_INET + SOCK_STREAM`，服务端执行 `bind/listen/accept`，每个客户端进入线程处理；默认端口和固定缓冲区以源码为准。

原整理时读取的版本中，客户端默认端口为 8765，接收缓冲 8192 字节，发送 `command.length()+1` 以包括 NUL；随后单次 recv。服务端也直接 read 固定缓冲再解析。NUL 是已有的协议约定，但并没有因此自动获得按 NUL 收齐/循环解析的逻辑。客户端单次 write/recv 和服务端单次 read/write 是应逐项分析的边界，而非已经改好的完整协议层。

**推荐 2 分钟回答：**

“RMDB 的客户端与服务端采用 TCP 字节流。服务端启动监听 socket，绑定地址和端口后 listen，accept 得到连接 fd，再由线程读取命令、调用数据库执行链并写回结果。这里真正需要注意的是一次 read 不保证对应一条 SQL，write 也可能短写。当前教学实现使用固定缓冲和命令结束标记；生产化会改成长度前缀或明确分隔符，循环处理半包/多包，增加长度上限、超时、EINTR/EAGAIN、对端关闭和错误码处理。”

**高频追问：**

1. 为什么用 SOCK_STREAM？需要可靠、有序、面向连接的字节流。
2. 为什么不能 `recv` 一次就解析？TCP 没有应用消息边界。
3. 一连接一线程有什么问题？线程数、上下文切换、慢客户端占用资源。
4. 如何修复短写？维护发送偏移，循环 `send` 直到完成或失败。
5. 线程参数有什么坑？不要把会被下一次 accept 覆盖的局部变量地址直接传给线程，应按值复制或独立分配。
6. 如何验证？`nc`/自写客户端发送拆分消息，Wireshark 或 tcpdump 观察 TCP 段和应用层边界。

### 11.2 RMDB 内部执行链与网络边界

```text
TCP 命令
 -> Parser/AST
 -> Analyze
 -> Planner
 -> Portal/Executor
 -> BufferPool/Disk/Index
 -> 格式化结果
 -> TCP write
```

网络层负责连接和字节传输，SQL 解析和事务锁在应用/数据库内核层。不要把 TCP ACK 当作数据库事务 COMMIT；客户端收到响应也不自动代表日志已持久化，必须结合项目事务语义回答。

### 11.3 ITMS-BD 请求链

```text
React/Axios
 -> HTTP JSON + Bearer JWT
 -> Spring Security Filter
 -> Controller
 -> Service
 -> Repository/JPA
 -> PostgreSQL
```

扩展链路包括 Redis、Kafka `traffic-data` 和 WebSocket。面试重点：HTTP keep-alive 与数据库连接池不同；Kafka 消费确认和 HTTP 响应也不是同一个事务；跨服务写入需要幂等键、重试和补偿。

### 11.4 Flask 族谱系统

Flask 提供 HTTP 路由和会话，psycopg2 访问 PostgreSQL。网络相关追问包括：WSGI worker 模型、请求超时、连接池、参数化 SQL、Cookie 的 HttpOnly/Secure/SameSite、反向代理和分页查询。

项目使用默认签名 Cookie session，登录态包括 user_id 等信息。保护 SECRET_KEY、控制过期和 Cookie 属性；`session.clear()` 主要清除当前浏览器的会话，单凭此操作不会撤销已被复制的旧 Cookie。即时撤销需要服务端校验状态等额外机制。族谱的 10 万级成员、30 代是模拟数据规模，不是线上用户规模。

慢关系查询应拆成网络 RTT、数据库执行、Python 遍历、序列化和响应大小分别测量；把逐条查库改成每层批量查可减少 RTT 叠加。EXPLAIN ANALYZE 衡量数据库内的执行，不涵盖浏览器到数据库整条网络路径。

### 11.5 Docker Compose 网络

Compose 服务通常通过服务名进行 DNS 解析，容器端口和宿主机映射端口不是一回事。`depends_on` 只表达启动顺序，不能保证数据库已完成初始化；应使用健康检查、重试和启动探针。

普通启动依赖不足以保证就绪；若配置 `condition: service_healthy` 并有健康检查，可等待相应条件，但仍应处理服务运行期失效。容器里的 localhost 指自身网络命名空间，后端访问 PostgreSQL 通常用服务名与容器端口，浏览器访问前端则用宿主地址和映射端口。

### 11.6 Kafka、Redis 与数据库连接的递进追问

**Kafka：**bootstrap.servers 是发现入口；客户端拿到元数据后会直接连接各 broker 的 advertised.listeners。入口能通但后续失败，要查元数据发布的主机名/端口是否在客户端网络可达。分区内日志有序，跨分区没有天然全局顺序；重试、幂等生产、acks 和消费者 offset 各解决不同层次的问题。业务写数据库和提交 Kafka offset 分属两个系统，TCP 可靠传输不提供跨系统“恰好一次”。

**Redis：**RESP 使用类型和长度描述消息，在 TCP 字节流上建立边界；pipeline 能合并等待、减少多次 RTT，却不自动变成事务。缓存更新失败需要定义过期、重试和一致性策略，先说明项目实际缓存路径，再讨论设计扩展。

**PostgreSQL：**数据库协议也有自身消息格式。连接池复用昂贵的连接和认证步骤，但线程等连接的时间可能高于网络时间。池容量不应简单等于 Web 最大线程数；结合数据库并发能力、事务时长、等待时间和超时配置。COMMIT 发出后连接断开，客户端可能处于结果未知状态，需要通过业务键或状态查询确认。

## 12. CAN/CANoe 汽车网络面试

### 12.1 经典 CAN 重点

- 标准帧常见 11 位 ID，扩展帧可使用 29 位 ID。
- ID 越小，仲裁优先级通常越高。
- CAN 采用非破坏性位仲裁：发送显性位的节点可覆盖隐性位，失去仲裁的节点停止发送，等待下一次。
- DLC 表示数据长度语义；经典 CAN payload 最多 8 字节，CAN FD 语义不同，不能混答。
- 报文解析要明确起始位、长度、Intel/Motorola 字节序、缩放和偏移。
- CRC、ACK、错误帧、错误计数器和 Bus-Off 是可靠性/故障处理重点。

### 12.2 CANoe 测试闭环

`需求编号 → 信号/报文定义 → 节点仿真或刺激 → Trace 观察 → 日志保存 → 判定 → Jira/Codebeamer 缺陷与回归`。

回答实习经历时重点放在“如何验证和定位”：输入刺激是什么、预期报文是什么、实际 payload 哪一位不符、如何复现、如何关联需求和回归，而不是声称独立设计整车算法。

## 13. 网络故障排查与系统设计

### 13.1 分层排查顺序

1. 进程是否存活：日志、端口、线程、文件描述符。
2. 链路是否可达：网卡、路由、ARP、ping、traceroute。
3. 端口是否监听：`ss -lntp`、`netstat`、`nc`。
4. DNS 是否正确：`dig`、`nslookup`、TTL 和多 A 记录。
5. TCP 是否建立：SYN/SYN-ACK/ACK、重传、RST、状态数量。
6. TLS 是否成功：证书、SNI、ALPN、协议版本。
7. HTTP 是否正确：状态码、首部、超时、重试、响应体。
8. 应用依赖是否拥塞：线程池、连接池、Redis、Kafka lag、数据库慢 SQL。

### 13.2 常见故障定位

| 症状 | 首先看什么 | 常见根因 |
|---|---|---|
| 连接超时 | SYN 是否返回、路由和防火墙 | 服务未监听、网络 ACL、端口映射 |
| 连接被拒绝 | 目标端口状态 | 进程未启动、监听地址错误 |
| CLOSE_WAIT 多 | 应用 fd 生命周期 | 业务未 close、异常路径泄漏 |
| TIME_WAIT 多 | 谁主动关闭、短连接比例 | 连接复用不足、客户端主动关闭 |
| HTTP 401 | Authorization、过期时间 | token 缺失/签名不匹配 |
| HTTP 403 | 权限与资源归属 | 认证通过但授权失败 |
| Kafka 积压 | consumer lag、分区数 | 消费慢、下游阻塞、分区不均 |
| WebSocket 断开 | 心跳、代理 idle timeout | 半开连接、负载均衡超时 |

### 13.3 网络系统设计回答模板

需求与指标 → 协议和接口 → 连接管理 → 超时/重试 → 幂等 → 限流/熔断 → 数据一致性 → 观测指标 → 容量估算 → 故障与回滚。

例如设计实时交通推送：HTTP 用于查询和控制，WebSocket 用于推送，Kafka 解耦事件生产/消费，Redis 做热点缓存；需要定义事件 ID、重复消费、断线补偿、心跳、背压和多实例广播。

## 14. 高频面试题与标准答题骨架

### Q1：三次握手为什么不能两次？

两次不足以让服务端确认客户端能收到自己的响应，也无法可靠排除历史失效 SYN 导致的错误连接。第三次 ACK 让服务端确认客户端已收到服务端选择的 ISN，双方状态达成一致。

### Q2：TCP 粘包是 TCP 的 bug 吗？

不是。TCP 提供连续字节流，不提供应用消息边界。粘包和半包是应用读取粒度与发送粒度不一致的表现，需要长度前缀、分隔符或固定长度协议解决。

### Q3：流量控制和拥塞控制有什么区别？

流量控制面向接收方能力，核心变量是 rwnd；拥塞控制面向网络承载能力，核心变量是 cwnd；发送窗口取两者较小值。

### Q4：TIME_WAIT 为什么存在？

如果对端没有收到最终 ACK 而重传 FIN，TIME_WAIT 期间本端仍可再次回复 ACK；纯 ACK 本身没有针对该 ACK 的重传计时器。等待也让旧报文过期，降低同四元组新连接被旧报文污染的风险。

### Q5：HTTP/2 是否完全解决队头阻塞？

只减少了 HTTP 层不同请求之间的队头阻塞；同一 TCP 连接发生丢包时，TCP 仍要按序交付，所有 HTTP/2 流仍可能受影响。HTTP/3/QUIC 在流级别进一步缓解。

### Q6：JWT 安全吗？

JWT 只是令牌格式和签名机制，不天然加密、不可撤销或防重放。要配合 HTTPS、短过期、刷新轮换、撤销策略、算法白名单、密钥保护和日志脱敏。

### Q7：epoll ET 为什么必须循环读？

ET 不保证 fd 仍就绪时持续重复提醒，事件可能合并，也可能由后来到达的数据触发。应用不应依赖新通知处理缓冲区内已经存在的数据；通常用非阻塞 fd 持续读取到 EAGAIN，遇 EOF 或不可恢复错误则按连接状态处理。

### Q8：输入 URL 后发生什么？

按 DNS、ARP/路由、TCP 或 QUIC、TLS、HTTP、服务端处理、响应渲染顺序说明，并指出缓存、连接复用和代理会改变路径。

### Q9：Kafka 如何避免重复消费影响业务？

不能只依赖 offset。使用业务幂等键、唯一约束、去重表、事务性 outbox 或可重试/死信流程；明确 offset 提交是在业务处理前还是后，以及失败时如何重放。

### Q10：如何证明网络优化有效？

先定义基线和指标：连接建立耗时、DNS/TLS/TTFB、吞吐、P50/P95/P99、重传率、错误率、连接数、CPU 和内存；再用 curl、抓包、服务指标和压测对照，不能只说“感觉变快”。

## 17. 计算题与逐步解答

### 17.1 传输时延和传播时延

**题目：**发送 1500 字节的包，链路速率 100 Mbit/s，距离 1000 km，传播速率 `2×10^8 m/s`，忽略排队和处理。求时延。

1. 包长 `1500×8 = 12000 bit`。
2. 传输时延 `12000/100000000 = 0.12 ms`。
3. 传播时延 `1000000/200000000 = 5 ms`。
4. 最后一个比特到达约需 `5.12 ms`。

**追问：**带宽翻倍只让 0.12 ms 变成 0.06 ms，并不缩短传播的 5 ms。链路时延与应用排队时延要分开估算。

### 17.2 带宽时延积和窗口吞吐上限

**题目：**带宽 100 Mbit/s，RTT=40 ms，求填满链路的在途数据量。

`BDP = 100×10^6×0.04 = 4×10^6 bit = 500000 byte`，约 488 KiB。

如果有效窗口只有 64 KiB，忽略其它因素，吞吐上限约为 `65536/0.04 = 1638400 byte/s = 13.1 Mbit/s`。窗口扩大选项能让 TCP 支持更大的接收窗口，但还需考虑 cwnd、丢包和应用读取速度。

### 17.3 CIDR 子网

**题目：**`192.168.10.77/26` 的网络地址、广播地址、常规可用主机范围是什么？

`/26` 掩码是 `255.255.255.192`，末字节块大小 64。77 落在 64 至 127 这一块，所以网络地址是 `.64`，广播地址是 `.127`，常规主机范围 `.65` 至 `.126`，62 个。

**边界：**`2^(32-prefix)-2` 是普通 IPv4 广播子网的计算方式，不要机械套到 `/31` 点到点网络和 `/32` 主机路由。

### 17.4 最长前缀匹配

路由表如下：

| 前缀 | 下一跳 |
|---|---|
| 0.0.0.0/0 | A |
| 10.0.0.0/8 | B |
| 10.1.0.0/16 | C |
| 10.1.2.0/24 | D |

目的地址 `10.1.2.99` 选 D，`10.1.3.5` 选 C，`10.2.1.1` 选 B，`192.0.2.1` 选 A。匹配的是目的前缀，不是“哪一条路由先写在表里”。

### 17.5 IPv4 分片

**题目：**原 IPv4 包总长 4000 字节，首部固定 20 字节，下游 MTU=1500，允许分片，无选项。

原载荷 3980 字节。每个非最后分片最多携带 `floor((1500-20)/8)×8 = 1480` 字节，以满足偏移单位 8 字节。

| 分片 | 数据长度 | 总长度 | 片偏移 | MF |
|---|---|---|---|---|
| 1 | 1480 | 1500 | 0 | 1 |
| 2 | 1480 | 1500 | 185 | 1 |
| 3 | 1020 | 1040 | 370 | 0 |

三个分片使用对应的同一数据报标识进行重组。丢失一个分片会使原 IP 数据报重组失败，最终可能引发 TCP 的重传；IP 层本身不会因为这个丢失自动重传。

### 17.6 TCP 序号和累计 ACK

**题目：**A 的 SYN 序号为 1000，握手后依次发送 200 字节、100 字节，求序号和 ACK。

- SYN 消耗一个序号，首段数据起始为 1001。
- 200 字节覆盖 1001 至 1200，接收后期望 1201。
- 第二段从 1201 开始，覆盖至 1300，累计 ACK=1301。
- 若第一段丢失、第二段先到，普通累计 ACK 仍指向 1001；SACK 可额外报告后面的已收区间。
- 接着发 FIN，序号为 1301，对 FIN 的确认号为 1302。

序号按字节计算，不按“这是第几个包”计算；ACK 不包含报文段边界信息。

### 17.7 滑动窗口和剩余发送额度

**题目：**rwnd=64 KiB，cwnd=16 KiB，已发未确认 10 KiB，忽略其它细节，最多还能发多少新数据？

有效窗口 `min(64,16)=16 KiB`，剩余额度约 `16-10=6 KiB`。不能把 rwnd 和 cwnd 相加，也不能忘记已经在途的数据。

### 17.8 简化拥塞窗口演变

**题目：**假设教学模型中初始 cwnd=1 MSS，ssthresh=8 MSS，每 RTT 收到完整 ACK，无延迟 ACK、无丢包。

各轮开始的窗口可写为 `1 → 2 → 4 → 8 → 9 → 10`。到门限后进入加性增长。若题目改为现代初始 cwnd 或 CUBIC，答案会变化；答题先声明模型和参数。

### 17.9 停止等待利用率和分组流水线

**停止等待：**若一个包发送耗时 `t_tx`，RTT 不含该包串行化时间，ACK 发送耗时忽略，则发送链路利用率近似 `t_tx/(t_tx+RTT)`。`t_tx=1 ms, RTT=9 ms` 时为 10%。滑动窗口允许多个包在途，可提高长肥网络利用率。

**流水线：**N 个等长包穿过 H 条同速率存储转发链路，忽略传播、排队与处理，完成时间为 `(N+H-1)×L/R`。如 N=10、H=3、每包传输 1 ms，共 12 ms；不是把 10 个包各自三跳简单相加成 30 ms。

### 17.10 香农、奈奎斯特与信噪比

**题目：**信道带宽 3000 Hz，SNR=30 dB。

先转线性值 `S/N=10^(30/10)=1000`。香农容量 `3000×log2(1001)` 约为 29.9 kbit/s。若再给理想无噪声的 M=4 级码元条件，奈奎斯特式给出 `2×3000×log2(4)=12000 bit/s`；这两式约束的条件不同，结合使用时取符合题设的更严格限制。

### 17.11 CRC 小例题

**题目：**数据 `1101`，生成多项式比特串 `1011`（最高次数为 3）。

1. 数据后补 3 个 0 得 `1101000`。
2. 对 `1011` 做模 2 长除法，减法用 XOR，余数为 `001`。
3. 发送串为 `1101001`。
4. 接收端用相同除数验证，完整串余数为 0。

CRC 余数为 0 只说明通过该差错检测规则，不意味着通过身份认证。

### 17.12 并发容量与超时预算

**题目：**稳定情况下平均到达率 1000 请求/s，平均系统逗留时间 0.2 s，估算平均在途请求数。

Little 定律 `L = λW` 给出约 200。这里的 W 必须是同一统计边界内的平均逗留时间，不要用平均 QPS 乘 P99 后宣称精确容量。它不是直接等于数据库连接池大小，很多请求可能在计算、排队或等待其他依赖。

**追问：**整条请求 deadline=1 s，若三个服务各自重试三次，实际耗时可能远超预算，还可能放大负载。应传递剩余 deadline，设置单次超时、有限重试和退避，并先判断操作幂等性。

### 18.3 实验三 抓 RMDB 的握手和消息边界

前提：RMDB 开发服务已经运行，先查实际端口和监听地址。本章不会替你启动或修改数据库。

```powershell
Test-NetConnection 127.0.0.1 -Port 8765
Get-NetTCPConnection -LocalPort 8765 -ErrorAction SilentlyContinue
```

```bash
ss -lntp
tcpdump -i lo -nn -s 0 -c 80 'tcp port 8765'
```

Wireshark 显示过滤器可用 `tcp.port == 8765`，追踪一个连接用 `tcp.stream eq N`。N 从捕获结果选择，不是固定流号。分别观察 SYN、SYN+ACK、ACK、SQL 的 NUL 结束符、响应、FIN/RST。

**判定：**一个 SQL 请求在 TCP 流中可以完整，但拆到多个段；抓包中的段不等于 `recv` 调用返回块。网卡卸载、GRO/TSO 和捕获点还会影响你看到的段大小。Wireshark 的 retransmission 标签是分析器判断，需要结合序号与实际捕获完整性确认。

### 18.4 实验四 消息拆分与合并的测试矩阵

针对开发中的应用解码器，不依赖公网服务即可设计以下测试：

| 输入情况 | 预期行为 |
|---|---|
| 4 字节长度头拆成 1+3 字节 | 累积后解析，不提前读取 body |
| body 分三次到达 | 收齐前不交给 SQL/业务解析 |
| 两条完整消息一次到达 | 正好解析两条，保持顺序 |
| 完整消息后跟下一条半个头 | 第一条正常处理，保留后半部分 |
| 长度超过上限或整数溢出边界 | 明确协议错误，不分配无限内存 |
| 对端在 body 中间 FIN | 标记不完整消息，释放对应状态 |
| 一次 send 只成功发送前一部分 | 保存偏移并继续，不重复发送已完成部分 |
| 非阻塞读/写返回 EAGAIN | 不忙等，保留状态等待合适事件 |

本机 `socketpair` 可以验证流式切块行为，但不能代替真实 TCP 握手/拥塞测试。测试通过证明解析器处理了这些输入，不等于生产并发和长期稳定性已验证。

### 18.5 实验五 HTTP 缓存与跨域

在浏览器开发者工具 Network 页访问你运行的前端，观察 Cache-Control、ETag、If-None-Match、304 和是否命中 memory/disk cache。关闭“Disable cache”才观察正常缓存行为；使用内容变化与未变化两种情况对照。

联调前后端不同端口时，观察是否有 OPTIONS、实际 Origin、Access-Control-Allow-Origin 和凭据设置。curl 能得到响应而浏览器报 CORS，说明“服务通了”和“浏览器允许脚本读取”是两件事。此实验不会向服务写入业务数据。

### 18.6 实验六 POP3 模拟响应与 TLS

针对第 19 章的 POP3 解析函数构造输入，不连接真实邮箱执行删除：

```text
+OK message follows\r\n
Subject: test\r\n
\r\n
..leading-dot\r\n
.\r\n
```

其中 `\r\n` 表示真实 CRLF 字节，不是发送反斜杠字符。预期得到正文 `.leading-dot`，最终单点行终止当前多行响应。把同样字节在每个可能位置切开，解析结果应一致；如果提前 EOF，应报协议截断而非当作成功的空邮件。

TLS 验证可针对专门测试端点或开发服务测试有效证书、错误主机名、不受信任证书和握手超时。证书错误应保留为错误，不通过关闭校验把测试变绿。真实 POP3 的 DELE 属于写操作，实验优先使用模拟服务器或专用测试邮箱，不直接操作重要邮件。

### 19.3 POP3 状态机

```text
TCP 建连 / 按配置完成 TLS
        |
        v
AUTHORIZATION: 欢迎响应，USER/PASS 认证
        |
        v
TRANSACTION: STAT / LIST / UIDL / RETR / DELE / RSET
        |
        | QUIT
        v
UPDATE: 尝试提交被标记的删除，释放资源，关闭连接
```

异常断开或自动登出不等同于正常进入 UPDATE。认证未完成时的 QUIT 也不是提交删除。你的解析器要校验 +OK/-ERR，区分 socket 异常、TLS 异常、认证失败、协议格式错误和业务状态未知。[S8]

### 19.4 POP3 命令逐项解释

| 命令 | 返回/作用 | 实现注意 |
|---|---|---|
| USER / PASS | 身份认证 | 凭据保密，不进入调试日志；在受保护链路使用 |
| STAT | 当前消息数及总大小 | 是概览，不含每封内容 |
| LIST / LIST n | 多行列表或单条大小 | 区分有参数和无参数响应形式 |
| UIDL / UIDL n | 稳定消息标识 | 用于跨会话识别；应有不支持时的明确降级策略 |
| RETR n | 多行原始邮件 | 处理 dot-stuffing、结束行、大小与超时限制 |
| DELE n | 在事务中标记删除 | +OK 不代表更新阶段已经提交 |
| RSET | 撤销本会话删除标记 | 与重新下载邮件不同 |
| NOOP | 保持会话并验证响应 | 协议层活性，不证明所有业务功能正常 |
| QUIT | 从事务状态进入 UPDATE | 要检查回复，连接断开时可能需要再次查询 |

### 19.5 为什么使用 readline，而不是一次 recv

`sock.makefile('rb').readline()` 会借助缓冲把多个底层读取组合到一个行结束符，是文本行协议的便利接口；它没有让 TCP 获得消息边界。SMTP/POP3 的一条逻辑响应还可能包含多行，需要在行级读取之上实现协议状态。

行读取仍需考虑单行长度上限、超时、EOF、字符集和缓存生命周期。POP3 邮件内容是字节串，先保留原始数据，再按邮件头/MIME 决定解码；不要在 socket 层一律当 UTF-8，否则非 UTF-8 内容可能损坏。

### 19.6 单点结束与点转义

POP3 多行响应以单独一行 `.` 结束。若真实数据行以点开头，服务器会加一个点；客户端在确定不是结束行后移除一个额外点。

```text
线上字节行              解析动作
.\r\n                   结束多行响应，不交给邮件正文
..hello\r\n             恢复为 .hello\r\n
...hello\r\n            恢复为 ..hello\r\n
abc.\r\n                原样保留
```

检查顺序很重要：先判断完整单点结束行，再做 dot-unstuffing。不要对整封邮件做“删除所有双点”的替换，否则会损坏非行首数据。

### 19.7 序号与 UIDL 是最值得准备的追问

消息序号 `1,2,3...` 是当前 maildrop 会话里的位置，跨连接可能变化。UIDL 用来识别邮件，通常适合作为跨会话去重依据；本地缓存还应纳入邮箱账户和服务器范围，不要假定不同用户的 UID 全球唯一。

**具体风险：**用户先读取列表、关闭连接，稍后点击“删除第 5 封”；若其它客户端已删除前面的邮件，新会话的第 5 封可能不是原邮件。报告内嵌代码的删除 worker 重新建连并使用保存的 index，这使“重新按 UIDL 查找当前 index”成为明确的改进点。

**回答方案：**本地选中记录保存 `(账户范围, UID)`；删除前在新会话执行 UIDL 得到当前 UID→序号映射；确认目标仍在，再 DELE 当前序号，最后检查 QUIT 更新结果。如果 UID 不存在，返回“目标已不存在”，不继续按旧序号删除。

### 19.8 DELE 成功不等于删除成功

DELE 返回 +OK 只表示当前事务已标记删除，通常在随后 QUIT 进入 UPDATE 时才尝试真正移除。连接突然断开、QUIT 出错或回复丢失，需要分别处理。

报告代码的上下文退出会尝试 QUIT，并吞掉部分退出异常；删除 worker 随后更新本地 deleted 标记。作为复盘可指出：吞掉关键提交异常可能让本地状态与服务器不一致。改进是把“成功发出 DELE”“QUIT 提交确认”“待重新核验”拆开，不把清理代码的成功等同于业务成功。

如果 QUIT 已被服务端执行但最后响应在网络中丢失，客户端面对的是结果未知。重新连接后按 UIDL 查询目标是否仍存在，并以幂等方式同步本地状态；不要盲目重试旧序号。这与数据库 COMMIT 超时、HTTP 写请求超时是同一类分布式结果不确定问题。

### 19.9 SMTP 流程需要懂，但区分分工

```text
服务端 220 欢迎
客户端 EHLO -> 服务端 250 能力列表
可选 STARTTLS -> 服务端 220 -> TLS 握手 -> 再次 EHLO
认证（实际方式按服务器能力）
MAIL FROM -> RCPT TO（每个接收人）-> DATA
服务端 354 后发送邮件内容，以 CRLF . CRLF 结束
服务端 250 接受 -> QUIT -> 221
```

EHLO 能力列表可多行返回，以 `250-` 开头表示后面还有行，以 `250 ` 表示最后一行。AUTH LOGIN 里的 Base64 是编码，不是加密；服务器实际支持的机制与策略要协商，不能默认任何服务器都允许 LOGIN。

MAIL FROM/RCPT TO 是信封地址，邮件头中的 From/To/Cc 是内容字段，二者职责不同。SMTP 250 表示当前服务器接受邮件继续处理，不保证已经进入对方收件箱，更不表示收件人已阅读。5xx 常表示永久失败，4xx 常表示暂时失败，重试时还要评估重复投递。[S9]

### 19.10 隐式 TLS 与 STARTTLS

隐式 TLS 在 TCP 建立后立即 TLS 握手，再传应用协议；常见邮件端口包括 465（邮件提交）和 995（POP3S）。STARTTLS 先开始明文应用协议，再发送升级命令并执行 TLS；升级前不应发送敏感凭据。邮件提交常见 587，服务器间 SMTP 常见 25，具体配置以服务器为准。

SMTP STARTTLS 成功后需要重新 EHLO，因为升级前的能力知识不应直接沿用。你的 POP3 类按报告支持 use_ssl 的隐式 TLS 路径；不要因此声称已经实现 POP3 的 STLS 升级。`ssl.create_default_context()` 与 `server_hostname` 帮助校验证书和主机名，应保留这类默认校验。

### 19.11 MIME、原始邮件与 GUI 线程

MIME 用 Content-Type、boundary、Content-Transfer-Encoding 等描述文本、附件和多部分结构。它与 TCP 分包不同；Base64 增加编码体积，不提供保密性。邮件头字符集与正文字符集可不同，HTML 正文显示也需要考虑不可信内容。

网络等待放后台线程可以避免 GUI 主线程卡住，结果通过队列交回主线程更新界面。进一步检查：后台线程是否直接读取或操作 Tk 控件、SQLite 连接是否跨线程使用、多个收取任务是否竞态、窗口退出时怎样取消任务。根据真实实现回答，不能把“用了线程”当作线程安全证明。

### 19.12 个人专项自测

1. **为什么收邮件用 POP3 而不是 SMTP？** SMTP 负责提交/转发，POP3 提供邮箱检索；IMAP 更偏服务器端文件夹和多设备状态同步。
2. **邮件读完会自动删除吗？** 不是协议必然行为；POP3 删除需要相应命令和更新阶段。
3. **为什么有 LIST 还要 UIDL？** LIST 给当前序号/大小，UIDL 支持跨会话识别与去重。
4. **服务器响应拆成多次 TCP 到达怎么办？** 字节缓冲累计至完整行，再累积到完整响应，含超时和上限。
5. **怎么测“删除没有删错”？** 模拟跨会话重排，按目标 UID 解析当前序号，验证 DELE 目标与提交结果。
6. **QUIT 断开后本地为什么不直接标成功？** 可能未提交，也可能已提交但回复丢失，需要结果未知态与重新核验。
7. **证书自签或域名错误怎么办？** 报告具体校验原因；开发环境使用明确的测试信任根，不关闭生产验证。
8. **个人贡献怎么说？** POP3 客户端与接收删除是报告记录的职责；SMTP、MIME、缓存和 GUI 说明合作边界。

## 20. 面试纠错表与模拟面试

### 20.1 高频错误结论纠正

| 容易背错的说法 | 更准确的回答 |
|---|---|
| 一次 send 对应一次 recv | TCP 不保留应用边界，应用自行 framing |
| TCP ACK 等于业务成功 | ACK 只确认字节接收，业务状态需应用确认 |
| 第三个握手 ACK 丢了就由 ACK 定时器重发 | 纯 ACK 无该计时器，服务端重传 SYN+ACK 等可促成再次确认 |
| 关闭一定四个包 | FIN/ACK 可合并，也有同时关闭、RST 等路径 |
| TIME_WAIT 永远是客户端 | 通常由主动关闭端进入，双方同时关闭也有不同路径 |
| HTTP 长连接就是 TCP keepalive | 请求复用与闲置连接探测是不同机制 |
| UDP 最大只能 512 字节 | 512 是传统 DNS UDP 消息限制，不是 UDP 最大载荷 |
| UDP 不可靠，所以 QUIC 不可靠 | QUIC 在 UDP 上实现可靠性与拥塞控制 |
| HTTP/2 消灭所有队头阻塞 | 底层 TCP 字节流阻塞仍存在 |
| HTTP/3 任何流都不阻塞 | 同流缺字节仍等待，各流还共享部分连接资源 |
| GET 安全因为没 body，POST 加密因为有 body | 方法语义、传输加密与参数位置相互独立 |
| no-cache 与 no-store 一样 | 前者可存但要验证，后者要求不存储本次响应 |
| Session 一定在服务端 | Flask 默认 session 使用客户端签名 Cookie |
| JWT payload 有签名所以别人看不到 | 常见 JWT payload 可读，签名不等于加密 |
| epoll 是异步 I/O 完成通知 | epoll 主要通知就绪，应用仍执行读写 |
| ET 每次只读一点等下一次通知就行 | 不保证重复提醒，妥善处理到 EAGAIN |
| SO_REUSEADDR 能修复所有 TIME_WAIT | 它不是跳过连接生命周期的通用开关 |
| ping 成功就是服务正常 | ICMP、TCP 监听、TLS 和业务是不同检查层 |
| CAN ACK 表示目标应用已经处理 | ACK 只反映总线上接收节点认可帧，不保证业务执行 |
| POP3 DELE 返回 +OK 就已永久删除 | 还涉及 QUIT 的 UPDATE 与结果确认 |
| 原来的 POP3 序号可用于重连后删除 | 应按 UIDL 重新解析当前序号 |
| SMTP 返回 250 就是对方读到了 | 只表示当前阶段服务器接受处理 |

### 20.2 追加二十道短问答

**Q11 一个监听端口如何服务多个客户端？** 监听 socket 接受连接，内核用各连接两端 IP/端口区分，accept 返回独立的已连接 fd；端口相同不意味着连接相同。

**Q12 accept 前还是后完成三次握手？** 典型 TCP 服务由内核先处理握手，已建立连接进入接受队列，应用 accept 取出连接；具体内核队列和拥塞行为有实现细节。

**Q13 全局锁与多连接线程有什么关系？** 多线程能同时等待网络，但若数据库执行链被一把全局锁覆盖，执行仍可能串行。应测锁等待，不要用线程数量直接证明并发吞吐。

**Q14 HTTP 请求超时可以直接重试吗？** 先判断操作是否幂等以及原操作是否可能已执行。读请求通常较易重试，写请求需幂等键、状态查询或补偿，仍要限制重试预算。

**Q15 为什么浏览器能打开网页但某个接口 504？** 入口可达不代表上游及时返回。检查代理超时、应用队列、连接池和慢查询；504 是定位线索，不是最终根因。

**Q16 DNS 已更新为何仍访问旧服务？** 多层缓存、TTL、长连接复用、应用自身 DNS 缓存和不同解析器都可能导致旧地址继续使用。

**Q17 HTTP 的缓存与 Redis 缓存有什么不同？** 前者复用 HTTP 表示并遵循客户端/代理语义，后者是应用显式管理的数据缓存；失效策略、权限边界和键设计各自独立。

**Q18 REST 就是 JSON 加 HTTP 吗？** REST 是围绕资源、统一接口、无状态交互、缓存等约束的架构风格；JSON 只是常见表示格式，路径 `/doSomething` 也不因传 JSON 就自动符合 REST。

**Q19 POST 可以做到幂等吗？** 可以在业务层使用幂等键和唯一约束实现，重复请求返回已记录结果；但 POST 方法本身不声明幂等，客户端不能因此普遍假定它可无条件重试。

**Q20 数据库连接池耗尽就是网络慢吗？** 不一定。长事务、连接泄漏、慢 SQL 和锁等待都会占连接。应同时看借用等待、活跃连接、事务时长和数据库活动。

**Q21 Docker 里为什么不直接连 localhost:5432？** localhost 通常是当前容器自身，数据库在另一容器时应使用对应服务名和容器端口，或明确配置其它网络模式。

**Q22 Kafka bootstrap 端口可达却消费失败？** 客户端获取元数据后连接 advertised.listeners，发布了不可达地址、认证配置错误或分区 leader 故障都可能导致后续失败。

**Q23 为什么要有 traceId？** 它把网关、应用和下游日志关联起来，以请求为单位还原路径；只看单台机器 CPU 或总耗时容易误判。不要在 trace 中记录完整令牌或私密邮件。

**Q24 TCP 重传和 Kafka 重试是一回事吗？** 前者恢复传输字节，后者恢复应用协议操作；即使 TCP 数据可靠，服务端处理后响应丢失仍可能造成应用重试与重复副作用。

**Q25 mTLS 已验证证书还要权限控制吗？** 要。证书帮助识别调用方，是否允许读写某个资源由授权规则决定。

**Q26 小包正常大包失败先查什么？** PMTU、隧道额外首部、ICMP 过滤、代理请求体上限和应用最大消息限制，按网络层与应用层分别排查。

**Q27 为什么 connection pool 不是越大越好？** 过多并发可能挤压数据库、增加排队和上下文切换；以延迟分位数、等待和吞吐曲线找合适范围。

**Q28 如何检测半开长连接？** 综合 TCP 错误、适当的 keepalive 和有期限的业务心跳。没有流量时，连接状态保持 ESTABLISHED 不证明对端业务仍存活。

**Q29 CAN 与 TCP 都重传，为什么语义不同？** CAN 面向总线帧和仲裁、错误检测；TCP 面向端到端字节序列、窗口和拥塞。两者都不直接提供业务事务的原子提交。

**Q30 没有做过某种生产方案怎么答？** 先说已实现或读到的路径，再把设计推演标为改进方案，给出验证方法和代价，不把方案包装成历史经历。
