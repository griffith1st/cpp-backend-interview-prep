## 建连与关闭 Q58–Q62

### Q58 三次握手为什么不是两次

**口述：**双方各选择初始序号，SYN、SYN+ACK、ACK 同步序号并建立连接状态。第三步让服务端确认自己的 SYN 已被客户端接收，也防止历史失效 SYN 直接使服务端进入正常已建立状态。

**机制与边界：**`seq=x → seq=y,ack=x+1 → ack=y+1`；SYN 消耗一个序号，第三次 ACK 可携带数据。第三次纯 ACK 丢失时，并不存在专门针对该纯 ACK 的重传计时器；服务端重发 SYN+ACK 可促成再次确认。握手解决连接建立，后续可靠交付仍依赖重传、序号等机制。

**追问/验证：**画两端状态，解释 SYN-SENT、SYN-RECEIVED、ESTABLISHED；在测试环境抓握手并观察重传，不以背出三个包代替状态分析。

### Q59 SYN 队列和 accept 队列

**口述：**Linux 典型实现中，SYN 队列记录握手尚未完成的连接请求；accept 队列保存已经完成握手、等待应用 accept 的连接。accept 主要取出已建立连接，不是应用自己执行三次握手。

**机制与边界：**listen backlog、系统上限和 SYN cookie 等共同影响排队行为，参数含义依内核版本而异。应用线程长期忙于计算，会使已完成连接等待；增加 backlog 只是缓冲突发，不增加稳定处理能力。

**追问/验证：**为什么端口监听但连接体验差？同时看连接队列、应用事件循环延迟、fd 限额和失败计数，不仅看进程是否存活。

### Q60 四次挥手与半关闭

**口述：**TCP 全双工，两个方向分别结束。A 发 FIN 后，B 先确认，B 的剩余数据发送完再发自己的 FIN，A 再确认。FIN 表示这一方向不会再有新数据，不等于另一方向也结束。

**机制与边界：**ACK 与 FIN 可合并，抓包未必正好四个包；同时关闭和 RST 中止有其它状态路径。对正长度 TCP 读取，recv=0 表示已读完且对端关闭发送方向，本端仍可能继续发送。FIN 也消耗一个序号。

**追问/验证：**比较 shutdown(SHUT_WR) 与 close；解释 FIN-WAIT-1、FIN-WAIT-2、CLOSE-WAIT、LAST-ACK。

### Q61 TIME_WAIT 的作用

**口述：**正常非同时关闭时，主动关闭方通常进入 TIME_WAIT。一方面对端若没收到最后 ACK 而重发 FIN，本端可再次确认；另一方面等待旧报文失效，降低同四元组新连接受旧报文影响的风险。

**机制与边界：**协议用 2MSL 说明等待，实际时长依系统。客户端、服务端都可能主动关闭，TIME_WAIT 不固定属于客户端。数量高不必然是故障，应结合临时端口占用、建连失败率、连接复用率与短连接比例。

**追问/验证：**不要先复制一组内核调参；先用 ss 识别责任端、目标集中程度和连接寿命，评估连接池与协议复用。

### Q62 CLOSE_WAIT 的根因

**口述：**本端已收到对端 FIN 并确认，但应用尚未结束自己的发送方向。短暂存在正常，持续积累常见于未关闭 fd、异常分支遗漏或业务线程长时间卡住。

**机制与边界：**不代表网络对端“还没发 FIN”；它描述的是本机连接状态。关闭应与连接所有权、RAII 和线程生命周期一起设计。

**追问/验证：**关联 `ss -tanp`、进程 fd 数和线程栈；复现超时、解析失败、客户端提前断开三条路径，检查资源是否都能释放。

## 可靠性与连接管理 Q63–Q67

### Q63 序号 ACK 滑动窗口与重传

**口述：**TCP 按字节编号，累计 ACK 指向期望的下一个连续字节。发送端保留未确认数据，接收端重组乱序数据；超时或丢包推断触发重传。SACK 可报告非连续已收区间。

**机制与边界：**收到 ACK 表示对端 TCP 接收了字节，不等于应用已读取、SQL 已提交。TCP 没有业务消息边界；一个完整消息可跨多个段，一个段也可含多条消息。

**追问/验证：**`seq=1001,len=200` 被连续收到后 ACK=1201；若前段丢失，后段先到，累计 ACK 停在缺口而非直接跳到最后一段。

### Q64 流量控制与拥塞控制

**口述：**rwnd 表示接收能力，保护接收端缓存；cwnd 表示发送方根据网络状况控制的在途上限，缓解拥塞。实际窗口近似取 min(rwnd,cwnd)，还需减去已经在途的字节。

**机制与边界：**rwnd=0 后停止常规新数据，但可通过持久计时器探测窗口恢复，避免窗口更新丢失造成永久等待。零窗口探测不同于闲置连接 keepalive。

**追问/验证：**rwnd=64 KiB、cwnd=16 KiB、在途10 KiB，剩余额度约6 KiB。区分“慢客户端不读”与“网络拥塞丢包”。

### Q65 快速重传 快速恢复和 RTO

**口述：**RTO 超时触发重传并退避；经典快速重传在三个重复 ACK 后推断缺失段。快速恢复控制丢失后的窗口，和超时重回慢开始的路径不同。

**机制与边界：**RTO 常用平滑 RTT 和偏差计算：`SRTT + max(G,4*RTTVAR)`。重传后的 ACK 有样本歧义，Karn 思路避免污染估计。Reno 慢开始近似每 RTT 翻倍，而非每个 ACK 翻倍；现代 CUBIC 等不应机械套 Reno 公式。

**追问/验证：**丢包可能来自拥塞、无线差错或抓包遗漏，“出现重复 ACK 就证明网络完全不拥塞”是错误结论。关联重传、RTT、窗口和捕获点。

### Q66 粘包与 framing

**口述：**所谓粘包是应用把 TCP 字节流误当消息流。可以用定长、分隔符或长度前缀建立边界，接收端累积数据并循环提取完整消息。

**机制与边界：**长度前缀例如 4 字节网络序长度+body；先检查长度上限和溢出，再等待收齐。保留未完成尾部，一次可解析多条。send/write 也可能短写，要保存输出偏移。JSON 本身不自动定义连续多个 JSON 的边界。

**追问/验证：**测试头被拆开、body 分批、两包合并、超长声明、中途 EOF、EINTR/EAGAIN。发包大小不保证 recv 返回大小，不能只在本机正常请求下测试。

### Q67 长连接 连接池与心跳

**口述：**长连接降低建连成本；连接池限制并复用连接；业务心跳检测对端业务响应；空闲超时释放长期不活跃资源。它们分别解决成本、容量、活性和资源回收问题。

**机制与边界：**HTTP keep-alive 不是 TCP keepalive。探测频率要考虑代理 idle timeout、移动网络与开销；重连用退避和抖动，任务需幂等或状态确认。连接池越大不一定吞吐越高，下游会排队。

**追问/验证：**进程显示 ESTABLISHED 不证明对端业务存活；统计借连接等待、池内活跃数、连接年龄和心跳超时。

## 应用协议与事件模型 Q68–Q74

### Q68 HTTP 三个版本的队头阻塞

**口述：**HTTP/1.1 请求复用仍受响应顺序等限制；HTTP/2 用二进制帧和流多路复用，但同一个 TCP 字节流丢包仍影响各流有序交付；HTTP/3 用 QUIC，让独立流不受 TCP 全连接字节缺口牵连。

**机制与边界：**QUIC 流内部仍有序，缺字节仍等待；多个流共享拥塞与部分连接资源。HTTP/2 HPACK、HTTP/3 QPACK 都是首部压缩，但动态表同步机制不同。QUIC 基于 UDP 不意味着没有可靠性和拥塞控制。

**追问/验证：**缓存 `no-cache` 是复用前验证，`no-store` 要求不存储本次响应；304 不带要替换的响应体。GET/PUT/DELETE 的幂等语义不意味着响应状态码每次相同。

### Q69 TLS 中证书 密钥交换和加密

**口述：**证书和签名认证身份，密钥协商让双方得到共享秘密，对称 AEAD 高效保护数据。证书信任链、主机名与有效期都要验证，HTTPS 不替代业务授权。

**机制与边界：**普通证书型 TLS1.3：ClientHello/key_share → ServerHello/key_share 后派生握手密钥；之后加密发送 EncryptedExtensions、Certificate、CertificateVerify、Finished。客户端验证并发送 Finished，应用流量用另行派生的密钥。完整握手约1 RTT，不计 TCP 且不含重试；0-RTT 有重放风险。

**追问/验证：**SNI 选择站点，ALPN 协商应用协议；网关终止 TLS 不代表内部链路也加密。JWT 签名不是加密，客户端会话也可能是签名 Cookie。

### Q70 DNS 递归 迭代 缓存和 TTL

**口述：**客户端通常向递归解析器提问；解析器查缓存，未命中再迭代问根、TLD、权威服务器。A/AAAA 是地址，CNAME 是别名，TTL 控制缓存寿命。

**机制与边界：**不必每次访问根。DNS 可用 UDP 和 TCP，传统无 EDNS 的512字节限制不是 UDP 最大载荷；截断等情况可重试 TCP。DoH/DoT 保护传输，DNSSEC 验证 DNS 数据，目标不同。

**追问/验证：**DNS 更改后长连接仍连旧 IP，解析器不同也会给出不同结果。用 dig/Resolve-DnsName 观察地址与 TTL，不仅看浏览器错误页。

### Q71 非阻塞 connect 怎样判断结果

**口述：**connect 立即返回0表示已成功；返回-1且 errno=EINPROGRESS 表示进行中。关注可写/错误事件并设置 deadline，事件到达后用 getsockopt(SOL_SOCKET,SO_ERROR) 读取结果，0才表示连接成功。

**机制与边界：**“可写”不是成功证明，失败连接也可能触发事件。检查 getsockopt 自身返回值，超时或失败时清理注册和 fd，避免 fd 复用后的旧回调误操作新连接。

**追问/验证：**分别测试成功监听、无监听导致拒绝、丢弃报文导致超时。题目针对 Linux；Windows 的接口与错误处理不同。

### Q72 Reactor Proactor 与 one loop per thread

**口述：**Reactor 通知就绪，应用执行读写；Proactor 在异步操作完成后分发完成结果。one loop per thread 约束事件循环线程归属，不是一种不同的传输协议。

**机制与边界：**Muduo 的 EventLoop、Poller、Channel、TcpConnection 分离轮询、fd 事件和连接状态，跨线程通过任务队列与唤醒进入 loop 线程。回调里做长阻塞计算仍会拖慢所有同 loop 连接。

**追问/验证：**当前固定版本 EPollPoller 未默认设置 EPOLLET，不能把“读过 epoll ET”说成“Muduo 一定使用 ET”。依据注册标志和读写处理核对实际模型。

### Q73 慢客户端与背压

**口述：**客户端读取慢会占满发送缓冲，服务端持续生成结果会堆积应用输出队列。背压让上游根据下游容量减速、暂停或拒绝，而不是无限加队列。

**机制与边界：**限制每连接输出字节、全局队列与请求并发；高水位触发减速策略，写不完保留偏移，EAGAIN 等下一次事件，队列空时取消 EPOLLOUT，防止忙循环。定时器与公平调度避免单连接长期霸占 loop。

**追问/验证：**慢读客户端测试观察队列字节、RSS、P99和正常连接延迟；高水位回调本身只是通知，不代表已执行限流。

### Q74 如何建立网络故障时间线

**口述：**以一次请求和时间戳为线索，分解 DNS、建连、TLS、请求发送、服务处理和响应接收。用状态、抓包和应用 trace 共同支持根因，避免把超时统一叫网络慢。

**机制与边界：**ss 看连接和队列，tcpdump 看序号/重传/RST，curl 看协议与累计时间字段，服务日志看线程/连接池/下游耗时。ping 只检查 ICMP 路径；抓包卸载与丢样也可能误导。

**追问/验证：**记录目标、环境、时间窗口、实际命令、观察与反证。TLS 抓包不直接显示明文业务，token/Cookie/邮件内容不要写进公开报告。

## 计算和抓包练习

1. 100 Mbit/s、RTT40 ms 的 BDP 为500000 byte；64 KiB窗口给出的粗略上限约13.1 Mbit/s，说明大带宽下窗口仍可能限速。
2. `192.168.10.77/26` 属于 `.64` 网络，广播 `.127`，常规主机 `.65–.126`。解释为什么 `/31` 不能机械减2。
3. TCP SYN seq=1000，随后200 byte数据从1001开始，累计 ACK=1201；再发 FIN seq=1201，ACK=1202。

下面是待做练习，不是已有测试结果。Linux：

```bash
ss -s
ss -tanp
tcpdump -i lo -nn -s 0 -c 80 'tcp port 8765'
curl --connect-timeout 5 --max-time 15 -sS -o /dev/null \
  -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} first=%{time_starttransfer} total=%{time_total}\n' \
  https://example.com/
```

抓包端口按实际测试服务调整。Windows 使用 curl.exe 和输出 NUL，可用 Get-NetTCPConnection、Test-NetConnection；Linux 抓包需要相应权限。curl 时间字段是累计时刻，代理/重定向/连接复用会影响阶段差分。
