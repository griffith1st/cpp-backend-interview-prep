## 1. 知识地图与操作系统职责

操作系统解决三类问题：把硬件资源抽象成可编程接口，把有限资源分配给多个执行者，并隔离错误和保护资源。进程让程序拥有独立的地址空间视图，线程提供可调度执行流，文件把不同存储设备抽象成统一的名字与字节接口。抽象简化了程序，但没有消除竞争、等待与失败。

理解后端请求时可以沿这条主线追踪：

```text
网络报文到达 -> 内核接收缓冲 -> 就绪通知/唤醒
-> 服务线程被调度 -> 读取与解析 -> 等锁/连接池/数据库
-> 文件页读写与日志同步 -> 生成响应 -> 输出队列 -> 网络发送
```

每一步可能占用 CPU，也可能等待资源。一个请求的墙钟耗时大，并不意味着它使用的 CPU 时间大；CPU 低也不意味着请求没有排队。性能分析首先区分“在执行什么”和“在等待什么”。

| 课程主题 | 核心约束 | 后端中的具体表现 |
|---|---|---|
| 进程与调度 | CPU 同一时刻执行的线程有限 | 运行队列、线程池、抢占 |
| 同步 | 多执行者共享可变状态 | 锁竞争、数据竞争、死锁 |
| 内存管理 | 地址空间大于实际驻留资源 | 缺页、缓存、内存压力 |
| 文件系统 | 名字、内容与持久状态分离 | fd 泄漏、日志刷盘、重启恢复 |
| I/O | 数据准备与应用处理不同步 | 阻塞、事件循环、背压 |

回答机制题时使用固定顺序：需求是什么，维护哪些状态，正常路径怎样变化，失败发生在哪里，保证范围到哪里。具体项目再补源码、日志和测试证据。

## 2. 执行状态、系统调用与上下文切换

### 2.1 就绪、运行与阻塞

“就绪”表示具备运行条件但尚未分配 CPU；“运行”表示正在占用 CPU；“阻塞”表示等待某个条件，例如锁释放、数据到达或定时器到期。I/O 完成通常先使线程就绪，调度器随后决定何时运行它，并非设备一完成就立即执行用户代码。

Linux 的任务状态比教材三态更细。工具中常见 R 包括运行或可运行，S 常表示可被信号唤醒的睡眠，D 常表示不可中断睡眠，Z 表示僵尸。D 状态经常与 I/O 等待有关，但仅凭字母不足以定位具体设备或根因。应结合内核栈、等待位置和时间窗口。

### 2.2 用户态、内核态和事件来源

用户态代码受页表权限和 CPU 特权级限制。系统调用通过受控入口进入内核，例如 read、write、mmap 和 futex。硬件中断通常由设备异步触发；异常由当前执行指令产生，例如缺页或非法指令。缺页并不一定是错误，内核可以分配或装入页面后让指令重试。

进入内核需要保存必要的执行状态、检查参数并执行内核路径。一次系统调用可以直接完成，也可以睡眠等待。前一种路径有特权级转换，却未必发生线程上下文切换。调度切换还需保存寄存器、栈指针等执行上下文，跨地址空间可能改变页表根与翻译上下文。

不要把切换成本理解成“复制整个进程内存”。实际开销包含入口出口、调度、缓存局部性和 TLB 影响；地址空间标识、PCID/ASID 等硬件能力可降低部分翻译开销。CPU 数据缓存通常也不是每次切换就清空。

### 2.3 两个常见性能取舍

减少 syscall 次数可以通过批量读写实现，但批量越大，等待凑齐和单次处理时间也可能增加。把多个请求放进一次批处理，要同时检查吞吐和尾延迟。

阻塞等待会让出 CPU，忙等持续检查状态则占用 CPU。忙等在等待极短且运行环境可控时可能减少调度开销；等待网络或磁盘这类长尾事件时，持续空转通常消耗大量资源。

## 3. 进程、线程、协程与生命周期

### 3.1 三种执行组织方式

进程是地址空间与资源组织单位。一个进程中的线程通常共享代码、全局数据、堆与 fd 表，但拥有各自的寄存器、栈和线程局部存储。线程栈仍处于共享地址空间内，另一个线程若持有指针，也可能访问它；“私有栈”不是硬件隔离。

协程通常由用户态运行时保存和恢复执行状态，再映射到一个或多个内核线程上。协程适合把等待密集逻辑写成顺序形式，但一个内核线程同一时刻仍只执行一个执行流。协程中直接调用阻塞接口，可能阻塞承载它的整个线程，除非运行时替换接口、使用异步 I/O 或把阻塞任务转交其他线程。

| 方式 | 隔离与共享 | 调度方 | 主要代价或限制 |
|---|---|---|---|
| 多进程 | 地址空间通常隔离 | 内核 | IPC、地址空间与资源开销 |
| 多线程 | 易共享，也易相互破坏 | 内核 | 同步、线程栈、调度竞争 |
| 协程 | 由运行时定义共享关系 | 用户态运行时与内核 | 阻塞传播、取消、生命周期 |

### 3.2 fork、exec 与 wait

fork 返回两次：父进程得到子 PID，子进程得到 0，失败则父进程收到 -1。父子拥有逻辑独立的私有内存视图，Linux 通常利用 COW 延迟复制物理页。文件描述符表虽然复制，表项可能仍引用同一 open file description，因此可共享文件偏移和打开状态标志。

exec 成功后替换当前进程映像，PID 不因 exec 自身改变，成功路径不返回原程序。未设置 close-on-exec 的 fd 可能继续存在，因此服务程序常用 O_CLOEXEC、SOCK_CLOEXEC 等避免意外继承。

子进程退出后，内核保留退出码等信息供父进程 wait/waitpid 读取。尚待回收的退出记录表现为僵尸，已经不执行用户代码。孤儿则是父进程先退出而自身仍存活的子进程，通常由子收割进程或该 PID 命名空间的 init 接管；二者不是同义词。

多线程进程 fork 后，子进程只保留调用 fork 的线程。其他线程持有的锁状态可能被继承，却没有对应线程解锁。因此 fork 到 exec 之间应遵守 async-signal-safe 限制，避免普通日志库、分配器等复杂路径造成死锁。

### 3.3 退出也是并发协议

服务退出应先停止接收新任务，再通知等待者、处理或取消在途任务，等待工作线程结束，最后释放 fd、队列和共享对象。若主线程先销毁工作线程仍引用的对象，就会出现生命周期错误。RAII 能表达所有权和清理路径，但不能自动决定“何时所有并发访问已经结束”。

## 4. CPU 调度与性能指标

### 4.1 先定义指标

到达时间 A、首次运行时间 S、完成时间 C、CPU 服务总时长 B，在无 I/O 的教学模型中：周转时间为 C-A，等待时间为 C-A-B，响应时间为 S-A。带 I/O 时，周转还包含阻塞时间，不能直接把 C-A-B 全部称为就绪队列等待。

吞吐强调单位时间完成多少任务，响应时间强调首次得到服务有多快，尾延迟关注最慢一部分请求。公平性、吞吐和交互响应存在取舍，调度器没有对所有工作负载都最优的一套参数。

### 4.2 经典算法及其原因

FCFS 按到达顺序运行，开销小，但长任务排在前面会形成护航效应。非抢占 SJF 按预计服务时长选择短任务，在所有任务已知且同时到达等条件下可降低平均等待，但真实服务时长常未知，长任务还可能长期得不到机会。

SRTF 是抢占式的最短剩余时间优先；新短任务到达可以抢占长任务。时间片轮转 RR 周期性让各任务运行，缩短交互任务首次等待；时间片太短增加切换，太长逐渐接近 FCFS。优先级调度支持业务等级，但需要老化或其他机制控制饥饿。

多级反馈队列根据任务用完时间片、阻塞等行为调整等级，用历史行为近似判断交互型与计算型任务。它不是“优先级永远不变的多个队列”。

### 4.3 Linux 的版本边界

普通 Linux 调度不能直接等同于教材 RR。历史公平调度常用 CFS 和虚拟运行时间解释：按权重推进 vruntime，避免单个任务长期占用 CPU。Linux 6.6 起公平调度引入 EEVDF 的选择机制，强调资格与虚拟截止时间；具体行为应查看内核版本与对应文档。

SCHED_FIFO、SCHED_RR 是实时调度策略，SCHED_DEADLINE 采用运行预算、期限与周期等约束。实时策略不自动构成端到端实时保证，驱动、锁、缺页与下游仍可能带来不可控等待。

对后端服务，线程池大小没有统一“CPU 数乘二”答案。CPU 密集任务先按可用 CPU 配额和测量选择并行度；等待密集任务可以增加并发，但必须受队列、fd、数据库连接与内存预算限制。容器内看到的逻辑 CPU 数也未必等于实际 cgroup CPU 配额。

## 5. 进程间通信与同步边界

IPC 的选型先问数据边界、参与者位置、吞吐、故障隔离与流控。把同样的数据发送到另一个进程，不仅涉及复制，还涉及唤醒、调度和协议设计。

| 机制 | 数据模型与用途 | 同步或失败边界 |
|---|---|---|
| 匿名管道 | 常用于有亲缘关系进程的字节流 | EOF 依赖所有写端关闭，写满会等待或 EAGAIN |
| FIFO | 有路径名的管道 | 打开、读写与对端存在性有关 |
| 消息队列 | 保留消息边界与类型/优先级语义 | 队列容量、消息大小、生命周期 |
| 共享内存 | 多进程映射同一对象 | 内容发布、并发同步、损坏隔离需另行设计 |
| Unix domain socket | 同机流或数据报通信，可传 fd | 流需 framing，接口与权限有平台边界 |
| TCP socket | 同机或跨机可靠字节流 | 半关闭、超时、重连与业务结果未知 |
| 信号 | 异步事件通知 | 普通信号可能合并，不适合作为任意数据队列 |

管道的原子写边界值得单独记：POSIX 对长度不超过 PIPE_BUF 的写提供特定原子性保证；这不等于读端一次 read 就得到一条业务消息，也不等于超过 PIPE_BUF 的写不会交错。必须结合阻塞模式和写入长度理解。

共享内存避免了经系统调用逐次复制大块数据，但“双方都能看到这块内存”不等于并发正确。需要定义谁写、谁读、何时发布、槽位何时复用；跨进程 mutex 等还需使用适当的进程共享属性。普通 C++ mutex 不能仅因被放入 mmap 就自动获得可移植的进程间语义。

信号处理程序可能打断任何用户代码，不适合随意调用需要锁的函数。一个可解释的设计是：处理程序只设置合适的信号标志或通过允许的接口通知主循环，由正常线程上下文完成关闭、日志与资源回收。Linux 也可将相关信号集中交给专用处理线程或 signalfd，细节以信号屏蔽策略为准。

面试比较 IPC 性能时至少固定消息大小、发送次数、批量程度、CPU 亲和性和阻塞方式。小消息往往受 syscall 与唤醒开销影响，大消息更可能受复制和内存带宽影响。

## 6. 并发正确性与同步原语

### 6.1 先找共享状态与不变量

并发错误通常来自“看似一步”的操作实际上是多步。例如读取计数、加一、写回，两个线程都读到旧值就可能覆盖彼此结果。正确性不能只靠多运行几次没出错，必须说明操作在哪里线性化，以及读写之间建立什么先后关系。

在 C++ 中，缺少同步的冲突非原子访问构成 data race，行为未定义。volatile 不代替原子或锁；它也不建立跨线程 happens-before。mutex 的解锁和后续成功加锁可以建立同步关系，release/acquire 原子也可在匹配条件下发布数据。原子操作保证的是特定对象与规定的顺序关系，不自动维护跨多个字段的业务不变量。

### 6.2 原语比较

| 原语 | 解决的问题 | 应说明的边界 |
|---|---|---|
| mutex | 互斥修改共享状态 | 持锁时长、异常清理、统一锁顺序 |
| rwlock | 允许多个读者并行 | 写者饥饿、公平性与升级策略 |
| spinlock | 短等待时主动轮询 | 持锁方被抢占时浪费 CPU，避免长阻塞 |
| semaphore | 计数资源或并发配额 | 不等同于互斥锁所有权 |
| condition variable | 等待共享谓词改变 | 谓词由锁保护，循环检查 |
| atomic | 不可分的对象操作及顺序关系 | 复合结构仍需算法与内存回收设计 |
| futex | Linux 用户态等待字的内核支撑 | 不是完整高级锁，竞争时可睡眠/唤醒 |

典型 futex 锁在无竞争时先用用户态原子操作完成，只有需要等待或唤醒时才进入内核。并非每次 mutex lock 都发生系统调用，也不是所有平台与所有 mutex 类型都使用同一路径。

### 6.3 有界队列的并发推演

容量为 K，队列维护 `0 <= size <= K`，并有 closed 标志。消费者需要等待“队列非空或关闭”，生产者需要等待“队列未满或关闭”。

```text
消费者持锁：while queue.empty() and not closed: wait(lock)
            if queue.empty() and closed: 结束
            取出一个元素，解锁，通知 not_full
生产者持锁：while queue.full() and not closed: wait(lock)
            if closed: 返回关闭结果
            放入一个元素，解锁，通知 not_empty
关闭者持锁设置 closed，随后唤醒所有生产者和消费者
```

wait 会按接口语义释放锁并等待，返回前重新获得锁。使用 while 有两个原因：可能虚假唤醒；即使通知真实，另一个消费者也可能先取走元素。通知不是可长期储存的业务状态，真正决定是否继续的是锁保护的谓词。

逐步看容量 1 的情形：P 放入 A；C1 与 C2 同时等待竞争；C1 先取得 A；C2 获锁发现队列已空，继续等待。若使用 if，C2 可能对空队列取值。关闭时只通知一个等待者也可能让剩余线程永远睡眠，因此退出策略要与等待谓词一起设计。

缓存行层面的伪共享与 data race 不同：两个线程修改不同变量，语义上可以正确，但变量落在同一缓存行，会反复触发缓存一致性流量。对齐与分离热点数据能改善部分场景，前提是测量确认而非盲目填充所有结构。

## 7. 死锁、活锁与优先级反转

死锁的经典必要条件是互斥、持有并等待、不可抢占、循环等待。线程 T1 持有 A 等 B，T2 持有 B 等 A，就是最小等待环。多个条件一起出现是危险信号；一般资源模型中不能把任意画出的环都不加条件地当作死锁证明，多实例资源还要检查实际可用数量。

预防通过破坏条件实现，例如所有路径按统一序号拿锁来避免环。避免策略则在每次资源分配前评估是否仍有安全完成顺序，银行家算法属于这一类，依赖对最大需求等信息的假设。检测与恢复允许先出现等待，再检查图或超时并选择受害者。

普通内存锁不像数据库事务那样自带 undo。强行让线程退出可能留下部分更新和被持有的锁；超时返回之前必须明确共享状态是否已经改变、怎样回滚或继续。try_lock 重试若双方总在同时释放再重试，还可能形成活锁。死锁是没有进展，活锁是不断动作却没有完成有效工作，饥饿则是某个参与者长期得不到服务。

优先级反转例子：低优先级 L 持锁，高优先级 H 等锁，中优先级 M 持续占 CPU，导致 L 无法运行并释放锁，H 间接受 M 阻碍。优先级继承让锁持有者暂时继承等待者的优先级，优先级上限协议则采用另一种约束设计；是否启用取决于锁类型、调度策略和平台，并非所有 mutex 默认提供。

服务代码应特别检查以下持锁边界：锁内调用外部回调、跨网络请求、同步刷盘、日志输出、等待另一个线程 join。这些操作可能增加尾延迟或引入间接锁环。缩短持锁范围前，先确认移出去的数据仍然具有有效生命周期与一致快照。

## 8. 虚拟内存、页表与 TLB

### 8.1 地址翻译链

虚拟地址分成虚页号 VPN 与页内偏移 offset。页表将 VPN 映射到物理页框号 PFN，并记录 present、可写、用户权限等属性；物理地址由 PFN 与不变的页内偏移组成。不同进程可将同一虚拟地址映射到不同物理页，也可把不同虚拟地址映射到共享物理页。

TLB 缓存地址翻译。TLB miss 后需要页表遍历，这可能只涉及已缓存的页表内存，不必访问磁盘。发现页面未驻留或权限不满足时，才可能触发缺页异常，由内核判断是按需分配、COW、文件装入还是非法访问。

```text
虚拟地址 -> TLB 命中 -> 权限检查 -> 访问物理页
        -> TLB 未命中 -> 页表遍历
                       -> 有效映射：填充 TLB 后访问
                       -> 缺页异常：内核修复或报告错误
```

真实处理器可能并行查询缓存、使用多级 TLB 与页表遍历缓存。教材“先查 TLB 再查内存”的 EAT 公式是指定模型，不应直接当成硬件延迟预测。

### 8.2 多级页表与大页

单级页表为整个虚拟空间准备表项，稀疏地址空间浪费大。多级页表把页表本身分页，仅为实际覆盖的区域分配低级表页。它节省稀疏映射空间，但 TLB miss 时可能增加遍历层数。

更大的页可以扩大 TLB 覆盖范围，降低部分页表开销，却可能增加内部碎片与分配、整理成本。透明大页的效果与访问模式、内存压力和内核配置有关；它不是对所有低延迟服务都应无条件开启或关闭的开关。

虚拟内存的价值不仅是“用磁盘扩充内存”。隔离、权限、共享映射、按需加载和稀疏布局同样重要。没有 swap 的系统仍使用虚拟内存；虚拟地址空间很大也不代表物理内存和提交额度无限。

## 9. 按需分配、COW 与分配器

### 9.1 分配成功与实际驻留

分配器从自己的 arena 或缓存中取得块，必要时再向系统申请地址空间。malloc/new 并非每次都调用 brk 或 mmap，free 也可能只把块还给分配器，不立即归还操作系统。因此“对象已释放”“分配器可复用”“RSS 下降”是三个不同观察点。

匿名映射可以先获得虚拟区域，访问时再分配物理页。Linux 的内存承诺和 overcommit 策略决定哪些申请会提前失败；随后触页仍可能遭遇内存压力或 OOM。代码要处理分配失败，但也要避免把一次申请成功解释成未来所有触页都必然成功。

### 9.2 COW 的实际过程

fork 后私有页可先由父子共享且限制写入。某一方写入时触发异常：内核检查映射，必要时分配新页并复制内容，修改写入者页表，再让指令重试。如果页已不再被其他映射共享，实现也可能恢复写权限而不必复制。

MAP_PRIVATE 文件映射的修改通常形成私有页，不写回原文件；MAP_SHARED 则允许通过共享映射传播修改，但并发同步与持久化仍需设计。对映射指针的普通写入不等于事务提交。

### 9.3 碎片与度量

内部碎片来自申请粒度与实际使用大小之间的差额，外部碎片来自空闲空间散布造成连续申请困难。用户态分配器与物理内存管理各有自己的粒度与碎片问题，二者不要混用。

RSS 表示驻留规模，但共享页在多个进程的 RSS 中可能重复计数；PSS 按共享比例分摊，更适合部分共享场景的比较。虚拟空间 VSZ 包含未实际驻留区域。诊断泄漏时，应结合对象数量、分配器统计、smaps、时间趋势与请求量，而不是只观察某一个时刻的 RSS。

## 10. 页面置换、工作集与内存压力

当需要新页但可用内存不足，系统必须选择回收对象。干净的文件页可丢弃并日后重读；脏文件页通常先写回；匿名页可能需要交换空间，也可能因缺乏回收余地导致分配失败或 OOM。

OPT 淘汰未来最晚使用的页，是已知未来访问序列时的理论比较基线。FIFO 淘汰最早装入的页，未考虑局部性，可能出现分配更多页框反而更多缺页的 Belady 异常。精确 LRU 淘汰最久未使用的页，利用时间局部性，但对每次访问维护全局顺序代价大。Clock 用访问位与循环指针近似选择牺牲页，在精度和维护开销之间折中。

Linux 的实际回收并非照抄教材精确 LRU；内核版本、匿名页与文件页、活跃性以及 MGLRU 等配置会改变机制。面试先说明算法原理，再说明“实际内核使用近似与多种启发”，比背一句“Linux 就是 LRU”更准确。

工作集是在某个时间窗口内频繁使用的页面集合。如果进程需要的活跃页总量长期超过可用内存，就可能频繁缺页与回收，CPU 大量时间花在等待换页，形成抖动。增加并发可能扩大工作集并使吞吐下降，而不是线性增加处理能力。

后端还可能同时有三层缓存：应用对象缓存、数据库缓冲池和内核页缓存。命中率与内存预算需要分层计算；同一份数据可能存在多份表示。限制缓存容量、减少无界队列、控制并发，往往比单纯增加 swap 更直接。swap 也不等于磁盘缓存，它主要解决部分匿名页的换出等需求。

## 11. 文件系统、路径与文件描述符

### 11.1 从名字到内容

路径解析从目录开始，逐段查找名字与对象。inode 保存类型、权限、大小、数据块或 extent 等元数据；目录提供名字到对象的关联；Linux dentry 是内核路径查找缓存中的重要对象，不等于磁盘上的目录项本体。

文件数据可采用连续分配、链式、索引式等教材模型；现代文件系统常使用 extent 描述一段连续块，减少描述开销并适配大文件。逻辑连续不保证所有物理块始终连续，碎片、稀疏文件和延迟分配都可能改变布局。

### 11.2 fd、打开对象与偏移

```text
进程 fd 表的整数 -> open file description -> 文件对象/inode
                 偏移、打开状态、访问方式
```

dup 产生新的描述符但可指向同一打开对象，因此共享偏移；分别 open 同一路径通常得到独立打开对象与独立偏移。FD_CLOEXEC 这类标志属于描述符，O_APPEND 等状态标志属于打开对象层次。说明“共享 fd”时要准确说出共享的是表、表项还是打开对象。

pread/pwrite 传入显式偏移，不改变共享打开对象的当前偏移，适合数据库按页定位。但它们不自动保证同一区域的并发写原子性；仍要使用上层锁、页协议和错误处理。短读短写也需要处理。

### 11.3 链接、删除与重命名

硬链接使多个名字关联同一 inode，通常不跨文件系统且目录硬链接受限制。软链接保存路径，可能跨文件系统，也可能成为悬空链接。

unlink 删除名字与对象的关联。只要仍有硬链接或打开引用等，内容可能继续存在；一个日志文件被删除但服务仍持有 fd，磁盘占用就可能迟迟不降。检查 `lsof +L1` 是定位这类问题的常见入口。

同一文件系统内的 rename 可提供规定范围内的名字切换原子性，但命名原子性不等于断电持久性，更不等于两个任意文件内容一起原子更新。跨文件系统 rename 通常会失败并返回 EXDEV，复制加删除则是不同的语义。

权限检查还涉及目录搜索权限、文件访问模式、UID/GID、ACL 与命名空间等。权限位只是保护的一部分，文件打开后持有 fd 与之后通过路径重新打开也可能观察到不同对象。

## 12. 页缓存、写回与崩溃持久性

### 12.1 普通读写路径

普通文件读通常先找页缓存，命中则复制到用户缓冲；未命中则请求存储设备装入页面。普通 write 往往先复制到页缓存并标脏，随后由后台或同步操作写回。write 成功首先说明本次调用接受了相应字节，不默认说明它们已抵达断电可保持的介质。

stdio、iostream 等用户态缓冲又在页缓存之前增加了一层。fflush 主要推动用户态缓冲交给内核，fsync 则要求同步文件数据及必要元数据，fdatasync 可省略部分与数据恢复无关的元数据同步。任何一步都应检查错误返回，存储设备、驱动与文件系统还需正确兑现持久化语义。

O_DIRECT 通常绕过或减少页缓存参与，可能有地址、长度和偏移对齐要求；它不自动等同于 O_SYNC 或一次数据库持久提交。mmap 共享写入可能需要 msync 等同步手段，且同样必须结合文件系统和调用契约；映射本身不是事务机制。

### 12.2 日志型文件系统与 WAL

文件系统日志主要保证其声明范围内的结构与更新一致性，不等于任意应用业务事务原子。日志记录元数据还是也包含数据、提交顺序怎样，都取决于文件系统与模式。

数据库 WAL 要求依赖某条日志的数据页持久化之前，相关日志先达到所需持久状态。对于允许未提交脏页写出的设计，恢复需要处理未完成事务；对于提交后数据页尚未全部落盘的设计，需要重做。文件系统日志不能替代数据库对事务、索引和业务状态的恢复规则。

### 12.3 原子替换配置文件的边界

在已存在目录内替换单个配置文件，可以按以下流程讨论，而不是直接覆盖原文件：

1. 在同目录创建临时文件，设置预期权限，循环写完全部内容并检查错误。
2. fsync 临时文件，确保所需内容与元数据同步成功。
3. 在同一文件系统内 rename 临时文件替换目标名字。
4. fsync 父目录，使目录项切换达到要求的崩溃持久性。

在第 3 步前失败，旧名字仍指向旧版本；第 3 步后正常运行中的查找看到新版本。若省略第 4 步，崩溃后名字切换的持久性可能没有保证。新创建的目录层级、跨目录操作、网络文件系统和特殊存储还需要额外分析，不能把这一流程当成所有场景的万能协议。

## 13. I/O 模型、epoll 与零拷贝

### 13.1 两个维度与两种通知

阻塞/非阻塞关注调用在缺乏进展条件时是否等待；同步/异步关注操作怎样发起、完成与交付结果。Reactor 接收“就绪”通知，应用仍要执行读写；Proactor 面向异步操作的完成结果。具体 AIO、io_uring 和 IOCP 需要按接口及操作类型说明，不宜只画五个名字就推断实现。

read 返回正数说明本次取得若干字节；对正长度 TCP 读取返回 0 表示对端发送方向结束且先前数据已读完；-1 时检查 errno。EINTR 通常需要按操作语义重试，EAGAIN/EWOULDBLOCK 表示当前非阻塞操作缺乏进展条件，而不是连接必然损坏。

### 13.2 select、poll、epoll 的区别

select 使用 fd 集合并可能改写它，常见实现受 FD_SETSIZE 约束；poll 使用条目数组，避免同样的位图索引限制，但每次仍提交并遍历集合。epoll 在内核维护关注集合，epoll_wait 返回就绪事件，从而减少大量空闲连接反复扫描的成本。

epoll 不是“整个算法 O(1)”：注册修改有成本，返回 k 个事件要处理 k 项，应用业务开销也仍存在。小规模、高活跃比例、连接频繁增删和跨平台需求都会影响选型。

LT 会在条件持续满足时继续提醒。ET 不保证只因缓冲仍有数据就再次提醒，事件也可能合并，所以通常使用非阻塞 fd 并处理到 EAGAIN。accept 队列也需按这个原则持续取连接，直到没有更多可取项。

### 13.3 完整事件处理闭环

读事件需要持续接收、解析完整帧并保留残余字节。写事件需要保存尚未发送的偏移；应用输出队列为空时通常取消 EPOLLOUT 关注，避免持续可写造成忙循环。若遇到错误或 EOF，还要注销、关闭并防止旧回调访问复用后的 fd。

为公平性设置每次处理配额时，若 ET 还没处理到 EAGAIN 就暂停，必须把连接留在应用级 ready queue 中轮转继续。否则一个大输入可能永久留下尾部。反过来，一口气无限读完一个极活跃连接，也可能饿死同一 loop 上的其他连接。

EPOLLONESHOT 会在通知后停用关注，需要按设计重新 arm；它有助于组织事件所有权，但不自动管理对象生命周期。跨线程任务通过队列与唤醒机制进入所属 loop，可以减少共享状态路径；回调里的同步数据库请求仍可能阻塞整个 loop。

### 13.4 零拷贝与背压

普通文件发送可简化为“设备到页缓存、页缓存到用户缓冲、用户缓冲到内核网络路径、设备发送”。sendfile 可省略先读入用户缓冲再写出的环节，splice 在支持的路径间移动数据，mmap 让应用直接访问映射页。实际拷贝次数受设备、协议、内核与用户态加工影响，DMA 也是数据搬运而非没有搬运。

客户端读取慢时，内核发送缓冲先拥满，随后应用输出队列堆积。背压应限制每连接字节、全局队列与生成任务，暂停上游、拒绝新工作或按业务策略关闭慢连接。仅设置高水位回调而不采取动作，并未真正限制内存。

## 14. 三组逐步计算与算法推演

### 14.1 RR 调度：区分响应与周转

假设单 CPU，三个任务都在 t=0 到达，按 A、B、C 入队；CPU 服务时长分别 5、3、1 ms，时间片 2 ms，无 I/O、无切换开销。

| 时间段 ms | 任务 | 本段结束后的剩余服务量 A/B/C |
|---|---|---|
| 0-2 | A | 3/3/1 |
| 2-4 | B | 3/1/1 |
| 4-5 | C | 3/1/0 |
| 5-7 | A | 1/1/0 |
| 7-8 | B | 1/0/0 |
| 8-9 | A | 0/0/0 |

完成时间 A=9、B=8、C=5，平均周转 `(9+8+5)/3 = 22/3 ms`；等待时间分别为 9-5=4、8-3=5、5-1=4，平均 `13/3 ms`。首次运行时间为 0、2、4，平均响应 `2 ms`。

对照 FCFS：A、B、C 的完成时间为 5、8、9，平均周转恰好仍为 `22/3 ms`，但平均响应为 `(0+5+8)/3 = 13/3 ms`。本例说明平均周转一样，不代表交互体验一样；也不证明 RR 对所有任务都优于 FCFS。若计入每次切换成本，需先说明是否计初次派发与最后退出。

### 14.2 页表与 TLB：统一地址、容量和时间单位

假设虚拟地址 32 位、页大小 4 KiB=`2^12` byte、每个页表项 4 byte，单级页表覆盖完整地址空间。

1. 页内偏移 12 位，虚页号 32-12=20 位，因此有 `2^20` 个表项。
2. 页表大小为 `2^20 * 4 = 2^22 byte = 4 MiB`，不是 4 MB 的十进制精确值。
3. 对虚拟地址 `0x12345ABC`，VPN=`0x12345`，offset=`0xABC`。假设该 VPN 对应 PFN=`0x234`，物理地址为 `0x234000 + 0xABC = 0x234ABC`。
4. 若改为两级 10/10/12 位分解，每张表页含 1024 项，每页 4 KiB。假设只映射从虚拟地址 0 开始的 8 MiB 连续区域，需要一个顶级页表和两个二级表，共 12 KiB；这只是页表存储，不包括数据页，也不是任意零散 8 MiB 映射的统一答案。

再假设 TLB 串行查询 10 ns、内存一次访问 100 ns、命中率 95%、单级页表、无缺页。命中路径需 110 ns，未命中路径需 210 ns，所以 `EAT=0.95*110+0.05*210=115 ns`。若增加多级遍历、页表缓存、并行查找或缺页概率，公式必须重新建立。

### 14.3 LRU 置换：维护顺序而非猜答案

假设 3 个页框，初始为空，访问序列 `1,2,3,1,4,2,5`。下表按最近使用到最久使用排列，命中也要调整顺序。

| 步骤 | 访问 | 结果 | 淘汰 | 最新 -> 最旧 |
|---|---|---|---|---|
| 1 | 1 | 缺页 | 无 | 1 |
| 2 | 2 | 缺页 | 无 | 2,1 |
| 3 | 3 | 缺页 | 无 | 3,2,1 |
| 4 | 1 | 命中 | 无 | 1,3,2 |
| 5 | 4 | 缺页 | 2 | 4,1,3 |
| 6 | 2 | 缺页 | 3 | 2,4,1 |
| 7 | 5 | 缺页 | 1 | 5,2,4 |

共 6 次缺页，缺页率 `6/7`。这是引用序列上的逻辑缺页计数，不能直接乘固定磁盘时间推算真实程序耗时，因为页面可能来自缓存、匿名零页或其他路径。自行用 FIFO 重做同一序列，比较第 4 步命中是否改变淘汰顺序，再理解算法差异。

## 15. 项目映射与可复现实验

### 15.1 连接 RMDB 与后端经历

| 理论 | 可以沿项目阅读的链路 | 尚需提交的证据 |
|---|---|---|
| 线程与 fd | RMDB 监听、accept、连接处理线程、退出 | 入口函数、所有权图、异常清理路径 |
| 虚拟页与数据库页 | 数据库 page/frame、缓冲池、DiskManager | 数据库页不是操作系统页表的说明 |
| pin 与替换 | fetch、pin/unpin、dirty、替换器 | 全部页被 pin 时行为和边界测试 |
| 锁与恢复 | 执行器、事务锁、日志与刷页 | 锁覆盖范围、WAL 顺序、崩溃结果 |
| 服务排队 | 事件循环、工作线程、连接池与下游 | 时间线、队列等待与资源指标 |

RMDB 学习材料明确当前有教学实现边界：部分索引是简化有序容器，恢复也不是完整 ARIES。本文的调度、文件系统与生产化 I/O 方案是解释和实验方向，不是把所有理论功能归入个人实现。答辩模板与已有边界见 [项目答辩与证据手册](../07-项目与工程/项目答辩与证据手册.md#rmdb-数据库内核)。

数据库缓冲池页锁保护内存数据结构，事务锁保护逻辑并发语义，pin 防止 frame 被替换；它们不是同一把锁。把三者混成“加锁所以线程安全”，会漏掉淘汰、访问生命周期和事务一致性的不同约束。

### 15.2 实验环境与记录格式

以下实验在独立练习目录执行，默认 Linux/WSL2，需编译器、CMake 和对应观察工具；WSL2 的虚拟化、宿主缓存和文件挂载路径会影响性能。记录内核、CPU 配额、文件系统、编译参数、输入和输出。先有功能正确的基线，再加观测，最后比较性能。

```bash
uname -r
getconf PAGESIZE
getconf _NPROCESSORS_ONLN
ps -eo pid,ppid,stat,comm
ss -s
```

PID 应替换为实际练习进程；以下为诊断方案，不是已执行记录：

```bash
pidstat -t -p PID 1 10
pidstat -r -p PID 1 10
pidstat -w -p PID 1 10
ls -l /proc/PID/fd
grep -E 'Rss:|Pss:|Private_Dirty:|Shared_Clean:' /proc/PID/smaps
```

### 15.3 五个有预期与反证的实验

**实验 A：fork 与 COW。**申请并触页一段匿名内存，再 fork；一组子进程只读，另一组逐页写。观察父子读值是否独立、minor fault、PSS 与 Private_Dirty 的差异。预期是写路径增加私有页成本，不应把父子 RSS 相加作为唯一结论。固定页大小与触页顺序，结束后由父进程 wait 回收。

**实验 B：有界队列与退出。**容量设为 1，使用多个生产者与消费者，给每条消息唯一 ID；验证每条被消费一次、size 始终在边界内、关闭后所有线程可结束。加入虚假唤醒式通知、空队列关闭、满队列关闭情形。C++ 实现可单独用 TSan 构建测试，但 TSan 与 ASan 通常分开运行，未报错不等于并发正确性证明。

**实验 C：LT/ET 与慢客户端。**发送超过单次读取缓冲的消息，强制拆分头和正文，客户端限速读取；记录每连接输入/输出字节、EAGAIN 和 ready queue。故意限制每轮配额后，检查残余数据是否继续处理、其他连接是否获得服务、关闭后 fd 数是否回落。通过后才讨论事件循环吞吐。

**实验 D：持久化路径。**对练习文件比较普通写、文件 fsync 和“临时文件+rename+目录 fsync”的 syscall 序列。进程被终止只能模拟应用崩溃，内核缓存仍可能继续写回；它不等同于断电实验。存储级故障应在可丢弃虚拟机或专用测试介质中另行设计，本文不声称已验证断电持久性。

**实验 E：页缓存与发送路径。**对相同测试文件比较 read/write 与 sendfile，固定文件大小、目标速率和缓存条件，记录 syscall 次数、CPU、吞吐与延迟。不在共享机器上随意清空全局页缓存；可使用独立环境并明确冷/热状态的不确定性。若启用 TLS 或压缩，应另列测试组，避免把不同数据路径直接对比。

结果记录至少包含“假设、操作、预期、实际、反证、限制”。性能结论保留多轮样本与分位数，失败测试保存最小输入及日志。通过本页计算与链接检查，不等于这些服务实验已经运行。

## 16. 误区、模拟面试与参考

### 16.1 常见误区校正

| 常见说法 | 更精确的回答 |
|---|---|
| 系统调用就是进程切换 | 特权级切换与调度切换是两件事 |
| 线程栈被其他线程硬件隔离 | 同一地址空间内仍可通过指针访问 |
| 协程天然让阻塞 I/O 不阻塞 | 取决于运行时如何调度与接入 I/O |
| TLB miss 就访问磁盘 | 先进行地址翻译，缺页也可能无需设备 I/O |
| free 后 RSS 必然下降 | 分配器可保留空闲块供复用 |
| swap 就是虚拟内存 | 虚拟内存还提供隔离、映射和权限 |
| mmap 或 O_DIRECT 等于持久化 | 映射、缓存路径与同步持久性分别讨论 |
| rename 原子等于断电后必保留 | 名字切换原子性与崩溃持久性分开 |
| epoll 返回就绪意味着完整消息到达 | TCP 是字节流，应用需维护 framing |
| ET 配额用尽就等下一次通知 | 未到 EAGAIN 时需保存应用级就绪状态 |
| 加 mutex 就解决所有生命周期问题 | 锁、对象所有权和退出协议都要成立 |
| P99 高但 CPU 低就加线程 | 先排查锁、I/O、连接池、配额和下游 |

### 16.2 一轮 35 分钟模拟面试

1. 5 分钟：用一次 RMDB 请求串起进程、线程、内核与 I/O。追问“数据库页和虚拟内存页有什么关系”。
2. 6 分钟：画 fork 后私有页与打开文件对象，解释子进程写内存、读文件、exec 和退出分别改变什么。
3. 6 分钟：完成本页 RR 和页表题，口述假设变化时如何重算，而非只报最终数字。
4. 6 分钟：解释有界队列、虚假唤醒与关闭，给出死锁和优先级反转的不同例子。
5. 6 分钟：设计 ET 慢客户端处理，说明 EAGAIN、剩余偏移、处理配额与 fd 生命周期。
6. 6 分钟：面对“提交返回后断电丢数据”的假设，区分业务提交、用户缓存、页缓存、日志同步与存储保证。
