### Q1 `const` 的顶层和底层分别约束什么？

**口述答案：** 顶层 `const` 限定对象自身，底层 `const` 限定通过指针或引用访问的对象。`int* const p` 中指针自身固定；`const int* p` 中经由 `p` 观察到的整数只读，但指针可改指向。两者可同时存在。

**机制与边界：** 按值参数的顶层 `const` 不区分函数签名，例如 `f(int)` 与 `f(const int)` 是同一函数。按值 `auto` 推导通常丢弃顶层 `const` 和引用，`auto&` 可保留被引用对象的常量性。`const` 不自动提供跨线程同步，也不等于深度不可变：常量对象内的指针仍可能指向可变外部对象。

**反例 / 验证：** 对原本非 `const` 的对象，移除访问路径上的 `const` 后修改可以合法；对原本就是 `const` 的对象强行写入产生未定义行为。分别声明 `const int* a` 与 `int* const b`，用编译器验证修改 `*a`、修改 `b` 被拒绝，而修改 `a`、修改 `*b` 可被接受。

### Q2 `constexpr`、`consteval`、`constinit` 有什么区别？

**口述答案：** `constexpr` 变量要求常量表达式初始化；`constexpr` 函数在满足常量求值要求的上下文中进行编译期求值，也可运行期调用。`consteval` 是 C++20 的立即函数，通常的实际调用必须产生常量表达式。`constinit` 是 C++20 对静态或线程存储期变量的初始化约束，保证静态初始化，变量此后仍可改变。

**机制与边界：** `constexpr` 函数声明并不保证每次调用都发生在编译期。`constexpr` 变量是 `const`，但 `const` 变量未必适用于常量表达式。`constinit` 既不是只读承诺，也不让普通运行期读取成为常量表达式；它用于阻止意外的动态初始化，不解决对象间的所有生命周期依赖。

**反例 / 验证：** 在 C++17 中定义 `constexpr int square(int x) { return x * x; }`，`static_assert(square(3) == 9);` 是编译期检查，传入用户输入则可在运行期执行。C++20 的 `constinit int count = 0;` 之后 `++count` 合法；把 `consteval` 函数传入普通运行期整数，编译器应诊断错误。还要考虑整数乘法的溢出边界。

### Q3 数组传参为什么会退化成指针？如何保留长度？

**口述答案：** 函数形参写成 `void f(int a[10])` 时，参数类型按语言规则调整为 `int*`，`10` 不形成调用时长度检查。这与普通表达式中的数组到指针转换相关，但属于参数声明调整规则。数组引用或持有长度的类型可保留边界。

**机制与边界：** C++17 可用 `template<std::size_t N> void f(int (&a)[N])` 或 `std::array<int, N>&`。动态长度可以传入 `pointer + size`，或使用容器引用。C++20 的 `std::span<T>` 是非拥有视图，可表达长度，但寿命仍依赖原存储。二维参数 `int a[][4]` 调整为指向四元素数组的指针，而非 `int**`。

**反例 / 验证：** 在调用点对 `int a[10]` 使用 `sizeof(a)` 得到整个数组字节数；在 `f(int a[10])` 内得到指针大小。将 `int[3]` 传给接受 `int (&)[10]` 的函数，编译器会拒绝。不要用 `sizeof(pointer) / sizeof(pointer[0])` 推导元素个数。

<a id="q4"></a>
### Q4 `sizeof` 作用于数组、指针、空类和多态对象时如何判断？

**口述答案：** `sizeof` 返回对象表示占用的字节数，类型为 `std::size_t`。数组结果含全部元素；指针大小取决于平台和指针类别；完整空类对象大小至少为 1；多态类一般含实现多态所需的额外数据，但具体布局由 ABI 决定。

**机制与边界：** 普通 `sizeof(expr)` 不求值，`sizeof(i++)` 不递增 `i`。类大小包含成员与填充，并满足对齐要求。`sizeof(Base)` 或 `sizeof(*base_ptr)` 由静态类型决定，和该指针实际指向的派生对象不同。空基类优化可能使空基类子对象不额外占空间；这不等同于完整空对象大小为 0。`sizeof(char)` 恒为 1，1 字节的位数由 `CHAR_BIT` 给出。

**反例 / 验证：** “64 位环境下所有指针、`long` 都是 8 字节”是错误概括，Windows 常见 LLP64 与 Linux 常见 LP64 对 `long` 不同。打印 `sizeof` 和 `alignof` 并记录编译器、目标架构、ABI；把输出作为特定环境的观察，不提升成语言保证。

<a id="q5"></a>
### Q5 未定义行为、实现定义行为和未指定行为如何区分？

**口述答案：** 未定义行为发生后，标准不对程序行为作要求；实现定义行为由实现选择且须文档化；未指定行为允许多种合法结果，实现不必逐次说明选了哪种。另有程序不合式，通常应由编译器诊断，别把这几类混为一谈。

**机制与边界：** 有符号整数溢出、越界解引用、data race 是未定义行为。普通 `char` 的有无符号性由实现定义。两个普通函数实参哪个先求值通常未指定。无符号整数运算按模运算是有定义的。C++17 中函数实参之间是互不交错的顺序不确定求值，和 C++14 的若干规则存在差异。

**反例 / 验证：** 在 C++17 中，`f(i++, i++)` 的两次递增彼此有先后但先后次序未指定；它与仍含未排序冲突的 `i++ + i++` 不同。“Debug 一直正常”不证明没有未定义行为。对合法边界写静态检查与测试；对疑似 UB 用警告、UBSan 和标准规则交叉分析，不通过观察一次输出定义语义。

### Q6 什么是对象生命周期？何时会产生悬空指针 / 引用？

**口述答案：** 存储存在不等于对象还活着。对象生命周期一般在取得满足大小、对齐要求的存储并完成初始化后开始；类对象析构函数调用开始时其生命周期结束，释放或复用存储也有相应规则。指针还保留一个地址，但目标对象已经销毁或迁移时，再按活对象访问会产生问题。

**机制与边界：** 返回局部变量引用、容器重分配后的旧指针、指向临时字符串的 `string_view`、回调持有失效的 `this` 都是常见来源。临时对象的生命周期延长有严格适用场景，不沿着第二个引用再次延长；作为返回语句中引用目标的临时量不会因此活到调用者使用阶段。析构期间有专门的成员访问与虚调用规则，见 Q13。

**反例 / 验证：** 片段 `std::string_view view = std::string("abc");` 在该完整表达式结束后悬空。对照 `std::string owner = "abc"; std::string_view view = owner;`，仍要追问 `owner` 后续是否销毁或使缓冲区失效。用 ASan 辅助检查 use-after-free / use-after-scope，并在设计中明确“谁拥有、谁观察、谁保证寿命”。

### Q7 `malloc/free` 与 `new/delete` 的职责差异？

**口述答案：** `malloc` 申请原始存储，`free` 释放存储，不负责 C++ 类的构造析构；`new` 表达式申请存储并初始化对象，`delete` 表达式先析构再释放。`new[]` / `delete[]` 匹配数组语义。标准普通分配失败时 `new` 抛 `std::bad_alloc`，`malloc` 返回空指针。

**机制与边界：** 区分 `new` 表达式与 `operator new`：后者是分配函数，单独调用通常只取得存储。placement new 在已有合适存储上构造对象，不自动拥有该存储。标准 nothrow 分配形式可返回空指针，但初始化阶段的构造函数仍可能抛异常。C++17 有针对过度对齐类型的分配支持，原始内存管理也应满足相应对齐。

**反例 / 验证：** 把 `new Widget` 的结果交给 `free`，或把 `new[]` 的结果交给标量 `delete`，都是错误的分配 / 释放配对。用构造、析构计数器验证成功构造与异常路径：当 `new` 表达式中的构造抛出，已构造成员被销毁，适用的匹配释放函数被调用。工程中优先让容器和智能指针拥有资源。

### Q8 构造函数初始化列表和构造函数体的执行顺序？

**口述答案：** 构造顺序由类结构决定，而非初始化列表书写顺序：最派生类先初始化虚基类，再按声明顺序初始化直接基类，再按成员声明顺序初始化非静态成员，最后执行构造函数体。析构按相反次序处理已构造的子对象。

**机制与边界：** 在函数体里赋值不是初始化，会先发生成员默认初始化或默认成员初始化。引用与需初始化的 `const` 成员应在初始化阶段处理。若构造函数抛出，已完成构造的基类、成员会析构，该完整对象的析构函数不执行。资源成员应使用 RAII，而非在函数体末尾才补救。

**反例 / 验证：** 片段 `struct S { int a; int b; S() : b(1), a(b) {} };` 实际先初始化 `a`，读到尚未初始化的 `b`。修正声明顺序或令 `a` 的初始化不依赖后声明成员。启用 `-Wreorder`，用基类和成员的构造 / 析构日志验证异常发生前后的顺序。

### Q9 Rule of 0/3/5 分别解决什么问题？

**口述答案：** Rule of 0 优先用成员类型表达资源所有权，让编译器生成特殊成员函数。Rule of 3 提醒资源类同时考虑析构、拷贝构造、拷贝赋值。C++11 后 Rule of 5 加入移动构造和移动赋值。它们是设计原则，不要求五个函数都手写；删除不支持的操作也是明确契约。

**机制与边界：** 裸指针拥有资源时，默认拷贝通常只复制地址，可能双重释放。用户声明析构或拷贝等特殊成员会影响隐式移动生成。只拥有 `unique_ptr` 的包装类型往往可默认析构和移动，拷贝自然受限。拷贝赋值要考虑自赋值与异常保证，移动赋值还要先处理目标已有资源。`noexcept` 只能在真实满足时承诺。

**反例 / 验证：** 一个拥有 `int*` 的类仅手写析构，却让默认拷贝存在，复制后两个对象析构会释放同一地址。测试独立拷贝、移动构造、移动赋值覆盖非空目标、自赋值、分配失败；明确选择深拷贝还是仅移动，而不是为了凑“五个”提供错误语义。

<a id="q10"></a>
### Q10 `std::move` 做了什么？移动后对象必须满足什么保证？

**口述答案：** `std::move(x)` 本质上把表达式转换成适合参与移动重载选择的将亡值，它自己不转移资源，也不结束 `x` 的生命周期。真正发生拷贝还是移动由后续构造、赋值或函数重载决定。

**机制与边界：** 标准库类型在移动后通常处于有效但未指定状态，另有明确规定的类型遵从其专门契约，例如成功移动后源 `unique_ptr` 为空。可以销毁、重新赋值；调用有前置条件的方法应先检查条件。用户定义类型的移动后契约由实现和接口决定，别把标准库保证自动套给任意类。`const T` 经 `std::move` 得到 `const T&&`，常见 `T(T&&)` 不接受它，可能回退到拷贝。

**反例 / 验证：** 片段 `const std::string a = "x"; std::string b = std::move(a);` 通常选择拷贝构造。用计数类记录复制 / 移动重载；单独求值 `std::move(a)` 应没有资源转移日志。不要断言所有移动后的 `string`、`vector` 都为空，也不要继续依赖它们移动前的值。

### Q11 完美转发中的转发引用和引用折叠是什么？

**口述答案：** 当 `T` 是该函数模板待推导的、无 cv 限定的类型参数时，形参 `T&&` 可成为转发引用：接收左值时 `T` 推导为左值引用，接收右值时为普通类型。引用折叠中，只要参与组合的一方是 `&`，结果就是 `&`；只有 `&&` 与 `&&` 合成 `&&`。

**机制与边界：** 命名变量表达式是左值，即使变量的声明类型是右值引用，因此在包装函数中使用 `std::forward<T>(x)` 根据推导结果恢复调用者的值类别。`const T&&` 不是转发引用；类模板已有参数的成员函数 `void f(T&&)` 不因这个写法自动成为转发引用。完美转发并不延长被转发对象的寿命。

**反例 / 验证：** 片段 `template<class T> void relay(T&& x) { sink(std::forward<T>(x)); }`，用 `sink(X&)` 和 `sink(X&&)` 观察两种调用。换成 `sink(x)` 都走左值；换成 `sink(std::move(x))` 会把调用者的左值也变为可移动表达式。花括号初始化列表、重载函数名和位域等场景有推导或绑定限制。

### Q12 RVO/NRVO 何时发生？为什么返回局部对象通常不应手写 `move`？

**口述答案：** C++17 中 `return T{};` 这类同类型纯右值可直接构造最终结果对象，通常称为保证的拷贝消除。返回命名局部变量 `return local;` 的 NRVO 仍是允许而非强制优化。符合条件且 NRVO 未发生时，返回值规则通常会尝试使用移动。

**机制与边界：** NRVO 要求返回表达式满足规定形态，例如合适的非 volatile 自动存储期局部对象；参数不适用 NRVO。手写 `return std::move(local);` 将命名局部对象表达式变成转换表达式，通常失去 NRVO 资格，增加一次移动机会。不是所有返回都适用同类型纯右值规则，基类子对象、类型转换等要具体分析。

**反例 / 验证：** 定义删除拷贝与移动构造的 `T`，C++17 的 `T make() { return T{}; }` 在其他必要条件满足时仍可合法；`T make() { T t; return t; }` 则依赖相关构造函数可用性。用计数类比较三种返回写法，`-fno-elide-constructors` 可影响可选消除，但不会撤销 C++17 的保证规则。不要在计数结果中漏掉临时对象析构。

### Q13 虚函数表是怎样支持多态的？哪些细节不是标准保证？

**口述答案：** 通过基类指针或引用调用虚函数时，通常分派到对象动态类型的最终覆盖函数。常见实现为对象中保存虚表指针，再通过虚表条目间接调用；标准规定可观察的分派行为，不规定必须有多少虚表、指针放在哪里或函数表具体布局。

**机制与边界：** 多继承常涉及多个基类子对象、`this` 调整和跳板函数，虚继承还涉及共享虚基类的定位。优化器在证明目标后可以去虚化。构造和析构过程中，虚调用分派受当前正在构造 / 析构的类层级限制，不会像完整派生对象那样分派到尚未构造或已析构的更派生部分。显式限定 `Base::f()` 也绕过通常的虚分派。

**反例 / 验证：** 在基类构造函数里调用虚 `f()`，即使最终创建的是派生类，也不调用派生覆盖版本。直接或间接在构造 / 析构期间对当前对象作相关纯虚函数虚调用会产生未定义行为。用非纯虚的小例子记录调用次序，再看编译器类布局报告或反汇编；不要通过任意地址强读“第一个指针”推定跨平台标准布局。

<a id="q14"></a>
### Q14 为什么基类析构函数常需要 `virtual`？

**口述答案：** 若设计允许经由基类指针删除派生对象，基类析构函数应为虚函数，保证执行派生析构再执行基类析构。在 C++17 的普通 `delete base_ptr` 场景中，动态类型不同而基类析构非虚会产生未定义行为，而不只是“可能少释放一点内存”。

**机制与边界：** 常用设计是“public virtual 析构”以支持多态销毁，或“protected non-virtual 析构”以禁止外部通过基类删除。纯虚析构函数仍需提供定义，因为派生类析构链会调用基类析构。`unique_ptr<Base>` 默认删除器最终按 `Base*` 删除，因此同样要求正确的虚析构策略。

**反例 / 验证：** `shared_ptr<Base>` 从 `make_shared<Derived>()` 转换而来时，控制块保留正确的销毁信息；这不是任意 `Base*` 都适合交给智能指针的证明。先把 `new Derived` 存到非虚析构的 `Base*`，再用该指针构造 `shared_ptr<Base>`，删除类型信息可能已丢失。为多态基类启用 `-Wnon-virtual-dtor` / `-Wdelete-non-virtual-dtor`，结合设计检查。

<a id="q15"></a>
### Q15 对象切片是什么？如何避免？

**口述答案：** 把派生对象按值复制或赋值到基类对象时，只保留对应基类部分，派生类特有状态被切掉，目标对象的动态类型就是基类。最常见来源是基类按值形参、返回值和 `vector<Base>`。

**机制与边界：** 多态接口一般用 `Base&`、`const Base&` 或指针表达观察，用 `unique_ptr<Base>` 等表达所有权。需要多态复制时，应设计返回拥有指针的虚 `clone()`，而不是依赖基类复制构造自动复制完整动态类型。对一个既存派生对象经基类引用赋值只修改其基类子对象，还可能破坏派生对象的不变量。

**反例 / 验证：** 片段 `void inspect(Base b); Derived d; inspect(d);` 中 `b` 的虚函数按基类对象处理；改成 `const Base&` 才保留动态分派。通过类型标识和虚函数输出验证。并非所有基类值语义都错误，例如刻意提取公共记录字段可以合理；关键在接口是否承诺保留多态行为。

<a id="q16"></a>
### Q16 `dynamic_cast`、`static_cast`、`reinterpret_cast` 的风险边界？

**口述答案：** `static_cast` 做编译期检查的显式转换，但向下转换一般不验证实际动态类型。`dynamic_cast` 对合适的多态对象执行运行期类型检查，失败的指针转换返回空指针，失败的引用转换抛 `std::bad_cast`。`reinterpret_cast` 执行低层表示 / 指针转换，不保证目标可被当成新类型合法访问。

**机制与边界：** 向上转换通常使用隐式转换即可；某些虚基类相关向下 `static_cast` 本身不合式。`dynamic_cast` 的运行期下转 / 侧转要求多态源类型以及可访问、无歧义等条件。强制指针转换不自动满足对齐、对象生命周期、严格别名规则。C 风格转换可能组合多种能力，使风险更难审计。

**反例 / 验证：** `reinterpret_cast<float*>(&integer)` 后解引用，不因两者同为 4 字节就合法。C++17 可在满足条件时用 `memcpy` 复制对象表示；C++20 `std::bit_cast` 要求等大小且源、目标平凡可复制，仍需考虑目标位模式语义。对多态转换分别测试成功指针、空指针失败和引用异常，并在设计中优先消除不必要的向下转换。

<a id="q17"></a>
### Q17 `unique_ptr`、`shared_ptr`、`weak_ptr` 的所有权模型？

**口述答案：** `unique_ptr` 表达独占所有权，可移动、通常不可拷贝；`shared_ptr` 共享控制块中的所有权，最后一个强引用消失时销毁被管理对象；`weak_ptr` 观察控制块而不延长对象的拥有寿命，通过 `lock()` 尝试取得有效的强引用。

**机制与边界：** `shared_ptr` 的控制块计数具有相应线程安全保障：多个线程操作共享控制块的不同 `shared_ptr` 实例是一个层面；同时读写同一个 `shared_ptr` 变量是另一层面，需锁或专门原子操作。C++17 可用 `atomic_load` / `atomic_store` 等 shared_ptr 专用自由函数；`atomic<shared_ptr<T>>` 是 C++20。被指向的 `T` 的字段完全是第三层，仍须自身同步。原子智能指针也不保证无锁。

**反例 / 验证：** 两个线程各自复制一份 `shared_ptr<Counter>` 后同时对普通 `int` 执行 `++p->value`，仍可能 data race。`if (!w.expired()) use(w.lock())` 也有检查与使用的时间差，正确模式是一次 `if (auto p = w.lock())` 后在强引用寿命内使用。用 TSan 检查对象字段访问，而非只检查引用计数。

<a id="q18"></a>
### Q18 `make_shared` 与单独 `new` 的内存布局和异常安全取舍？

**口述答案：** `make_shared<T>(...)` 通常把对象和控制块合并分配，减少分配次数和局部性开销；`shared_ptr<T>(new T(...))` 通常分别分配对象与控制块。合并分配不是应随意依赖的 ABI 布局契约，具体实现需测量。

**机制与边界：** 最后一个强引用消失就会析构对象；若仍有 `weak_ptr`，控制块继续存在。合并分配可能使包含大对象的整块分配保留到弱引用也清零，尽管对象析构函数已释放它拥有的其他资源。`make_shared` 不接受自定义删除器，`allocate_shared` 可控制分配器。C++17 中数组形式的 `make_shared<T[]>` 尚未进入标准，C++20 才支持相应重载。

**反例 / 验证：** “使用显式 `new` 构造 shared_ptr 一定异常不安全”过度概括：若控制块分配失败，构造函数会处理传入对象的删除；C++17 还强化了函数实参求值次序，旧标准中常讲的参数交错泄漏例子要注明版本。更常见的危险是让裸指针在接管前跨越可能抛异常的操作。用计数分配器与析构日志区分“对象销毁”和“合并存储回收”。

<a id="q19"></a>
### Q19 如何解决 `shared_ptr` 循环引用？

**口述答案：** 两个对象或更长的环通过强引用互相拥有，外部引用清零后环内强计数仍非零，对象留存。解决方式是先定义所有权图，把观察、回指关系改为 `weak_ptr` 或由明确外部所有者保证的非拥有引用，而不是任意把一个字段机械换成弱指针。

**机制与边界：** 树结构常让父节点拥有子节点、子节点弱引用父节点。回调也会形成环：对象拥有任务，任务闭包捕获 `shared_ptr` 指回对象。可捕获 `weak_ptr` 并在执行时 `lock()`；业务必须接受对象已销毁时任务退出。`enable_shared_from_this` 帮助获取同一控制块的强引用，不自动打破环，应在对象已由 shared_ptr 正确管理后使用。

**反例 / 验证：** 对同一个裸指针分别构造两个独立 `shared_ptr` 会创建不同控制块，最终可能双重删除，这与循环引用不是同一问题。画出每条强 / 弱所有权边，释放外部所有者后检查析构计数与弱引用是否过期。不要用某次 `use_count()` 的数值代替并发下的生命周期证明。

<a id="q20"></a>
### Q20 `vector` 扩容的触发、复杂度和失效规则？

**口述答案：** `vector` 的元素连续存储，`size` 是已构造元素数量，`capacity` 是已分配存储可容纳的元素数量。插入后所需容量超过现有容量时需重分配：申请新存储、构造已有及新增元素、销毁旧元素并释放旧存储。尾部插入摊还 O(1)，单次重分配通常 O(n)。标准不规定统一的 1.5 倍或 2 倍增长策略。

**机制与边界：** 重分配使原全部迭代器、指针、引用以及旧 `end()` 失效。未重分配时，尾插不影响已有元素的引用与迭代器，但旧 `end()` 仍失效；中间插入则使插入点及之后的引用、指针、迭代器失效。扩容常在移动可能抛异常且可复制时选择复制，以支持强异常保证；若元素仅可移动且移动可能抛异常，某些操作在异常后的保证会减弱，具体按该操作要求判断。

**反例 / 验证：** `reserve` 不让所有后续操作都保持迭代器有效，中间插入仍会移动元素。先记录 `data()`、`size()`、`capacity()` 和元素构造日志，再触发边界尾插；旧指针失效后只记录先前保存的地址信息，别解引用它证明“数据还在”。使用库调试迭代器可检测部分失效访问，性能测量时关闭调试模式。

<a id="q21"></a>
### Q21 `reserve` 与 `resize` 的区别？

**口述答案：** `reserve(n)` 请求容量至少为 `n`，不改变元素数量；仅在 `n` 超过当前容量时重分配。`resize(n)` 调整实际元素数量：增加时构造元素，减少时销毁尾部元素。缩小 `size` 不要求释放相应容量。

**机制与边界：** 对采用常规分配器的 `vector<int>`，`resize(n)` 增加的整数为零；用户类型需满足相应构造要求，也可以用带值版本。`reserve` 后，`[size(), capacity())` 仍不是可以用 `operator[]` 访问的元素区间。`shrink_to_fit()` 是非强制的缩容请求，若导致重分配则原引用等失效。每次尾插前都 `reserve(size()+1)` 可能破坏几何增长，造成近似 O(n²) 的搬移量。

**反例 / 验证：** 片段 `std::vector<int> v; v.reserve(100); v[0] = 1;` 违反元素访问边界，即使内存似乎足够。用 `v.push_back(1)` 或先 `v.resize(1)`。检查 `size/capacity` 并使用 `at(0)` 观察异常；ASan 未必捕获所有“已分配但尚非有效元素”的访问，容器边界注解与库实现也会影响检测。

<a id="q22"></a>
### Q22 `unordered_map` 的桶、负载因子、rehash 和最坏复杂度？

**口述答案：** 哈希表按哈希结果把键组织到桶中，桶冲突要进一步比较键。负载因子为 `size()/bucket_count()`。查找、插入、删除平均可近似 O(1)，严重碰撞时单次可退化到 O(n)。rehash 重新组织桶，平均复杂度线性，标准复杂度边界还允许更差情形。

**机制与边界：** 插入可能触发 rehash；`rehash(b)` 面向桶数量，`reserve(n)` 面向预计元素数量，并结合最大负载因子计算需求。rehash 使迭代器失效，但不使未删除元素的引用和指针失效。哈希和相等判定必须一致：若两键相等，哈希值必须相同；哈希相同不代表相等。不要依赖遍历顺序，也不要修改会改变键哈希 / 相等语义的外部状态。

**反例 / 验证：** 保存某元素地址和迭代器，调用 `rehash` 后可通过保存的有效元素指针读取，但应重新获取迭代器。用“所有键哈希都为 0”的测试哈希器观察查找退化，记录桶分布和负载因子。读取不存在的键时 `operator[]` 会插入默认值，可能改变表并触发 rehash；纯查询应考虑 `find` 或 `at`。

<a id="q23"></a>
### Q23 map/set 为什么常用红黑树？何时选择哈希表？

**口述答案：** `map/set` 提供按比较关系组织的有序访问，查找和插入等具有对数复杂度要求。红黑树是常见实现，靠受控树高支持更新和查询；标准没有要求必须用红黑树。需要范围查询、前驱后继、有序遍历或稳定对数边界时选有序容器；以精确键查询为主且哈希质量好时可考虑哈希表。

**机制与边界：** 有序容器使用严格弱序，键等价由 `!comp(a,b) && !comp(b,a)` 判定，不一定等于 `operator==`。哈希容器使用 `Hash` 和 `KeyEqual`。节点分配、缓存局部性、键长和比较 / 哈希成本都影响真实速度。小规模或批量构建后只读的集合，可比较排序数组加二分，别仅按大 O 选容器。

**反例 / 验证：** 将 `<=` 用作有序容器比较器违反严格弱序；浮点 NaN 也需要审慎定义键语义。准备相同键分布、命中率和预留策略，对比 p50/p99 查询时延、内存占用与更新成本；“哈希表任何时候都更快”没有这样的普遍保证。

<a id="q24"></a>
### Q24 `emplace_back` 是否总比 `push_back` 好？

**口述答案：** `emplace_back(args...)` 把参数转发给尾部元素的构造函数，可能省去显式构造临时对象再移动的步骤；`push_back(value)` 更直观地表达放入一个已有值。已经有 `T` 对象时，`emplace_back(std::move(t))` 通常仍然调用移动构造，并不天然比 `push_back(std::move(t))` 少一次移动。

**机制与边界：** emplace 可匹配 explicit 构造函数，重载选择与列表初始化的语义也可能不同，应先确认生成的对象正确。vector 扩容时原有元素仍需迁移，emplace 没有取消这项成本。传入资源表达式时，要在调用前用 RAII 包装好；例如先产生裸拥有指针，容器又在构造元素前因分配失败抛出，可能留下无人拥有的资源。

**反例 / 验证：** `vector<unique_ptr<T>>` 优先接收 `make_unique<T>()` 的结果，而不是直接 `emplace_back(new T)`。对比构造器计数时分别测“已有对象插入”“参数就地构造”“触发扩容”，不要把三种实验混为同一优化结论。C++17 的 `emplace_back` 返回新元素引用，此返回能力也要与更早标准区分。

<a id="q25"></a>
### Q25 erase 一个容器元素后哪些迭代器、指针、引用仍有效？

**口述答案：** 先指出容器、操作位置、是否重分配，再谈有效性。删除元素本身的引用 / 指针都失效；剩余元素是否受影响取决于该容器的存储和标准规则。`end()` 也属于需要单独判断的迭代器，不是永远有效的固定标记。

**机制与边界：** 下表针对标准容器的常规 `erase` 操作，不推导出任意其他修改操作也有相同规则。

| 容器 | 删除后的有效性 |
| --- | --- |
| `vector` | 擦除点及之后的迭代器、指针、引用失效，旧 `end()` 失效；之前的保留 |
| `list` / `forward_list` | 仅被擦除元素的迭代器与引用失效，其他元素保留 |
| `map/set` 及其 multi 版本 | 仅被擦除元素的迭代器与引用失效 |
| `unordered_map/set` 及其 multi 版本 | erase 仅使被擦除元素失效；别与 rehash 的迭代器失效规则混淆 |
| `deque` 擦除尾部并包含最后元素 | 擦除元素的迭代器与引用、旧 `end()` 失效 |
| `deque` 擦除头部但未包含最后元素 | 仅擦除元素的迭代器与引用失效 |
| `deque` 擦除中间且未包含首尾元素 | 所有迭代器与引用失效，包括旧 `end()` |

**反例 / 验证：** 对支持返回下一迭代器的容器，常用片段 `if (remove(*it)) it = c.erase(it); else ++it;`，但还需检查保存的其他迭代器。`forward_list` 使用 `erase_after`，需要维护前驱。`remove_if` 算法只移动保留值并返回逻辑新尾，不缩小容器，C++17 常配合 `erase`；C++20 才加入标准容器相关 `std::erase_if`。用调试迭代器检测“erase 后继续 ++旧迭代器”的错误。

<a id="q26"></a>
### Q26 lambda 捕获引用的生命周期风险是什么？

**口述答案：** 引用捕获不拥有被引用对象，闭包被返回、存入线程池或异步回调后，外部对象可能已经销毁。按值捕获只复制捕获的值；若这个值是裸指针、`string_view` 或 `span`，并未复制其指向的数据。

**机制与边界：** `[this]` 复制的是指针，要求对象持续存活。C++17 的 `[*this]` 按值复制当前对象，有额外复制成本且要求可复制，并非复制整个对象图。初始化捕获可用 `[p = std::move(owner)]` 转移唯一所有权，但这样生成的闭包可能仅可移动，C++17 的 `std::function` 对目标的可复制要求要考虑。捕获 shared_ptr 延长寿命时，还应审查 Q19 的环。

**反例 / 验证：** 函数内 `int x = 1;` 后返回 `[&x]{ return x; }`，调用时引用已悬空。按值捕获修复这个整数案例，却不自动修复“按值捕获指向局部缓冲区的指针”。测试函数返回后、对象销毁后以及任务取消后执行回调的边界，用 ASan 和析构日志检查；并明确线程间共享状态是否需要锁。

<a id="q27"></a>
### Q27 模板实例化、特化和 ODR 有什么关系？

**口述答案：** 模板是按类型 / 参数生成实体的规则，编译器在需要定义的地方进行隐式或显式实例化。常把模板定义放头文件，是因为实例化点通常需要看到定义；也可在实现文件对有限类型显式实例化，并用 `extern template` 抑制不必要的隐式实例化。

**机制与边界：** ODR 约束实体的定义数量与一致性。满足条件的类、模板、inline 函数 / C++17 inline 变量可在多个翻译单元有相同定义，但不仅要求看似同名，还要求相应 token、名字查找等条件一致。函数模板的完整特化具有独立规则，放头文件的非 inline 完整特化容易造成多重定义；类模板可偏特化，函数模板不支持偏特化，常使用重载。

**反例 / 验证：** 只在 `lib.cpp` 中定义模板且未显式实例化调用方所需类型，常导致链接阶段缺少实例符号。分别做两个翻译单元包含相同头文件，测试普通函数定义、inline 函数、完整函数特化的链接结果。某些跨翻译单元 ODR 违规不要求诊断，链接成功也不证明定义一致；预编译宏差异尤其值得检查。

<a id="q28"></a>
### Q28 编译、汇编、链接分别做什么？

**口述答案：** 预处理展开头文件和宏；编译进行词法语法、类型语义分析与优化，并通常生成汇编或中间表示；汇编产生带机器码、符号及重定位信息的目标文件；链接解析跨目标文件符号、完成相应重定位并产出可执行文件或库。运行时装载还负责映射文件、处理动态依赖等。

**机制与边界：** “未定义引用”常是声明可见而定义未参与链接，也可能来自签名、命名空间、C / C++ linkage、库顺序、架构、ABI 或编译选项不一致。头文件保护避免同一翻译单元重复包含，不代替跨翻译单元 ODR 规则。LTO 让部分优化跨越传统阶段，但不改变区分编译错误和符号解析错误的必要性。

**反例 / 验证：** GCC / Clang 环境可依次运行 `g++ -E main.cpp`、`g++ -S main.cpp`、`g++ -c main.cpp` 检查不同产物，再显式链接所需 `.o`。在 ELF 工具链中用 `nm -C` 区分符号定义和未定义引用，`readelf -r` 看重定位。Windows 使用对应的编译器与 `dumpbin` 等工具，不把 ELF 文件结构当作所有平台通用格式。

<a id="q29"></a>
### Q29 静态库和动态库的链接 / 部署差异？

**口述答案：** 静态库一般是目标文件归档，链接器按需把相关目标成员加入最终产物；动态库保持独立文件，由装载器在启动或运行期间加载，进程可共享相应只读代码页。静态方式部署依赖更集中但更新通常需重新链接；动态方式可独立更新兼容库，但增加搜索路径、版本和 ABI 管理成本。

**机制与边界：** “链接一个静态库”不等于整个程序完全静态，仍可能依赖动态运行时。C++ 动态库边界涉及编译器 ABI、名称修饰、异常、标准库布局以及分配 / 释放责任。跨 Windows DLL 使用不同 CRT 堆等配置时，资源在何处申请、何处销毁尤其关键。长期稳定接口可考虑 C ABI、不透明句柄与显式销毁函数，但仍需定义结构布局和版本策略。

**反例 / 验证：** ELF 常见命令形态 `g++ main.o -lfoo` 中，传统静态库解析与扫描顺序相关；把库放在需要它的对象前可能留下未解析符号，具体依链接器选项而定。用 `readelf -d` / `ldd` 检查可信产物的动态依赖，Windows 用 `dumpbin /DEPENDENTS`。在干净运行环境测试缺库、错误版本与架构不匹配，不用开发机“恰好有库”作为部署验收。

<a id="q30"></a>
### Q30 如何用 ASan、UBSan、TSan 和 GDB 定位不同类别的问题？

**口述答案：** ASan 查常见越界和释放后使用；UBSan 检查一部分未定义操作；TSan 查运行中发生的数据竞争；GDB 用断点、线程栈、core dump 观察程序状态。先最小复现、记录构建和输入，再选择工具；工具无报告不代表所有路径正确。

**机制与边界：** ASan 不是通用未初始化内存检测器，泄漏检测能力还受平台与配置影响；UBSan 也不覆盖所有 UB。TSan 改变时序并增加开销，支持的平台、同步识别能力和忽略规则要确认。TSan 与 ASan 通常应构建为不同二进制，不混在同一测试配置。Release、Debug 和 Sanitizer 构建都值得保留，性能基线使用未插桩的优化构建。

**反例 / 验证：** 下列是 Linux 上具备相应运行库的 GCC / Clang **命令模板**，`repro.cpp` 需替换成练习程序；不是本仓库附带的已运行测试。

```bash
g++ -std=c++17 -g -O1 -fno-omit-frame-pointer -pthread \
    -fsanitize=address,undefined repro.cpp -o repro-asan
g++ -std=c++17 -g -O1 -fno-omit-frame-pointer -pthread \
    -fsanitize=thread repro.cpp -o repro-tsan
gdb ./repro-asan
```

在 GDB 中用 `bt`、`thread apply all bt`、`frame`、`print` 追溯相关状态。先修最早的有效错误报告，再回归同一输入。Windows 本地工具链的 ASan / TSan 支持与 Linux 不同，不把命令可复制等同于环境已具备。

<a id="q31"></a>
### Q31 data race 与一般 race condition 的差别？

**口述答案：** race condition 是程序结果不正确地依赖并发事件时序，范围较广。C++ data race 有严格定义：潜在并发的冲突操作中至少一个是非原子的，且两者之间没有所需的 happens-before 顺序；冲突包含读写同一内存位置、写写以及相关生命周期操作。存在 data race 的程序具有未定义行为。

**机制与边界：** 两线程同时读一个不被修改的普通对象通常没有 data race；写不同独立内存位置也未必有，但位域、`vector<bool>` 等要按实际内存位置判断。全部使用 atomic 可消除特定字段的数据竞争，仍可能有业务逻辑竞态。`volatile` 不提供原子性或线程同步，缓存一致性也不代替 C++ 内存模型。

**反例 / 验证：** 两线程对普通 `int count` 做 `++count` 是 data race。换成 atomic 后 `if (balance.load() >= cost) balance.fetch_sub(cost)` 仍可能在两线程交错时透支，这是复合条件逻辑竞态。用互斥区或正确 CAS 循环表达完整不变量；用 TSan 查第一类问题，用并发不变量测试查第二类问题。

<a id="q32"></a>
### Q32 什么是 happens-before？如何建立跨线程可见性？

**口述答案：** happens-before 是判断跨操作可见性与冲突访问是否合法的偏序关系，可由线程内的 sequenced-before 与跨线程的 synchronizes-with 等关系连接得到，并具有传递性。不要把它解释成日志中“物理时间先发生”或某条 CPU 指令执行较早。

**机制与边界：** 常见同步边有同一 mutex 的解锁与后续成功加锁、线程结束与成功 `join` 返回，以及被 acquire 读取到的 release 发布。release store 不会与任意 acquire load 自动配对，读操作必须读取到相应 release 或适用 release sequence 的值。发布一次初始化数据后，若发布方又无同步地修改同一数据，原有发布并不覆盖这些新冲突。

**反例 / 验证：** 下列为共享状态及两个线程中的**片段**，前提是两个线程开始前已创建这些对象，`payload` 只由发布方写一次，两个线程结束前对象持续存活：

```cpp
int payload = 0;
std::atomic<bool> ready{false};

// 发布线程：
payload = 42;
ready.store(true, std::memory_order_release);

// 接收线程：
while (!ready.load(std::memory_order_acquire)) { /* 仅作语义演示 */ }
assert(payload == 42);
```

成功读到 `true` 建立同步，因此此前写 `payload` happens-before 随后的读。若仅把标记读写换成 relaxed，原来的普通数据访问就失去这条同步保证。实际服务应按等待时长选阻塞或退避，别把空转示例当成队列实现；sleep 也不是同步边。

<a id="q33"></a>
### Q33 mutex、rwlock、自旋锁、信号量和条件变量分别适合什么场景？

**口述答案：** mutex 提供互斥所有权，适合普通共享不变量；读写锁允许多个读者或一个写者，适合确实可并行的只读操作；自旋锁忙等等待，只有极短且持锁线程有机会运行的临界区才可能获益；信号量按计数控制资源许可；条件变量等待共享状态满足某个谓词，本身不是保护状态的锁。

**机制与边界：** C++17 有 `shared_mutex`，标准计数信号量 `counting_semaphore` 从 C++20 起提供。读写锁的公平性和是否饿死某一方要看实现，读多不自动等于更快。自旋遇到线程被抢占、超额订阅、长 I/O 临界区时可能浪费 CPU。条件变量应结合 mutex 保护谓词；信号量可以保存许可，条件变量通知不是持久事件计数。

**反例 / 验证：** 读操作若顺便更新 LRU 或统计普通字段，就不再是共享锁下的纯读。把同一工作负载分别换用 mutex 与 shared_mutex，记录读写比例、持锁时长、吞吐、CPU 和写者 p99 等待时间；不要只用线程数与平均值判断。锁内部自旋策略也可能让“mutex 就一定立即睡眠”的描述失真。

<a id="q34"></a>
### Q34 条件变量为什么要在 `while` 中检查谓词？

**口述答案：** 唤醒只表示需要重新检查共享状态，不保证条件已经满足：可能虚假唤醒，也可能被通知后状态又被其他消费者改变。`wait(lock, predicate)` 等价于在锁保护下循环检查谓词，谓词为假时执行等待，是通常优先使用的形式。

**机制与边界：** `wait` 原子地释放关联 mutex 并进入等待，返回前重新加锁。谓词的检查与修改应遵从同一同步协议，常见做法是都在同一 mutex 下进行。通知本身不保存“待消费通知”，若先通知、后开始等待而没有持久状态，可能丢失事件。修改状态后可以在锁内或解锁后通知，正确性依赖状态协议，不由通知位置单独决定；还要保证 mutex、cv 和对象寿命。

**反例 / 验证：** 有界队列消费者谓词可写为 `closed || !queue.empty()`，醒来后在锁内区分“有任务”与“已关闭且空”。用 `if (queue.empty()) cv.wait(lock);` 后无条件取队头是错误模式。测试先生产后等待、多个消费者争夺一个元素、额外无效通知与关闭唤醒；这些测试可暴露设计错误，但压力测试通过仍应配合同步关系论证。

<a id="q35"></a>
### Q35 如何设计有界阻塞队列的关闭和异常路径？

**口述答案：** 先定契约：容量大于 0；`push` 在满时等待，关闭后拒绝新任务；`pop` 在空且未关闭时等待，关闭后可选择排空剩余任务再返回结束。用一个 mutex 保护队列与关闭标记，两个条件变量分别等待“非空”和“非满”，关闭时唤醒全部生产者与消费者。

**机制与边界：** push 谓词为 `closed || size < capacity`，醒来后先判断关闭再入队；pop 谓词为 `closed || !empty`，醒来后优先按契约处理已有元素。状态转换在锁内完成，成功入队通知非空，成功出队通知非满，close 幂等地设置标记并通知双方。不要在锁内执行用户任务。析构前必须确保所有访问者已结束，close 不是对象可立即销毁的充分条件。

**反例 / 验证：** 元素移动可能抛异常时，先改计数再构造结果可能破坏不变量；元素被移动一半也可能影响“原任务完整保留”的强保证。可限定任务为 noexcept 可移动的包装或传递拥有指针，并明确异常时队列状态。验证容量 1、多生产者 / 多消费者、满队列关闭、空队列关闭、重复关闭、注入构造失败；检查每个成功接收的任务按排空 / 取消契约终结，没有等待线程遗留。

<a id="q36"></a>
### Q36 `lock_guard`、`unique_lock`、`scoped_lock` 如何选择？

**口述答案：** `lock_guard` 用最简单的作用域 RAII 保护一个锁，构造加锁、析构解锁；`unique_lock` 可移动，支持延迟加锁、尝试加锁、手动解锁 / 重锁，适合条件变量；C++17 的 `scoped_lock` 可同时管理多个 mutex，对多个锁采用避免死锁的获取策略。

**机制与边界：** `condition_variable::wait` 接收 `unique_lock<mutex>`，因为等待过程要临时释放并重新获得锁。RAII 保证异常离开作用域时解锁，不保证临界区内的数据修改已回滚。`adopt_lock` 表示接管已经持有的锁，前提必须真实满足；`defer_lock` 只构造管理器不立即获取锁。将锁交给另一个线程解锁等违反 mutex 所有权约束的行为需要避免。

**反例 / 验证：** 创建一个无名临时锁管理器，可能在完整表达式结束就解锁，后续语句并未受保护，应使用明确的命名变量。将两个已知相异的 mutex 交给 `scoped_lock(a, b)` 可统一获取；误把同一个非递归 mutex 传两次仍是设计错误。用异常注入验证锁释放，再用不变量测试验证受保护的数据是否一致。

<a id="q37"></a>
### Q37 如何通过锁顺序避免死锁？死锁检测和超时有什么代价？

**口述答案：** 给锁建立一致的全局顺序，线程只按该顺序获取需要同时持有的锁，可破坏循环等待。若同一操作一次获取多个锁，可以用 `std::lock` 或 `scoped_lock`。锁策略应覆盖跨模块调用、回调与析构，不只检查当前函数中的两个 mutex。

**机制与边界：** 死锁检测要维护或采集等待关系，并处理误判、采样空窗与开销。超时能让等待有界，但不自动撤销已做的修改，也不证明没有死锁；失败后应释放已持锁并按协议回滚、返回或退避。持续无协调重试可能活锁，公平性不足可能饥饿。持锁调用未知回调、阻塞 I/O 或等待某个也需要该锁的线程结束，是常见隐藏环。

**反例 / 验证：** 线程 A 持锁等待 `join(B)`，而 B 等待同一锁，即使系统只有一把业务锁也可能卡住。使用固定的业务 ID 定义排序，明确同一对象的去重处理；若按对象地址排序，应选能提供正确全序的比较方式而非随意比较不相关裸指针。卡住时采集所有线程栈、锁持有者和等待者，构建等待图，不只加大超时掩盖问题。

<a id="q38"></a>
### Q38 CAS 的 ABA 问题是什么？

**口述答案：** CAS 检查当前位置的值是否仍等于预期，但同一个值可能已经经历 A → B → A。比较通过只说明现在表示相同，不证明期间没有修改。例如无锁栈头回到同一地址时，该节点的后继或生命周期可能早已变化。

**机制与边界：** 版本计数可把“值 + 世代”一起比较，但要分析计数回绕、位宽与硬件是否支持所需原子宽度。hazard pointer、epoch 等内存回收技术用于阻止仍被观察的节点过早回收和地址复用；它们与逻辑状态验证相互配合，并非一句“加版本号”解决所有无锁算法问题。成功 CAS 前后都必须遵守节点生命周期。

**反例 / 验证：** 线程 A 读到头指针 p 后暂停；线程 B 弹出 p、操作其他节点并再次让头为 p；A 只比较指针会误把状态视为未变。用确定性调度屏障复现这个交错，记录节点 ID、地址和世代。`compare_exchange_weak` 的伪失败是另一问题，通常放循环重试；失败时 expected 被更新为实际值，后续依赖 expected 的计算也要重新做。

<a id="q39"></a>
### Q39 `memory_order_relaxed/acquire/release/seq_cst` 如何取舍？

**口述答案：** 先从并发协议和不变量出发。relaxed 提供该原子对象的原子操作与修改顺序，但不发布其他普通数据；release/acquire 适合有明确交接关系的数据发布；seq_cst 在相关原子操作上增加单一全序约束，最容易作为初始推理模型。更弱内存序不是随意的性能开关。

**机制与边界：** release 通常用于 store，acquire 通常用于 load；读改写可用 acq_rel。acquire 读到 release 或适用 release sequence 的值才产生所需同步。即使使用 seq_cst，未被同步的普通数据仍可 data race，它也不把一串原子操作变成事务。纯统计计数常可用 relaxed，但如果计数值同时宣布其他数据可读，就需重新证明协议。

| 内存序 | 主要保证 | 常见用途 | 关键限制 |
| --- | --- | --- | --- |
| relaxed | 单个原子操作不可分割、该对象有修改顺序 | 无额外数据发布责任的计数 | 不同步独立普通数据 |
| release / acquire | 符合读值条件时建立同步 | 初始化完成后发布对象 | 必须找出实际同步的读写对 |
| acq_rel | 读改写同时具有 acquire 和 release 效果 | 获取并交接状态的原子 RMW | 不适用于普通 load/store 的任意搭配 |
| seq_cst | 在 SC 操作之间增加符合规则的单一全序 | 初版正确性、较简单协议 | 不自动保护非原子字段或复合事务 |

**反例 / 验证：** CAS 的失败路径只执行读，失败内存序不得使用 release 或 acq_rel；使用合法且易审计的组合，例如成功 acq_rel、失败 acquire。对 Q32 的发布示例画出 sequenced-before / synchronizes-with 边，并解释删去任一边会怎样。x86 一次压力测试没失败不证明弱序平台也正确。C++17 与 C++20 对 release sequence 的正式定义存在变化；稳妥入门示例让 acquire 直接读取明确的 release 发布值，复杂 RMW 链另按标准版本逐项证明。

<a id="q40"></a>
### Q40 线程池如何处理任务队列、停止、拒绝和工作线程异常？

**口述答案：** 线程池是生命周期状态机，不只是一个任务队列。先定义 running、closing、stopped，以及排空或取消策略。提交任务与检查状态在同一同步协议下完成，关闭后明确拒绝；工作线程取出任务后释放队列锁，再执行任务。停止时唤醒等待线程并由合适的管理方 join。

**机制与边界：** 拒绝要给调用方可观测结果，例如错误返回或已完成为异常的 future，别留下永远等待的结果。`packaged_task` 可把任务异常保存到关联 future；直接调用普通任务时需捕获异常，避免异常逃出线程入口导致 `std::terminate`。构造线程池时中途创建线程失败，也要唤醒和 join 已启动线程。队列容量、阻塞提交、超时与拒绝策略决定背压表现。

**反例 / 验证：** 工作线程提交新任务后同步等待其 future，而全部线程都在做同样的事，可能形成线程池饥饿死锁；简单增加线程数只是改变阈值。工作线程直接销毁池也可能触发 self-join 或资源寿命问题，应在契约中限制或设计外部协调。测试提交与关闭竞争、任务抛异常、队列满、取消后 future 状态、重复停止以及析构时是否仍有任务访问池对象。

<a id="q41"></a>
### Q41 伪共享是什么？如何测量而不是猜测？

**口述答案：** 不同线程修改不同变量，这些变量却位于同一个缓存一致性块中，缓存行在核心间频繁争用，造成性能下降，就是伪共享。逻辑上变量可以完全独立甚至没有 data race，但硬件一致性流量仍会相互干扰。

**机制与边界：** 通过每线程分片、批量合并、分隔热点写字段可缓解。仅对数组起始地址做对齐，不保证相邻元素各占独立缓存行，需要检查元素大小和布局。C++17 的 `hardware_destructive_interference_size` 可提供实现相关建议，工具链支持和目标差异要记录；不要把“所有处理器缓存行都恰为 64 字节”当作前提。

**反例 / 验证：** 用每线程独立的原子计数器比较紧邻布局和隔离布局，采用相同 relaxed 操作、线程亲和性、工作量、预热与优化选项；避免编译器把循环消掉。记录吞吐、CPU、缓存到缓存传输等硬件指标，可在支持的平台用 `perf c2c` 观察。仅看 cache miss 总数不足以区分伪共享、真实共享和一般局部性差；隔离后也要评估更大内存占用的代价。

<a id="q42"></a>
### Q42 如何区分 CPU、锁、内存和 I/O 瓶颈？

**口述答案：** 先确认负载和服务目标，再把端到端延迟拆成排队、执行和外部等待；关联 CPU 利用率、运行队列、锁等待、内存、磁盘、网络与业务指标。CPU 高不一定是有效计算，CPU 低也不代表服务空闲。用时间线与剖析数据提出假设，再通过受控实验验证。

**机制与边界：** CPU 瓶颈看热点栈、每请求 CPU 时间与核扩展性；锁瓶颈看争用位置、等待时长及持锁临界区；内存瓶颈区分容量压力、缺页、分配器争用、带宽和局部性；I/O 瓶颈看磁盘 / 网络时延、队列深度、连接池等待和下游响应。NUMA、cgroup CPU 限制、线程抢占和内核路径也会改变表象。

| 假设 | 优先证据 | 受控实验 |
| --- | --- | --- |
| CPU 算法或编码成本 | `perf record/report` 热点、每请求 CPU 时间 | 固定输入规模，对比一个算法或实现变更 |
| 锁竞争 / 调度 | 所有线程栈、off-CPU 分析、锁等待指标 | 缩短临界区或分片，观察吞吐及尾延迟 |
| 内存容量 / 局部性 | RSS、缺页、分配画像、硬件计数器 | 固定工作集，比较布局与复用策略 |
| 磁盘 / 网络 / 下游 | I/O 时延、请求 trace、连接池排队 | 用可控下游或内存数据源隔离等待 |

**反例 / 验证：** 忙轮询使 CPU 100%，主要问题仍可能是等待方式；锁睡眠导致 CPU 低而尾延迟高。优化报告至少记录机器、构建、数据集、并发度、持续时间、p50/p95/p99、错误率与重复次数，并保留正确性回归。只报“QPS 提升”却不控制超时、丢请求或工作量，证据不成立。
