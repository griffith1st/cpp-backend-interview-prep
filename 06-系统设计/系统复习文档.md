## 1 需求与设计流程

不要一开始画 Redis、Kafka、分库分表。先确认用户做什么、哪个动作重要、允许什么失败、数据保留多久。功能需求是创建/查询/撤销等行为；非功能需求是峰值、延迟、可用性、一致性、成本和运维约束。

用一页确定：读写比、数据大小、热点分布、地域、认证、SLO、RPO/RTO。SLO 是服务目标，RPO 描述可接受数据丢失窗口，RTO 描述恢复时间目标；“高可用”没有数值与测量口径时难以验证。

设计主线：需求 -> 估算 -> API/数据 -> 正常路径 -> 失败路径 -> 扩容/恢复 -> 指标与验证。每加一个组件，说明它解决的瓶颈、引入的状态与失效模式。单机能满足需求时，简洁设计更易证明正确。

三种常见错误：把日活当 QPS；把所有缓存数据当权威数据；把异步提交当业务已成功。面试回答应先给最小可行链路，再根据量化约束扩展。

<a id="design-2"></a>
## 2 容量、延迟与排队

统一单位：QPS=request/s，带宽=byte/request×request/s，存储=新增条数×每条字节×保留时长。GB 通常十进制，GiB 是 2^30 byte。副本、索引、日志、备份和中间结果要分别估算，别把业务原始数据直接等于总磁盘需求。

在稳定系统且统计边界一致时，Little 定律 L=λW：平均在系统内请求数=平均到达率×平均逗留时间。5000 req/s、平均 40 ms，则平均并发约 200。这不是线程数的直接配置值，更不能把 P99 填入平均公式。

```text
端到端耗时 = 接入等待 + 服务排队 + 业务执行 + 下游等待 + 返回传输
剩余预算 = 总 deadline - 已消耗时间
```

队列不创造处理能力，只把瞬时流量转为等待。到达 3000/s、处理 5000/s、已有积压 100万，理想清空 500s；若到达超过处理，队列持续增长。按最坏请求内存估算队列上限，按可接受等待估算长度，必要时主动拒绝。

容量目标要包含故障状态：三个节点平均各承载 30% 总容量，一个节点下线后其余负载上升，是否仍满足延迟？自动扩容有启动时间，也不是无穷快。平均负载健康不代表热点分片或尾延迟健康。

<a id="design-3"></a>
## 3 API、身份与幂等

API 先规定输入约束、业务错误、分页稳定性、身份与资源权限。认证识别谁，授权决定能做什么；JWT 签名不自动解决资源级访问控制或立即撤销。请求 ID 用于追踪，幂等键用于去重，两者可关联但语义不同。

网络超时意味着结果未知，不等于服务端未执行。POST 也可在业务层实现幂等，但其 HTTP 方法语义不要求所有 POST 都可无条件重试。幂等作用域通常为(调用方,操作类型,幂等键)，还需保存请求摘要，避免同键不同参数复用。

```text
记录：key, request_hash, state, result, version, expires_at
状态：NEW -> PROCESSING -> SUCCEEDED / FAILED
重复：返回既有结果，或告知正在处理，避免再次产生效果
```

单库操作可让幂等记录、业务写和结果同事务提交。提前持久化 PROCESSING 时，要定义执行者失联接管、租约/心跳、版本校验与结果查询；单纯“超时就重跑”可能重复扣款。外部副作用需对方幂等接口、对账与补偿，不能用本地数据库事务包住所有世界。

去重键保留时间必须覆盖合理重试窗口。结果可以先存较小摘要再返回查询入口，但响应一致性、权限与过期语义要明确。

<a id="design-4"></a>
## 4 数据模型与一致性

先写不变量：短码唯一、库存非负、订单状态合法跃迁、每个幂等键只产生允许次数的业务效果。选择数据库不是背“关系型强一致、NoSQL 弱一致”，而是按具体存储引擎、事务与部署协议判断。

唯一约束是并发下兜底的工具，应用先查不存在再写会发生竞争。事务应明确范围、隔离和锁；跨数据库、缓存、消息时，多个本地事务不自动构成一个全局原子操作。

线性一致性强调操作看起来在调用与返回间某时刻生效；可串行化强调事务效果等价于某个串行执行，两者不是同义词。最终一致只有在更新停止、投递与合并策略满足条件时才有意义，必须说明如何收敛以及用户在窗口内看到什么。

CAP 讨论发生网络分区时的特定一致性和可用性保证，不是任意系统“随便三选二”。业务可对不同操作做不同选择，例如余额写入要求更强约束、浏览统计允许稍后收敛。

Outbox 把业务写与待发布事件放在同一数据库事务，解决提交和发消息之间的双写缺口；投递器确认丢失仍可能重发，消费者需幂等。Saga 把跨服务流程变成状态机与补偿，补偿不是时间倒流，已经发出的通知或外部动作未必可完全撤销。

<a id="design-5"></a>
## 5 缓存与热点

Cache-aside 读未命中查库再回填，写库成功后失效缓存。它减少正常回源，但旧读回填、删除失败、消息乱序都可能产生陈旧数据。TTL 提供收敛上界的一部分，不能单靠一句“最终一致”证明业务正确。

| 问题 | 机制 | 常用处理与代价 |
| --- | --- | --- |
| 穿透 | 大量不存在键回源 | 输入约束、短期空值、Bloom filter；考虑新增同步 |
| 击穿 | 单热点过期并发回源 | singleflight/互斥加载、软过期；注意锁失效 |
| 雪崩 | 大量键或缓存服务同时失效 | 随机 TTL、分批预热、回源限流、降级 |
| 热点 | 少数键流量极大 | 本地缓存、拆分可聚合计数、复制读；考虑失效 |
| 大值 | 单次数据与网络成本巨大 | 分块、限制返回、改模型；避免整值反复搬运 |

Bloom filter 可能误报“存在”，正常情况下不应漏报已插入集合中的成员，但更新同步与删除策略会影响实际保证。它不是数据库权威索引，也不替代权限检查。

99% 命中率下峰值 10000/s 只有约 100/s 回源；全失效时可能立刻变成 10000/s。缓存命中率是日常指标，数据库容量和保护策略要覆盖失效时的流量变化。

<a id="design-6"></a>
## 6 消息、顺序与可靠性

至少一次常由重试与确认机制实现，但消费者可收到重复；至多一次可能丢；“恰好一次”必须说明协议边界，不能扩展为任意数据库/邮件副作用都自然一次。

生产确认丢失会让已写入消息被重发；消费业务提交后 offset 未提交也会重放。先提交 offset 再业务处理会产生另一个丢失窗口。消息包含业务键、事件 ID、版本与必要上下文，消费者用唯一约束或状态版本处理重复与乱序。

同订单分到同分区可帮助保持该分区日志顺序，但消费后扔入任意工作线程又会乱序。需要按键串行、状态机版本检查或对业务明确不要求全序。全局排序代价更高，不应为局部需求建立全局瓶颈。

积压排查先看生产/消费速率、分区倾斜、失败重试与下游时延。加消费者受分区数和下游能力限制。死信队列应有报警、检索、人工/自动修复和受控重放，不是隐藏失败的终点。

<a id="design-7"></a>
## 7 分片、副本与迁移

副本提高可用性或读取能力，也引入复制延迟与故障切换；备份用于历史恢复，复制会把误删传播到副本，因此副本不等于备份。异步复制确认后的数据在主故障时可能丢失，取决于确认与切换协议。

分片键应同时考虑分布、局部性、增长、热点与查询。按用户聚合便于用户内事务，却可能被超大用户打穿；按时间易归档，但当前时间段写热点突出。随机 hash 分布均匀，不代表跨用户聚合查询容易。

一致性哈希减少节点变化时的迁移范围，不自动消除热点或保证迁移一致性。迁移通常需要基线复制、增量追赶、水位校验、路由版本、切换与回滚。双写必须考虑部分成功、重试与版本，否则迁移期间数据分叉。

读写分离需明确读到自身新写的要求：关键请求读主库、携带版本水位、等待副本追上或接受短暂陈旧。单凭“主从复制”不回答用户刚更新却看见旧值的问题。

<a id="design-8"></a>
## 8 过载保护与故障恢复

限流控制入口速率，熔断隔离高失败依赖，隔舱限制资源相互影响，背压向上游传递承载不足，降级改变服务能力。它们互补但不是同一个按钮。

| 算法 | 特征 | 注意 |
| --- | --- | --- |
| 固定窗口 | 简单计数 | 窗口边界允许较大瞬时突发 |
| 滑动窗口 | 更贴近连续时间 | 内存与计数维护成本 |
| 令牌桶 | 允许受控突发 | 桶容量与补充速率分别定义 |
| 漏桶 | 平滑输出 | 排队引入延迟，需要有限容量 |

重试只用于可重试错误和可接受副作用的操作，有限次数、指数退避、抖动与总预算共同约束。三层各三次尝试可能放大到 27 次末端请求；不要把重试次数隐藏在多个组件默认值里。

超时分连接、读、排队、整体 deadline，传播剩余预算。取消调用方等待不意味着服务端任务已取消；后台工作继续执行会消耗资源或产生副作用。优雅退出停止接新流量、处理在途任务、达到截止时采取明确策略。

恢复要验证半开探测、渐进放量和回滚，避免依赖一恢复全部请求同时涌入。故障演练有范围、停止阈值和数据保护，不用真实用户请求试探未知破坏性路径。

<a id="design-9"></a>
## 9 短链接完整案例

需求假设：每日创建 100万条、跳转 1亿次、保留一年、峰值是均值 10 倍、映射 200 byte、三副本、每次响应 500 byte。

| 项目 | 计算 | 结果 |
| --- | --- | --- |
| 创建均值 | 10^6 / 86400 | 11.6/s |
| 跳转均值/峰值 | 10^8 / 86400，再乘 10 | 1157/s、11574/s |
| 原始年存储 | 10^6×365×200 | 73 GB |
| 三副本 | 73×3 | 219 GB，另加索引日志 |
| 峰值响应带宽 | 11574×500×8 | 46.3 Mbit/s，未含额外协议开销 |

数据模型 Link(short_code唯一、destination、owner_id、status、expires_at)。创建使用全局 ID 转 Base62 或随机码+唯一约束；Base62 是表示法，不提供唯一性或保密。随机码碰撞要由约束重试处理，不能只说“概率很小”。

POST /links 做权限、目标 URL scheme 和长度检查、幂等创建；GET /{code} 查缓存/数据库，检查状态与过期，返回重定向。永久 301 缓存会削弱撤销与访问统计，302 也需明确缓存头，不能用状态码代替全部缓存策略。

统计从核心跳转链拆开，事件允许的丢失和重复由业务定义。缓存整体失效时启用回源限制与受控降级；热点短码可本地缓存；禁用生效时限需明确，多层缓存越多，失效协议越复杂。

失败验收：创建提交后响应丢失不重复生成；禁用后旧缓存按约定失效；过期边界不跳转；统计消费者停机可恢复积压；缓存停机时数据库不被无界流量压垮。

<a id="design-10"></a>
## 10 聊天与秒杀变式

### 聊天

先分“服务端接受、持久化、对端收到、用户已读”四种状态。客户端 message_id 用于重复提交去重，服务端分配会话内序号，重连携带最后确认水位补取消息。WebSocket 建连成功不证明消息持久化或对端已读。

跨设备确认范围、离线保留、撤回与顺序要单独定义。慢接收方需有限发送缓冲、断线重连和补偿拉取，不可无限缓存直到内存满。群聊扇出写与扇出读取舍依群规模和读取模式，不存在统一最佳方案。

### 秒杀

核心不变量是库存扣减与订单关联。单库可用条件更新 `stock >= quantity` 并事务写订单，受影响行数决定成功；请求重试依幂等键。Redis 预扣可削峰，但与数据库分离后需状态机、补偿与对账，预扣成功不等于订单已落库。

限流、排队资格、过期释放、支付回调重复、取消与付款交错逐条推演。防超卖和防超时是两个不同目标；牺牲正确性换吞吐需明确业务接受，面试中不能默认允许。

<a id="design-11"></a>
## 11 可观测性与验证

以请求路径关联日志、metrics 和 trace。至少观察速率、错误、延迟、饱和度，再补队列长度、连接池等待、重试放大、缓存回源、消息 lag 与业务不变量失败。高基数用户 ID 不宜无界放进指标标签。

可靠性测试矩阵：提交前崩溃、提交后响应丢失、重复请求、乱序消息、依赖延迟、缓存清空、单节点退出、分片热点。每项写清预期、实际、停止条件和恢复证据；没有执行就保持“待验证”。

压测报告记录环境、版本、数据分布、并发/到达率、持续时间、预热、错误率和延迟分位数。闭环负载会因服务变慢而降低发送速率，可能掩盖排队问题；根据目标选择负载模型，说明协调遗漏等测量偏差。

<a id="design-12"></a>
## 12 面试流程、自测与参考

45 分钟建议：5 分钟需求、8 分钟估算、10 分钟核心模型、12 分钟失败设计、5 分钟指标、5 分钟追问。先画一条核心链路，所有数字带单位，所有强保证写成立条件。

自测：幂等处理中节点崩溃谁接管？缓存删除失败怎样收敛？同分区为何仍可能业务乱序？副本为什么不是备份？全局 deadline 怎样传递？增加消费者何时没有效果？短链禁用如何穿透浏览器缓存？

参考：[System Design Primer](https://github.com/donnemartin/system-design-primer)、[Kafka 文档](https://kafka.apache.org/documentation/)、[Google SRE Book](https://sre.google/sre-book/table-of-contents/)、[HTTP 语义 RFC 9110](https://www.rfc-editor.org/rfc/rfc9110)。外部入口用于对照，不作为个人项目落地证据。用 [P9](../09-AI学习/提示词库.md#p9-系统设计面试)逐步追问，统一 0-4 分评分，4 分需真实项目证据而非漂亮架构图。
