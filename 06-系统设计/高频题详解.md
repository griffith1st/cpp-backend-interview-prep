## Q96 短链接服务

**口述：**先问读写比例、有效期、自定义别名、访问统计和可用性。创建路径生成唯一短码并持久化映射；跳转路径优先缓存再查数据库；统计可异步，不必阻塞每次跳转。热点、失效和恶意目标校验决定进一步设计。

### 数量级推演

假设每日新建100万条、每天跳转1亿次、峰值为平均10倍；一条映射按200 byte计，保留一年，三份副本。暂不计索引、日志、压缩等开销。

| 指标 | 计算 | 结果 |
|---|---|---|
| 平均创建QPS | 1000000/86400 | 约11.6 |
| 平均跳转QPS | 100000000/86400 | 约1157 |
| 峰值跳转QPS | 1157.4×10 | 约11574 |
| 每年基础映射数据 | 1000000×365×200 | 73 GB 十进制 |
| 三副本基础数据 | 73×3 | 219 GB，加上索引日志还会更多 |
| 每响应500 byte的峰值出口 | 11574×500×8 | 约46.3 Mbit/s，不含协议额外开销 |

日活与请求量不是同一指标，不能混用；峰值倍数只是假设，面试官更改它时应重新估算。副本量不是新增业务数据量。

### API 与数据模型

```text
POST /links
输入: destination, expires_at, optional_alias, idempotency_key
输出: short_code, short_url

GET /{short_code}
输出: 302 Location，或404/410等明确状态

Link: short_code(unique), destination, owner_id, status, expires_at
```

短码可用全局唯一ID转Base62或随机码加唯一约束重试。Base62只是表示法，不负责唯一性，也不提供保密；顺序ID更易枚举。随机码需要分析空间占用和碰撞，仍用数据库唯一约束兜底。创建接口幂等键避免重试生成多条业务记录。

### 请求链和故障

```text
请求 -> 接入与限流 -> 短码服务 -> 缓存命中 -> 检查有效性 -> 跳转
                                -> 未命中 -> 数据库 -> 回填
访问事件 -> 有界队列/批量 -> 统计消费与聚合
```

过期与禁用需同时在数据/缓存层定义生效时限；缓存TTL要考虑业务有效期。使用301永久缓存会削弱快速撤销与完整访问统计能力，302也需明确缓存头。入口只处理允许的URL scheme、创建权限和滥用策略，不把“任何字符串都可作为Location”当完整实现。

缓存全失效时做请求合并、降级/限流，避免全部流量打数据库；单热点短码可多级缓存；异步统计需要事件ID和重复处理策略。如果统计允许少量丢失，可以用不同于核心映射的持久化等级，但要明确业务同意。

**追问/验证：**缓存命中率如何影响回源QPS？假设99%命中，正常峰值回源约116/s，但缓存失效可能接近11574/s。重点验证故障下容量，而不是只报日常均值。

## Q97 幂等接口与重复消息

**口述：**网络超时意味着结果可能未知，不等于服务端没执行。使用作用域明确的幂等键，把请求与业务效果、处理状态和结果关联；重复请求查询已有结果或受控等待。

**状态设计：**`NEW → PROCESSING → SUCCEEDED/FAILED`，唯一键可为(调用方,操作类型,幂等键)。同时保存请求摘要，拒绝同一键对应不同请求体。关键业务写和幂等结果尽量在同一个数据库事务内提交，否则会产生“记了幂等但业务没做”或反向窗口。

对完全在单库完成的操作，可把幂等记录、业务写入和最终结果放在同一事务中，失败时一起回滚。若 PROCESSING 必须提前持久化，则记录执行者、租约或心跳与版本，定义失联后的接管规则。接管前应确认原业务是否已经提交；原执行者恢复后，也应通过版本或状态条件阻止陈旧提交。FAILED 应区分可重试失败与已确定的终态失败，结果未知时先查询或对账，避免直接重复外部副作用。

外部调用如支付、发邮件不在本地事务内，需要对方幂等接口、outbox或可对账状态机。outbox 把业务数据与待发布事件同事务提交，投递器仍可能重发，因此消费端还需去重或幂等。

**追问/验证：**并发两次请求、处理到一半崩溃、已提交但响应丢失、幂等键过期后重试四种情形必须分别推演。去重TTL短于业务重试窗口会重新执行。

## Q98 消息重复积压乱序

**口述：**生产确认丢失、消费成功但提交进度失败都可能重复；消费速率低于生产速率形成积压；多分区、并行处理和重试影响顺序。先定义业务需要的顺序范围，再选择分区键与处理策略。

**推演：**同订单按order_id进入同分区，并不代表消费后异步发到任意线程就继续有序。可使用按键串行、业务版本检查或状态机拒绝过期事件。Kafka所谓恰好一次有范围条件，不能扩展成所有外部数据库/邮件副作用都天然恰好一次。

积压排查从生产速率、消费速率、分区分布、失败重试和下游时延入手。盲目加消费者可能超过有效分区数，也可能压垮下游。死信队列需要检索、修复和受控重放流程，否则只是把失败搬走。

**追问/验证：**积压100万条，净消化速率=消费5000/s-新增3000/s=2000/s，理想清空约500s；忽略新消息会高估恢复能力。净速率≤0时积压不会自行清空。

## Q99 分片键与迁移

**口述：**分片键需平衡访问局部性、分布均匀、增长和跨分片查询。按用户可聚合用户数据，但大客户会热点；时间分片便于归档，却可能把新写集中在最新分片。

**机制/边界：**一致性哈希减少节点变化时的键迁移，并不自动解决热点或迁移一致性；虚拟节点改善分布也要看权重。全局唯一ID、二级索引、跨分片事务和聚合查询都要另行设计。

迁移可采用基线复制、增量追赶、路由版本与切换校验，明确在迁移中读哪个副本、写如何去重、回滚如何处理。双写两个分片若没有版本/事务/补偿，故障时会分叉。

**追问/验证：**用一个超大用户和一次迁移期间超时作为反例；定义迁移水位、校验计数/摘要和分批切换条件。

## Q100 避免级联故障

**口述：**用整体deadline限制等待，有限重试配合指数退避和抖动；限流控制入口，熔断暂时隔离失败依赖，隔舱与有界队列防止某一业务耗尽全部资源；降级只保留业务允许的能力。

**机制/边界：**每层都重试三次可能导致指数放大；重试应集中规划并仅用于可重试错误和可接受副作用的操作。熔断不是限流，探测恢复也要限制流量，避免同时恢复造成新一轮过载。

原请求deadline=1s，下游已经消耗800ms，剩余步骤不能再默认各等1s。传播剩余预算，区分连接、读、排队超时；监控P99、错误率、队列深度、重试放大系数与降级比例。

**追问/验证：**下游延迟变成原来10倍时，画入口到队列的负反馈；演练要有停止条件和回滚，不能只证明正常负载可用。

## 三组变式与评分

1. **聊天服务：**按会话定义顺序，离线消息持久化，客户端带最后已确认序号恢复；网络连接成功不等于消息送达/已读。
2. **秒杀库存：**明确是否允许排队和超卖，原子库存变更与幂等订单关联；缓存预扣和数据库提交分离时设计补偿与对账。
3. **日志采集：**批量、有界缓冲、磁盘暂存与背压；日志丢失预算和业务数据不同，磁盘满时必须有政策。

45分钟训练分配：5分钟需求、8分钟估算、10分钟接口和数据、12分钟失败与一致性、5分钟监控、5分钟追问。按原题库0–4分评分，3分至少说明机制、失败路径和验证，4分还需个人证据；假设数字不算个人绩效。
