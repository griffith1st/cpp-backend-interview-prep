## 索引与查询 Q75–Q79

### Q75 B+ 树为什么适合索引

**口述：**内部节点主要存键与子指针，扇出大、树高低，能减少页访问；有序叶子便于范围扫描。与哈希相比，它支持范围/顺序，与二叉树相比更适配页式存储。

**机制/边界：**真实成本还受键宽、填充率、页缓存与随机/顺序 I/O 影响；主键过宽会放大 InnoDB 二级索引。B+树不是所有工作负载的唯一选择，写密集场景也可能采用 LSM。

**追问/验证：**给定16 KiB页、每条内部索引约24 byte，可粗估数百扇出，但需扣页头与空间开销；不要用理想除法当精确实现参数。

### Q76 聚簇 二级索引与回表

**口述：**InnoDB 聚簇索引叶子承载行数据，二级索引叶子含索引键及主键值；二级索引未覆盖所需列时，再用主键定位行，称回表。

**机制/边界：**没有显式主键时 InnoDB 有选择唯一非空索引或生成隐藏键等规则。PostgreSQL 普通索引指向堆元组位置，并非同样的聚簇组织。索引覆盖也不意味着所有引擎完全免除可见性检查。

**追问/验证：**解释宽主键如何扩大所有二级索引；对比只选索引列与 SELECT * 的计划和实际读页。

### Q77 联合索引最左前缀

**口述：**联合索引按列次序形成字典序。连续左前缀的等值条件通常便于定位，再结合范围扫描；跳过前导列不再天然形成一个紧凑连续区间。

**机制/边界：**不要只背“范围后全部失效”。后续列仍可能用于过滤、覆盖或部分优化；skip scan 等优化取决于版本与成本。WHERE 文本书写顺序不等于索引列顺序。

**追问/验证：**索引(a,b,c)，分别推演a=1、a=1 AND b>3 AND c=9、b=3。用 EXPLAIN 核验访问范围和剩余过滤。

### Q78 覆盖索引与 ICP

**口述：**覆盖索引让查询所需信息可由索引提供，减少回表。Index Condition Pushdown 把可在索引项上判断的部分条件交给引擎，在回表前过滤不匹配项。

**机制/边界：**“索引下推”常是对 ICP 的简称，并非必然另一个独立功能。`Using index` 与 `Using index condition` 含义不同；覆盖与谓词下推解决不同成本。

**追问/验证：**统计扫描索引项、回表行和结果行；返回很少行不意味着只扫描很少行。

### Q79 为什么没走索引

**口述：**优化器选择估算成本较低的计划。低选择性、大比例返回、统计偏差、类型转换或函数表达式等可能改变索引可用性与成本；“建了索引就一定走”不成立。

**机制/边界：**有函数索引/生成列等支持时不能机械判定函数条件失效；隐式转换方向和字符集也重要。EXPLAIN 是估计，EXPLAIN ANALYZE 会实际执行，先确认语句副作用和资源成本。

**追问/验证：**相同 SQL 不同参数可能返回量悬殊；收集版本、DDL、数据分布、计划和运行读页，避免不加证据就 FORCE INDEX。

## 事务与优化 Q80–Q88

### Q80 ACID 由什么保证

**口述：**原子性依赖回滚与恢复机制；隔离性依赖锁、MVCC、序列化检测等；持久性依赖日志、刷盘与恢复；一致性还依赖约束和正确业务事务，不能全归功某一种锁。

**机制/边界：**应用把相互依赖的写拆成多个事务，数据库不会自动恢复业务不变量。持久性随刷盘与复制配置变化，崩溃恢复和灾备是不同层次。

**追问/验证：**订单已创建但库存未扣时，先画事务边界；区分单库事务与跨服务流程。

### Q81 隔离级别与异常

**口述：**读未提交、读已提交、可重复读、串行化提供不同可见性与并发约束。脏读是读到未提交数据，不可重复读是同一行重复读取变化，幻读是符合谓词的行集合变化。

**机制/边界：**实际实现不能只靠统一表格判断：InnoDB RR 的快照读与锁定读不同，next-key锁可保护某些范围；快照隔离仍可能出现写偏差，串行化通常需要更多检测/锁并可能失败重试。

**追问/验证：**设计双会话交错步骤，把BEGIN、读、写、COMMIT排成时间线；注明引擎、隔离级别与查询类型。

### Q82 MVCC Read View

**口述：**InnoDB 借助记录版本信息、undo版本链和 Read View 判断快照读可见版本。判断要考虑创建快照时的活跃事务集合、事务ID边界和本事务修改，而非只比较“比当前ID小”。

**机制/边界：**RC 通常每次一致性读使用新快照，RR 通常复用事务中的一致性读快照；长事务会阻碍旧版本清理。PostgreSQL 使用自己的元组可见性和事务状态规则，不能直接复述 InnoDB 链结构。

**追问/验证：**同一事务内第二次查询何时看到新提交？先问隔离级别、快照建立时机以及是否锁定读。

### Q83 当前读与快照读

**口述：**普通一致性 SELECT 倾向读取快照版本；SELECT FOR UPDATE、UPDATE 等锁定/修改操作按当前状态检查并加相应锁。MVCC 减少读写冲突，但不意味着更新操作无需锁。

**机制/边界：**一个事务混用快照读和锁定读时，观察结果可能来自不同可见性时点；隔离行为必须结合语句。锁通常在事务结束时释放，别在事务内等待用户输入。

**追问/验证：**两个会话更新同一行，观察等待与版本；用业务不变量解释为什么纯读快照不能防止所有并发写冲突。

### Q84 行锁 间隙锁 临键锁 意向锁

**口述：**记录锁保护索引记录；间隙锁保护键之间区间，限制插入；next-key 是记录与前方间隙组合；意向锁表明事务打算在较细粒度加锁，辅助多粒度兼容判断。

**机制/边界：**实际锁范围取决于访问索引、谓词、隔离级别和唯一性等。行锁不意味着“无索引时自动升级成真正的表锁”，但扫描/锁住大量记录会呈现大范围阻塞。

**追问/验证：**把等值唯一键、非唯一范围、未命中搜索分开画区间；查看锁等待视图验证，不仅从 SQL 字面猜。

### Q85 数据库死锁与重试

**口述：**事务互相持锁等待形成环，数据库检测后可选择事务回滚，应用重试完整业务事务。固定访问顺序、缩短事务和合适索引降低概率。

**机制/边界：**超时和死锁是不同错误原因，回滚语义可能不同。重试要有上限、退避及幂等，外部副作用不应因事务重试重复执行。

**追问/验证：**保存死锁报告，标出两个事务各持有哪些锁、下一步申请什么；将同样并发顺序作为回归场景。

### Q86 redo undo binlog

**口述：**redo 支持崩溃后重做已记录变更，undo 支持回滚和旧版本，binlog 记录逻辑变更用于复制与恢复链。WAL 要求相应日志先于依赖它的数据页持久化。

**机制/边界：**InnoDB 与 binlog 的协调常通过内部两阶段提交解释 prepare、binlog 和 commit，真实刷盘时点受配置、组提交与版本影响。不要把内部2PC等同于完整分布式事务，也不要把教学 REDO/UNDO 宣称为完整 ARIES。

**追问/验证：**故障发生在各阶段时日志如何判断事务？持久化配置放松后损失窗口是什么？区分进程崩溃与机器断电。

### Q87 大事务的影响

**口述：**大事务延长持锁、增加 undo/redo 和回滚成本，可能使旧版本滞留、复制延迟与恢复时间增长。大量行不只是“SQL执行稍慢”。

**机制/边界：**拆批会改变原子性与中间可见状态，需游标/任务检查点和幂等；不是所有业务都可任意拆。长只读事务也可能拖住版本清理。

**追问/验证：**看事务年龄、日志增长、锁等待与复制 lag；对批量任务明确断点重跑和终态验证。

### Q88 深分页 批量写 N+1

**口述：**深 OFFSET 可能扫描并丢弃大量行；稳定复合排序键支持 seek分页。批量写减少往返与提交开销，但批次过大会形成大事务。N+1 把一次集合查询变成每行一次额外请求，RTT 和查询开销叠加。

**机制/边界：**seek分页需要唯一确定的排序，如(created_at,id)，不擅长随机跳任意页；JOIN/批量取值减少N+1时也要控制结果膨胀与内存。

**追问/验证：**不只比较单条查询耗时，还比较总 SQL 数、往返、扫描行、结果大小和事务边界。

## Redis 与一致性 Q89–Q95

### Q89 Redis 类型选型

**口述：**string适合值/计数器，hash适合字段对象，list适合序列，set用于去重集合，zset用于带分数排序，stream支持带ID的消息流。按操作需求而非名字选型。

**机制/边界：**类型不是固定一种内部编码，小对象与大对象可用不同表示；数据类型、操作复杂度、内存与网络返回规模一起考虑。Redis list当队列不自动具备可靠投递语义。

**追问/验证：**排行榜需要按分数排序且处理同分，zset合适；大范围扫描/返回会阻塞或占带宽，应分页并限制大小。

### Q90 单线程与并发问题

**口述：**典型Redis核心命令按事件循环顺序执行，但网络I/O、持久化等可能涉及其它线程/进程，模块和版本也有扩展。多个客户端的多条命令仍会交错，GET后SET不是业务原子操作。

**机制/边界：**优先使用 INCR 等原子命令。需要先读再根据结果写时，可使用 WATCH 配合 MULTI/EXEC 做乐观并发校验并在冲突后重试，或使用 Lua 在服务端完成判断和修改。MULTI/EXEC 保证执行期间不插入其他客户端命令，但执行阶段某条命令报错不会回滚此前成功命令；Lua 运行时出错同样不会自动撤销先前写入。原子执行、事务回滚和持久性是不同保证。Lua 执行过久、慢命令、big key 和超大返回都会拉高尾延迟。

**追问/验证：**解释为何单线程仍有分布式锁和复合竞争；看SLOWLOG、延迟及CPU，而不只问线程数。

### Q91 RDB AOF 重写与切换

**口述：**RDB保存时间点快照，恢复可较直接但两次快照间存在丢失窗口；AOF记录写操作，其持久化策略影响丢失与I/O开销；重写压缩历史。主从复制与持久化是不同机制。

**机制/边界：**fork/COW可能增加内存，异步复制切换也可能丢失刚确认的写。现代AOF格式和混合持久化依版本；“开AOF就绝不丢数据”过度承诺。

**追问/验证：**先声明RPO/RTO，再选策略，模拟进程崩溃与节点失效时区分确认数据和持久数据。

### Q92 过期与淘汰

**口述：**过期按TTL使数据失效，淘汰在达到内存约束时按策略释放键。主动/惰性删除与LRU/LFU等淘汰不是同一机制。

**机制/边界：**noeviction可能导致写入报错；volatile类策略只针对带过期键。过期时间相同的大量热点可能引发集中回源。

**追问/验证：**观察内存、evicted/expired计数、命中率与回源量；过期抖动减少同时失效，但不保证一致性。

### Q93 穿透 击穿 雪崩

**口述：**穿透是查询本不存在数据持续打到数据库；击穿是热点失效后并发回源；雪崩是大批键或缓存整体失效。分别考虑空值/布隆过滤器、请求合并/重建互斥、过期打散和限流降级。

**机制/边界：**空值缓存会延迟新数据可见；布隆过滤器有误判，构建/更新不同步也可影响业务；逻辑过期返回旧值，需要业务接受陈旧。

**追问/验证：**不仅保证缓存平时命中，还验证缓存全不可用时数据库能承受多少回源。

### Q94 缓存与数据库一致性

**口述：**常见cache-aside先写数据库再失效缓存，读时未命中查库并填充。仍存在并发旧读回填、删除失败和消息延迟，需要TTL、可靠失效通知、版本校验等收敛手段。

**机制/边界：**延迟双删不是严格一致证明，延迟时间无法覆盖所有调度；CDC/outbox也要处理重复、乱序和失败。强一致要求可能意味着读主库或更严格协调，增加延迟与复杂度。

**追问/验证：**画“旧读开始→新写提交→删除缓存→旧读回填”的交错，明确陈旧窗口、监测和修复，不只写一句最终一致。

### Q95 分布式锁

**口述：**获取可用SET key token NX PX lease表达，释放时原子比较token后删除，避免删掉别人重建的锁。租约到期后原持有者可能仍在执行，因此仅有唯一token不足以保护资源。

**机制/边界：**暂停、网络隔离和异步主从切换都可能造成多个自认为持锁者；续租也有失败窗口。需要下游真正检查单调fencing token或采用更符合一致性要求的协调机制；fencing计数自身也要有可靠单调性。

**追问/验证：**构造A暂停超过租约、B获得锁、A恢复写入的时间线；说明由哪个资源拒绝A的过期写，而不是只说“加watchdog”。

## 联合索引推演与参考

示例查询与数据均为练习，不是已有线上规模：表orders(id,user_id,status,created_at,total)，要查某用户最近20条已支付订单，可评估(user_id,status,created_at,id)；created_at同值时用id保持稳定顺序。是否将total纳入覆盖取决于读收益、索引大小与写放大。

测试路径：记录DDL/样本分布 → EXPLAIN → 在测试数据上实际执行 → 比较扫描、回表、排序与耗时 → 变换高/低频用户和边界时间。不要在未知生产环境直接执行有副作用的EXPLAIN ANALYZE或压测。
