两项目项目边界与面试提纲

【总原则】
主简历只讲 RMDB 和 ITMS-BD。RMDB 是 C++/数据库底层主项目，ITMS-BD 是 Java 后端、服务集成和 Redis 实践项目。职责分成：主责/已完成，参与/协作，理解/范围外。

【RMDB：主责】
业务：数据库课程教学系统，目标是理解页、记录、查询、索引、事务和恢复的协作。
可认领：教师框架上的题目 1-11 学生实现；页与缓冲池；定长记录与扫描；查询执行；BIGINT/DATETIME；功能型唯一索引；聚合、排序、LIMIT、BNLJ；事务提交回滚；锁与 no-wait；基础 WAL REDO/UNDO。
证据关键词：page table、frame、pin、dirty、LRU、bitmap、slot、RID、Parser、Analyze、Planner、Executor、IndexScan、写集、锁兼容、日志顺序。
范围外：教师骨架、第三方库、lex.yy/yacc.tab 生成文件、完整代价优化器、完整磁盘 B+ 树、完整 ARIES、没有来源的性能数字、后续维护提交。
必须说清：当前索引主要是进程内有序条目并从基表重建；恢复是基础物理日志 REDO/UNDO，不是完整 ARIES。

RMDB 30 秒：
RMDB 是我的数据库课程项目。我在教师框架上独立完成题目 1-11，重点实现页和缓冲池、定长记录、查询执行、功能型索引，以及事务锁和基础 WAL 恢复。面试中我可以展开一次 UPDATE 如何同时维护记录、索引、写集和回滚。项目定位是教学数据库，索引和恢复都采用简化实现。

RMDB 3 分钟顺序：背景边界 -> SQL 到执行器 -> pin/dirty/LRU 和记录页 -> UPDATE/ABORT 的锁、索引、写集、日志 -> 取舍和测试证据 -> 简化索引/基础恢复限制。

RMDB 追问：
1. page 与 frame 区别？
2. pin 页面为什么不能被 LRU 淘汰？
3. 脏页什么时候写回？
4. UPDATE 为什么先收集 RID？
5. 复合索引如何按列顺序拼 key？
6. BNLJ 如何减少右表重复扫描？
7. no-wait 如何避免死锁？代价？
8. REDO 为什么正序、UNDO 为什么逆序？
9. 当前实现与 B+ 树、ARIES 有什么差别？

【ITMS-BD：主责】
业务：智能交通演示后端，提供认证、交通查询、数据保存和前后端联调能力。
可认领：Docker Compose 联调环境排障；Redis 连接配置；JWT 登出撤销；登录失败计数；实时交通查询短 TTL 缓存；Swagger、日志、SQL 和容器状态定位问题。
Redis Key：itms:auth:revoked:{sha256(token)}，TTL 为 JWT 剩余有效期；itms:auth:login-failed:{sha256(username)}，首次错误后 600 秒；itms:traffic:realtime，5 秒；itms:traffic:intersection-summary，5 秒。
参与/协作：PostgreSQL 模型、服务边界、REST 契约、既有认证流程、交通数据/Kafka/模拟器联调、前端契约对齐。
范围外：React 页面、Kafka 内部实现、预测/信号算法、真实设备、生产 QPS、Redis Stream、Redisson 锁、Lua 多维限流。后面三项属于 InterviewGuide 或独立练习，不是当前 ITMS 业务调用。
Compose 实际六服务：PostgreSQL、Redis、ZooKeeper、Kafka、backend、frontend。简历中的“五服务”应改成“六服务”或“多服务”。

ITMS 认证链路：Bearer Token -> Security Filter 验签/过期 -> Redis EXISTS 摘要 Key -> SecurityContext -> Controller/Service/Repository。
ITMS 登出链路：Controller -> AuthService -> JwtUtil 计算剩余时间 -> Redis SET 撤销 Key + PX。
ITMS 缓存链路：Redis GET -> 命中返回；miss -> PostgreSQL -> JSON SET EX 5 -> 返回；写交通数据 -> Repository.save -> 告警 upsert -> 删除两个缓存 Key。

ITMS 30 秒：
ITMS-BD 是我的 Java 后端与服务集成项目。我参与 PostgreSQL 数据模型、REST 契约和前后端联调，负责 Docker Compose 多服务环境排障，并补充 Redis 认证与缓存模块：用 Token 摘要和剩余 TTL 实现 JWT 登出撤销，用 INCR 记录登录失败次数，用 5 秒 Cache-Aside 缓存实时交通查询。这里我可以继续展开缓存失效竞态和 Redis 故障边界。

ITMS 3 分钟顺序：业务 -> 职责边界 -> JWT 黑名单 -> 交通缓存 -> 选型代价 -> 缺口和证据。

ITMS 必须承认的缺口：
1. 失败五次当前只改变提示，正确密码仍可登录；完整封禁尚待实现。
2. INCR 和 EXPIRE 是两条命令，首次计数存在 TTL 窗口；可用 Lua 合并。
3. revokeToken 捕获范围包含 Redis SET，写入异常会被吞；过滤器 EXISTS 没有统一降级。
4. 读旧值、更新删除、旧值回填存在并发竞态。
5. 保存、告警和缓存删除没有整体事务；批量保存逐条处理。
6. 当前 mvn clean test 只有 No tests to run；Docker 引擎未启动，40 项 Redis 运行脚本尚未得到运行结果。

【统一回答口径】
有源码、配置、测试或本次修改证据的内容用“我负责/我实现”；合作模块用“我参与/我联调”；只有理解的内容用“我能解释调用链，但不是我的实现”。数字必须带来源、环境、数据量、并发模型、时长和限制。Redis 的 Redis 7、AOF、5 秒、600 秒、24 小时是配置事实，不是性能指标。

5. 混合面试：每次先说当前实现，再说限制和改进。
