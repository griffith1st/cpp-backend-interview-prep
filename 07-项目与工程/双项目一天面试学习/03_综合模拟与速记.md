# 双项目综合模拟与面试速记

先学两个项目的知识点卡片，再用本章练脱稿回答。本章所有“假设”均是面试推演，不代表项目发生过相同事故；主问题与追问均附答案。源码细节以项目章节和证据边界为准。

## 两段项目介绍

### RMDB 三十秒

> RMDB 是我基于教学框架完成的数据库课程项目。我完成了题目 1–11 的学生实现，把页和缓冲池、定长记录、SQL 执行、索引、事务锁和基础日志恢复串起来。比较适合展开的是一次 UPDATE 如何影响记录和索引，以及冲突后怎样回滚。当前实现有教学简化，我会区分已实现功能与完整生产数据库的能力。

### RMDB 两分钟

> 这个项目的目标是把数据库从接收 SQL 到操作页文件的过程实际串通。我是在教学框架上完成题目 1–11 的学生实现。存储层包括磁盘页、缓冲池和定长记录：缓冲池维护磁盘页到内存 frame 的映射，用 pin 表示页面仍在使用，用 dirty 表示需要写回，用 LRU 选择可淘汰页面。
>
> 执行层从语法解析、语义检查和计划生成，转换成执行器完成扫描、投影和 DML。我扩展了 BIGINT、DATETIME、聚合、排序、LIMIT 和 BNLJ，并支持索引扫描。索引相关的重点是唯一约束与插入、更新、删除时的同步。当前主体是简化的有序条目模型，不能包装成完整磁盘 B+ 树。
>
> 事务方面有提交、回滚、表级锁和 no-wait 冲突处理，以及基础物理日志的 redo/undo。这里我会特别区分正常功能路径与崩溃保证：有日志不代表所有写入时序已经满足严格 WAL，有恢复脚本也不代表完整 ARIES 或所有崩溃窗口已验证。
>
> 面试中我可以用缓冲池淘汰、一次 UPDATE 和两事务冲突三个例子展开。简历中提到的测试，我会结合确实保留的命令和结果说明，不报没有依据的性能数字。

### ITMS 三十秒

> 智能交通项目中，我主要负责本地 Compose 联调环境和 Redis 相关能力，参与数据模型、REST API 与认证链路梳理。具体包括 JWT 登出黑名单、登录失败计数和五秒交通查询缓存。我能展开缓存命中与回源、写库后失效、Token 摘要和剩余 TTL，以及中间件连接问题的定位。

### ITMS 两分钟

> ITMS-BD 是智能交通管理系统的后端与集成实践。我参与 PostgreSQL 数据模型、REST API、认证和前后端联调范围的梳理，主责是本地 Docker Compose 环境和 Redis 能力。环境围绕 PostgreSQL、Redis、Kafka、后端和前端五类服务，当前配置还包含 ZooKeeper，所以按 Compose service 条目数是六个，面试时要把统计口径说清楚。
>
> Redis 主要有三个用途。第一是 JWT 登出撤销：JWT 本身到期前仍可能通过验签，所以把 Token 的摘要写入黑名单，TTL 使用剩余有效期，请求通过验签和过期检查后还要检查撤销状态。第二是登录失败计数：按用户维度累加，设置短期窗口，成功后清理；当前阈值影响提示，不应说已经实现完整锁号策略。第三是交通查询五秒缓存，命中时返回缓存，未命中查 PostgreSQL 并回填。正常保存流程在写库和告警处理后尝试删除两个缓存；中间异常可能阻断失效。
>
> 这套实现需要讲清边界：数据库与 Redis 操作不是一个原子事务，写后删除仍有旧值回填窗口；交通缓存异常回源数据库不等于 JWT 黑名单也可以同样降级。我在排障时从请求状态、后端日志、Profile、连接地址、容器状态和数据库结果交叉定位。Kafka 和前端可以说明接口与联调边界，不把整套实现归为个人成果。

## 第一轮模拟 RMDB 二十五分钟

使用方法：每个主问题 60–90 秒，两次追问各 30–60 秒，其余时间做状态推演。先遮住答案，答完再评分。

### M01 从一条 SQL 讲执行链路

**锚点：** SQL 解析、语义分析、计划生成、执行器。

**主问：** `SELECT id FROM t WHERE id > 10 ORDER BY id LIMIT 2` 经历哪些阶段？

**答案：** Parser 确认语法并生成语法结构；Analyze 核对表、列、类型及条件；Planner 组织扫描、条件、排序、LIMIT 和投影等计划；Portal 将计划转换成执行器。扫描获得记录，过滤后排序并限制输出，最后返回 id。这里说明逻辑关系，不假定每个算子在当前实现都严格对应一个独立节点；实际组合看计划转换代码。

**追问一：** 有索引就一定选它吗？

**答：** 需要看当前索引选择规则和条件能否利用它。索引存在不代表条件匹配，更不能从当前基础选择推断有完整代价优化器。通用原理上还要考虑选择率与回表成本，但不能说本项目已经统计并比较这些代价。

**追问二：** LIMIT 2 能不能先取任意两条再排序？

**答：** 一般不能，结果可能不是全体符合条件数据中的前两条。若有能够保证相应顺序的访问路径，才可能提前停止；不能凭存在索引就假定实现进行了这种优化。

### M02 缓冲池为什么不能简单删掉最久未用的一页

**锚点：** 磁盘页、缓冲池。

**主问：** 两个 frame 中 A 的 pin 为 1，B 的 pin 为 0 且 dirty，取新页 C 怎么办？

**答案：** A 正在被使用，不能淘汰。B 可以成为候选；复用前需要将其脏内容写回对应磁盘页，移除 B 的旧映射，加载 C，建立 C 到 frame 的新映射，初始化 pin 和 dirty 状态。写回失败时不能继续覆盖 B，否则丢失修改。该过程是机制推演，具体失败分支要对照当前代码。

**追问一：** 如果两页都 pin 住？

**答：** 没有可淘汰 frame，获取新页应失败或由上层处理，不能强制复用。先查是否有遗漏 unpin，也可能确实需要更多 frame；不能直接判定是缓存太小。

**追问二：** dirty 和 pin 有什么关系？

**答：** 两个状态独立。pin 表示是否正在使用，dirty 表示内容是否较磁盘更新。只读页也能被 pin，已修改但已释放的页可同时 dirty 且 pin 为零。

### M03 UPDATE 为什么是索引一致性高风险点

**锚点：** 维护插入、更新、删除后的索引一致性。

**主问：** 有唯一索引时，把键 7 改成已经存在的 9，应当怎样处理？

**答案：** 应拒绝违反唯一约束的更新，并使记录和相关索引保持原状态。一个完整思路是验证新键、保存旧值，再一致地完成基表及所有索引修改，并为失败准备补偿。当前代码可见逐索引操作与局部补偿，因此尤其不能把多索引中途失败的完整原子性当作已证实能力。

**追问一：** 只回滚记录够吗？

**答：** 不够。索引中已写入的新键、已删除的旧键都需要恢复。否则索引查询与全表扫描会得到不一致的结果。

**追问二：** 如何验证多个索引时的错误窗口？

**答：** 设计两个唯一索引，让第一个新键不冲突，第二个新键冲突；执行更新后分别检查基表、按两个索引的查询和再次插入行为。预期是整体不变，这是待执行的验证方案，不写成已通过测试。

### M04 no-wait 为什么能避开死锁等待环

**锚点：** 表级锁、no-wait 并发控制。

**主问：** T1 持有表 A 的写锁，T2 也要写 A，会发生什么？

**答案：** 不兼容的锁请求不会进入长期等待，而是立即失败并触发冲突事务中止。这样不形成等待其他事务释放锁的环，所以省掉等待图检测路径。代价是热点冲突下回滚和重试增多，需要上层重试策略，并不自动公平。

**追问一：** 表里两行不同，为什么还可能冲突？

**答：** 如果实际 DML 路径使用表级排他锁，冲突粒度就是整张表；记录锁接口存在也不能证明业务已用它允许两行并发写。

**追问二：** 一冲突就无限立刻重试可以吗？

**答：** 可能形成持续碰撞和资源消耗。改进可以使用有上限的重试、退避与抖动；这是上层策略设想，不能说 no-wait 自带这些机制。

### M05 有 redo 和 undo 就是完整 WAL 吗

**锚点：** WAL 物理日志 redo/undo。

**主问：** redo、undo 各解决什么问题，WAL 额外要求什么？

**答案：** redo 用于重放应保留的修改，undo 用于撤销不应保留的修改。WAL 还要求对应日志先于数据页持久化，以及在确认提交前满足提交日志的持久化要求。当前项目是基础物理日志恢复，需要检查写日志、刷页、解锁和提交返回的真实顺序，不能仅凭日志文件存在就保证所有崩溃点正确。

**追问一：** 一个事务把值从 10 改到 20，再改到 30，怎么撤销？

**答：** 从后往前，用第二次修改的旧值恢复到 20，再用第一次的旧值恢复到 10。若正序撤销，最终可能停在 20。

**追问二：** 进程崩溃测试能证明断电恢复吗？

**答：** 不能等同。进程退出后操作系统缓存可能还在；主机断电会涉及缓存与存储持久化。需要检查 fsync 等持久化语义及故障模型，测试结论只覆盖实际注入的故障。

## 第二轮模拟 ITMS 二十五分钟

### M06 JWT 没有服务端 Session 为何还需要 Redis

**锚点：** JWT 登出黑名单。

**主问：** 用户删除浏览器 Token 后，服务端为什么还要做撤销？

**答案：** 删除客户端副本不会使已经泄露或保存的 Token 失效。JWT 在签名和时间有效时仍可能通过验证，因此服务端需要额外的撤销状态。当前用 Token 摘要作为黑名单键，受保护请求验签与检查过期后再查撤销状态。

**追问一：** 原来有效 24 小时，使用了 23 小时才退出，还缓存 24 小时吗？

**答：** 只需剩余约 1 小时，实际按过期时刻减当前时刻计算并处理毫秒单位和非正值。过期后 JWT 自身校验已可拒绝，无需继续保存撤销键。

**追问二：** SHA-256 摘要是不是加密 Token？

**答：** 不是可逆加密，是摘要。它避免直接将原 Token 放进 Redis key，并产生固定长度键；它不能替代 JWT 签名校验，也不能让泄露 Token 重新安全。

### M07 Redis 的 INCR 原子是否意味着整套计数逻辑原子

**锚点：** 登录失败计数。

**主问：** 先 INCR，首次再 EXPIRE，有什么窗口？

**答案：** 单条 INCR 是原子的，但它与后续 EXPIRE 不是一个原子整体。首次计数成功后进程失败，键可能没有 TTL。应检查 TTL 缺失情形；完善时可将计数与必要的过期设置放入一段原子脚本，但当前实现不能说已经使用 Lua。

**追问一：** 每次失败都刷新 TTL 与只在第一次设置有什么差别？

**答：** 第一次设置是从首次失败起算的一段窗口；每次刷新会把过期点向后延长。它也不能直接等价为维护全部请求时间戳的精确滑动窗口。

**追问二：** 达到五次是否代表十分钟不能登录？

**答：** 当前源码阈值改变提示，没有完整的后续登录拒绝分支，不能称为完整锁号。若要实现锁定，应明确校验位置、解除条件、成功登录语义和误伤处理。

### M08 写库后删缓存为什么仍能读到旧数据

**锚点：** Cache-Aside、写库后失效、五秒缓存。

**主问：** 用两个请求解释一次旧值回填。

**答案：** 读请求 A 缓存未命中，从数据库读到旧值 v1，暂未回填；写请求 B 将数据库改成 v2 并删除缓存；A 恢复执行后把 v1 写回缓存。这时数据库新、缓存旧。写后删除减少直接更新缓存的复杂性，但不提供数据库与 Redis 的强一致事务。

**追问一：** 五秒 TTL 保证写入后最多陈旧五秒吗？

**答：** TTL 是从某次缓存写入开始计算。若旧读请求延迟后才回填，陈旧窗口应从该回填时刻计，不能无条件从数据库提交时刻计五秒。当前汇总缓存还可能由实时缓存构建，再获得自己的五秒 TTL，因此单个 Key 的 TTL 也不能当作端到端的新鲜度上限。

**追问二：** 延迟双删能否绝对解决？

**答：** 不能，固定延迟难覆盖所有交错，还存在第二次删除失败。可作为降低概率的改进之一；更严格需求需考虑版本校验、提交后事件、重试补偿及读写协调，并说明成本与当前未实现边界。

### M09 Redis 不可用为何不能全都回源 PostgreSQL

**锚点：** 交通缓存异常回退 PostgreSQL、JWT 撤销。

**主问：** 交通缓存读取失败与黑名单检查失败可以相同处理吗？

**答案：** 交通数据在 PostgreSQL 有权威来源，绕过缓存可以重新查询。JWT 撤销状态如果只存在 Redis，数据库并没有等价黑名单记录，回源 PostgreSQL 不能凭空恢复撤销信息。当前交通 Service 的缓存有捕获异常的回源路径，但携带有效 Token 的请求可能先在过滤器的 Redis 黑名单查询处失败，根本到不了 Service。所以只能说业务缓存这一层可回源，不能保证 Redis 宕机时整个交通接口仍可用。

**追问一：** 当前登出接口返回成功，能否证明黑名单写入成功？

**答：** 不能直接证明。当前登出服务将 Token 解析和 Redis SET 放在会捕获运行时异常的路径里，SET 失败可能没有正确反馈。入口黑名单 EXISTS 查询又可能先失败，所以也不能说 Redis 宕机时登出必定返回成功。应区分 HTTP 成功、业务处理完成和撤销状态已保存，进一步看日志与重放原 Token 的结果。

**追问二：** 缓存降级会产生新的压力吗？

**答：** 会，原本被缓存吸收的读请求会落到数据库，延迟和连接池占用可能上升。改进应先量测错误率、数据库负载及回源量，再评估限流、隔离或降级响应；不虚构当前生产流量。

### M10 容器都起来了接口为什么还不通

**锚点：** Compose 环境、初始化、Profile、中间件连接问题。

**主问：** 后端容器内连 `localhost:6379` 失败，怎样判断？

**答案：** 容器的 localhost 指它自身，Redis 位于另一个容器时应使用同一 Compose 网络下的服务名与容器端口，例如 redis 和 6379。先查最终生效的 Profile 与环境配置，再查容器状态、日志、网络和服务就绪，区分地址错误、端口未监听、认证错误与初始化失败。

**追问一：** depends_on 表示数据库已经可用吗？

**答：** 普通依赖通常只保证启动顺序；是否等到健康要看 healthcheck 与依赖条件。即使启动时健康，后续也会失败，应用仍需合理超时和错误处理。

**追问二：** Kafka 端口能连通但客户端仍报 broker 连接失败？

**答：** 客户端连接 bootstrap 后还会获取 broker 地址。如果 advertised listeners 返回的地址在客户端所处网络不可达，仍会失败。当前职责可以回答环境地址与联调定位，不能由此引申为自己实现了 Kafka 内部机制。

## 两项目对照 只背容易混淆的概念

| 容易混淆 | RMDB | ITMS |
| --- | --- | --- |
| 缓存中的修改 | dirty 页可能承载尚未写回的数据，不能任意丢弃 | 交通查询缓存是可从 PostgreSQL 重建的副本 |
| 不能丢的 Redis 数据 | 不适用 | JWT 撤销状态不是交通数据副本，丢失会改变认证语义 |
| 原子性的范围 | 需要核对记录、所有索引、写集、日志和失败补偿 | INCR 单命令原子不等于 INCR 加 EXPIRE 整体原子 |
| 持久化 | redo/undo 与真正持久化时序要分别验证 | Redis 有 AOF 配置也不能推断每次撤销写入都已安全落盘 |
| 降级与正确性 | 全 pin 时不能强行淘汰正在使用的页 | 黑名单不可读不能按普通缓存 miss 理解 |
| 数据库索引 | 当前 RMDB 主体是简化有序条目 | PostgreSQL 的索引原理不能当作 RMDB 当前实现细节 |
| 并发改进 | 细粒度锁、重试退避属于待评估改进 | Lua、版本化缓存、提交后失效属于待评估改进 |

## 证据不足时怎样回答

**问：你到底做了哪些？**

答：先重复当前简历的职责，再选择一个可定位的纵向功能说明输入、修改点和输出。仓库里存在的功能不自动算个人贡献；对框架、协作和后续维护分别表述。RMDB 可聚焦课程任务，ITMS 可聚焦 Redis 与联调。

**问：提高了多少性能？**

答：目前没有可核对的性能测量数据，所以不报百分比。我能解释减少数据库读取或减少重复扫描的机制；如果量测，会固定数据量和并发，比较基线与改动后的响应时间、吞吐和错误率，保留命令与原始数据。

**问：最难的问题是什么？**

答：从确实经历过的问题选一个，按“现象—排查证据—原因—修复—验证—剩余限制”讲。可练的技术主题是多索引失败一致性、缓存旧值回填、容器连接；如果只是这次读源码发现，应明确说是复盘发现，不能讲成当时处理过的事故。

**问：你简历写了支持 WAL，为什么现在又说有缺口？**

答：这里的功能范围是基础物理日志和 redo/undo 恢复流程。严格 WAL 还取决于日志与数据页持久化的顺序；当前静态核查暴露了需要进一步验证的窗口。我可以讲清已经完成的机制与未证明的保证，不把课程功能等同生产级正确性。

## 面试前最后十分钟

先口述两段三十秒介绍，再各画一条链路。RMDB 记住 page/frame、pin/dirty、RID、执行器、基表与索引、no-wait、逆序 undo 和 WAL 时序。ITMS 记住容器地址、JWT 验签与撤销、摘要与剩余 TTL、计数两命令窗口、Cache-Aside 旧值回填、交通与认证故障边界。

最后检查四种禁用表达：没有实测却说“性能提升”；有接口就说“全部实现”；有脚本就说“所有测试通过”；有缓存与日志就说“强一致或绝不丢数据”。把这些替换为当前机制、具体证据和限制即可。
