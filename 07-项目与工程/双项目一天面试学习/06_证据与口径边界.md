## ITMS 面试必须讲准的十点

| 容易说过头的表述 | 当前可支持的说法 | 直接相关追问 |
| --- | --- | --- |
| 五服务就是五个容器 | 五类主要组件之外还有 ZooKeeper，当前 Compose 有六个启用 service 条目 | 分类口径与配置条目数的区别 |
| 整体架构和算法都由我设计 | 主责 Redis 与本地联调，参与模型、REST 契约与认证整理 | 选一个纵向链路证明理解 |
| JWT 验签通过就是允许访问 | 还需检查过期、撤销及实际授权规则 | role claim 与真正角色权限是否接通 |
| Token 摘要就是加密 | SHA-256 是摘要，用于固定长度黑名单键 | 不能替代签名校验或令牌保密 |
| 退出成功说明撤销一定成功 | 登出服务存在吞运行时异常的边界；入口 Redis 查询又可能先失败 | 重放旧 Token 与检查撤销键，分别验证接口和状态 |
| 失败五次就锁定十分钟 | 计数阈值改变提示；没有完整登录前锁定判断 | 成功密码路径仍可继续、计数清除逻辑 |
| INCR 原子所以计数与过期原子 | INCR 和首次 EXPIRE 分离，中间失败可能留下无 TTL 的键 | Lua 原子脚本仅作为改进方案 |
| 五秒 TTL 等于数据最多旧五秒 | 单 Key 从最近写入开始计时；旧值延迟回填、两层缓存会延长端到端陈旧窗口 | 实时缓存构建汇总缓存时是否重新计算 TTL |
| 写库后失效就保证强一致 | 数据库和 Redis 操作不在同一原子事务，存在并发与删除失败窗口 | 加 Service 事务后还需考虑提交后失效 |
| Redis 故障接口全部回 PostgreSQL | 交通 Service 缓存异常有回源逻辑；认证黑名单查询可在入口失败 | 缓存层可降级不等于端到端请求可用 |

认证状态和业务缓存的差别是最高优先级。数据库可以重新查交通记录，却不能自动还原只保存在 Redis 中的撤销状态。公开路由配置也不必然跳过自定义认证过滤器，不能用 permitAll 推断完全没有 Redis 依赖。
