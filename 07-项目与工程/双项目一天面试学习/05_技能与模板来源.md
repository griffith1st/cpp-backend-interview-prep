## 2. 已读技能的适用性与取舍

### 2.1 Java 后端出题技能：仅使用递进方法

## 3. 事实来源优先级

| 等级 | 可用来源 | 可以支持什么 | 不能据此推出什么 |
| --- | --- | --- | --- |
| R：简历明确 | 用户指定的当前 DOCX | 应准备的项目、职责、技术锚点 | 某目录所有模块都由本人编写 |
| C：代码核实 | 对应仓库、版本、具体函数/配置 | 当前实现行为、参数、调用关系、限制 | 本人写过全部代码；代码一定已成功运行 |
| H：历史记录 | 已有笔记、旧对话、旧测试记录 | 帮助定位仓库和先前结论；提供待核对线索 | 历史成绩即当前验证；旧分工即当前简历事实 |
| G：一般原理 | 官方文档、教材、通用推理 | 解释机制与直接相关的边界题 | 本项目实现了该机制或已发生该事故 |

冲突处理：以当前简历确定学习范围，以当前源码校正实现行为；旧笔记的分工、性能、故障故事不能自动抄成第一人称答案。若当前简历用词宽于代码，应给出诚实、能承受追问的边界表述，不能用标准数据库/后端架构填补缺口。

特别有价值的历史来源是 [项目边界-RMDB-ITMS-最终版.md](/E:/BaiduNetdiskDownload/Anything/cpp-backend-interview-prep/07-项目与工程/项目边界-RMDB-ITMS-最终版.md)，文件标注更新时间为 2026-09-13。它记录了 RMDB 简化索引/恢复边界以及 ITMS Redis、联调、协作范围，适合用作源码核查清单。它仍属于历史笔记，不能单独认定个人贡献。

## 4. 每个知识点的统一学习卡

以下模板用于主知识点；不要求每道很小的追问重复所有字段。

```markdown
## R/IT-编号｜知识点名称｜P0/P1/P2

**简历锚点：** 当前简历中的对应短语。

**事实等级：** R/C/H/G；源码证据写文件与函数；未核实处明确标记。

**职责边界：** 本人实现 / 参与联调 / 框架已有 / 原理理解 / 待核对。

**学会标准：** 一句可检测的目标，例如“能说出 pin、dirty 与淘汰的关系”。

**先修：** 最多 1～2 个前置知识点 ID。

### 先学机制
1. 这个问题为什么出现。
2. 输入、关键状态变化、输出。
3. 必须保持的不变量。
4. 一个小例子或状态推演。
5. 当前实现的限制。

### 主问题
面试官会怎样问？

**60～90 秒口述答案：** 结论 → 当前机制 → 一个例子/证据 → 边界。

**展开答案：** 解释关键术语、步骤和因果；只写已核实的项目行为。

### 追问链
1. 使用/原理追问；参考答案。
2. 边界/失败追问；参考答案。
3. 取舍/验证追问；参考答案。

**容易说错：** 1～3 条；给出修正说法。

**最小自测：** 遮住答案，给定输入，推导输出/状态/失败点。

**掌握度：** 初测 __/3；复测 __/3；下次只补 __。

**证据落点：** 可核实文件/函数/配置/历史测试；没有证据时写“待核对”。
```

优先让学习者理解机制，再看到问答。只罗列“题目 + 长答案”容易形成背诵，无法适应换一种问法。

## 5. 追问生成规则

### 5.1 固定递进链

1. **讲使用：** 这个知识点解决什么问题，简历里对应哪项工作？
2. **讲机制：** 输入经过哪些状态变化；哪个不变量保证正确？
3. **做推演：** 给一个小输入、并发交错或失败时刻，结果会怎样？
4. **讲取舍：** 当前方案为什么够用，付出什么代价？
5. **讲验证：** 什么测试/日志能证明判断；什么证据能推翻判断？

同一主问题默认 2～3 个有效追问。核心薄弱点可加到 4～5 个；掌握度已达标的知识点不靠堆量继续扩张。

### 5.2 从回答触发下一问

| 回答出现的信号 | 下一问 | 回答应补出的信息 |
| --- | --- | --- |
| “我们实现了” | 你负责的输入、输出与改动是什么？ | 个人贡献、协作接口、证据 |
| “性能更好” | 对比基线、负载、测量口径是什么？ | 已有实测；无实测则说明理论预期 |
| “保证一致性” | 在两步之间失败会怎样？ | 原子边界、失败窗口、补偿或限制 |
| “使用某技术” | 当前代码在哪个分支使用它？ | 调用路径和作用，或承认只参与配置/联调 |
| 只背定义 | 用三条数据或两个并发请求演示 | 状态变化、边界输入、可观测结果 |
| 说未来方案 | 当前已经实现哪些，哪些是改进设想？ | 当前事实与方案设想的分界 |
| 没有记录 | 如何设计一个最小实验来验证？ | 输入、观察点、预期、反例；不编造已运行结果 |

### 5.3 允许延伸的边界

允许：从明确提到的缓冲池推导 pin/dirty、替换失败、基本 LRU 取舍；从 Cache-Aside 推导失效、TTL、并发旧值回填；从 JWT 撤销推导剩余有效期和 Redis 故障行为。前提是对应锚点已经在当前简历及代码中确认。

谨慎：标准 B+ 树、ARIES 等可以用于解释“与当前简化实现的差别”，避免转成“请讲你实现的树分裂/完整恢复算法”。

排除：仅因仓库或旧资料出现 Kafka、AI 算法、前端、生产系统概念就展开完整专项；未经证实的 QPS、延迟下降、生产事故、测试通过率；与两个项目没有直接关系的秒杀、抽卡、短链接、通用算法题大全。

## 6. 一天内的学习约束

“完整”指覆盖简历承诺及直接相关原理、边界、证据，而非掌握两项目全部源码。建议集中学习约 9 小时，分块休息，保留吃饭和睡眠；不要把 24 小时都排成连续背题。

| 阶段 | 时间预算 | 产出与过关条件 |
| --- | --- | --- |
| 范围与主线 | 30 分钟 | 每个项目 30 秒介绍；能区分本人、协作和框架 |
| RMDB 核心机制 | 2.5 小时 | 先存储/记录，再执行/索引，再事务/恢复；每组完成状态推演 |
| ITMS 核心机制 | 2 小时 | 一条请求链；与职责对应的认证/缓存/数据/联调知识卡 |
| 跨知识点串讲 | 1 小时 | 每个项目一个纵向完整例子；机制之间的因果关系 |
| 第一轮模拟 | 45 分钟 | 主问 60～90 秒，追问 30～60 秒；不看答案评分 |
| 定向补漏 | 1 小时 | 只补 0/1 分和边界说错的 P0；做小例子，不通读重背 |
| 第二轮模拟 | 45 分钟 | 换输入、换追问角度；确认不是记住原题措辞 |
| 最后口述与速记 | 30 分钟 | 两个项目的 30 秒/2 分钟介绍；每个项目三个限制和证据 |

优先级定义：P0 为简历明确承诺和必须能讲的核心链路；P1 为一跳能延伸的高概率边界；P2 为比较或改进，时间不足即可跳过。先让全部 P0 达到 2 分，再让最强的几个点达到 3 分，不平均用力。

知识点内节奏建议：阅读机制 3～5 分钟 → 遮住答案口述 1～2 分钟 → 推演反例 2 分钟 → 标记错误。每完成一个模块立即保存掌握度，持续生成与复测以薄弱点为输入。

## 7. 学习评分与停止标准

| 分数 | 可观察表现 | 下一步 |
| --- | --- | --- |
| 0 | 无法解释，或者把未实现的能力当作项目事实 | 重读机制与事实边界；重做最小例子 |
| 1 | 能给定义，讲不出状态变化或项目作用 | 补一个输入→状态→输出的推演 |
| 2 | 能正确讲原理、项目落点和一个边界 | 进入下一知识点，之后换问法复测 |
| 3 | 能脱稿表达，处理反例、取舍和证据质疑，职责准确 | 仅做间隔复测，停止无效加题 |

技能模板中的自动评分脚本只按关键词与字数计分，不评技术真伪，不能用其分数证明掌握程度。这里使用人工/语义评分，以概念正确和证据真实优先。

结业检查：P0 无 0 分；至少两轮不同问法下稳定到 2 分；每个项目至少有一个达到 3 分的技术主线；所有“我实现”“测试通过”“性能提升”都有对应证据或已降级为准确表述。此标准可衡量学习成果，不能保证面试结果。

可复用生成提示词：

> 仅围绕当前简历中 RMDB 与智能交通两个项目生成学习资料。先读取事实清单和历史已覆盖知识点。为本批选定的知识点写机制讲解、一个小例子、主问题与 60～90 秒口述答案、2～3 个递进追问及答案、易错说法、最小自测。每项标明简历锚点及事实等级，区分本人贡献、协作、框架已有与一般原理。具体函数、参数、测试结果须有证据；没有则明确待核对。问题从使用经验进入原理、边界、取舍和验证。假设事故明确写作假设，不编造经历；标准算法与当前实现分开。按知识点组织并持续保存，新增题目服务于覆盖缺口和薄弱点，不重复换皮出题。
