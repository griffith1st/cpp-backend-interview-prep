## Q101 一个真实 bug 怎样讲

**口述：**按现象、复现、假设、证据、根因、修改、回归顺序回答。先限定触发条件与影响，不把“加锁/加索引/重启”当作根因。

**机制/边界：**对一个候选原因至少说明一个反证。如结果缺失，网络短读、SQL解析、迭代器结束条件都可能导致；用报文、输入长度和断点逐层排除。没有实际复现记录时，就说这是代码阅读发现的风险，不说已发生生产事故。

**追问/验证：**修复前同样输入失败，修复后通过，保留最小回归；说明测试为何以前没覆盖，以及修复是否增加锁争用、内存或额外I/O。

## Q102 怎样证明优化有效

**口述：**固定环境和数据，在同等负载下对比优化前后，既看吞吐也看延迟分位数、错误率和资源占用。写清预热、缓存状态、重复次数与波动，避免只挑最好一轮。

**机制/边界：**P99须由足够样本计算，少量请求不能支撑稳健尾延迟结论；并发、QPS和连接数不是同一量。测量工具、日志级别、编译配置和磁盘缓存都可能改变结果。

**追问/验证：**吞吐从1000到1200并不能单独证明优化有效，如果P99从50ms升到500ms或错误率变高，必须解释权衡。数字是示例，不能填进个人简历冒充实测。

## Q103 框架与个人贡献

**口述：**把框架已有、本人实现、本人调试验证、只做源码阅读四类分开。对每项个人实现能指向改动、核心不变量与测试，而不是仅列依赖名。

**机制/边界：**仓库包含B+树接口不证明实现了分裂/合并；有Kafka依赖不证明设计过生产消息可靠性。BusTub不同学期接口和任务会变化，必须针对实际commit讲，而非背其它版本讲稿。

**追问/验证：**“你究竟写了什么？”用变更清单和测试回答。若实际是简化有序容器索引，说明功能范围，不宣称磁盘B+树；基础REDO/UNDO也不宣称完整ARIES。

## Q104 限制与演进

**口述：**先指出当前最影响目标的限制，给出可测量的下一步，不把所有现代技术都加入路线。说明风险、兼容方式、验证标准和失败回滚。

**机制/边界：**例如教学网络层用固定缓冲，先补framing、长度上限、短读短写和超时，再评估事件循环；不是直接换框架就获得正确协议。索引原型先明确持久化与恢复不变量，再讨论复杂并发优化。

**追问/验证：**为什么先做A不是B？用当前瓶颈/正确性风险和预期收益说明，区分已经实施与未来方案。

## Q105 五分钟排查延迟尖刺

**口述：**先定位时间、影响接口与错误率，查看最近变更，再以trace关联入口、线程池/连接池、依赖和存储；用CPU、锁、I/O、GC或内存等指标验证方向，必要时按预案止损。

**时间安排：**第1分钟确认范围与SLO；第2分钟看发布/流量变化；第3分钟看队列、饱和资源和下游；第4分钟选一个可证伪假设取轻量证据；第5分钟决定回滚/降级/继续定位，并记录依据。

**边界：**C++服务不要机械照搬JVM的GC原因；低CPU不排除锁/外部等待，平均延迟正常也不排除P99恶化。第一时间做破坏性全量重启可能清掉现场，止损与保留证据要协调。

## 三条项目答辩路线

### RMDB 数据库内核

```text
输入SQL -> 网络消息边界 -> Parser -> Analyze -> Planner
        -> Executor -> Record/Index -> BufferPool -> Disk
                  事务/锁/日志跨越其中多个环节
```

准备三个不变量：pin页不被替换、脏页与日志持久化顺序、DML与索引状态的一致性。准备三个失败点：缓冲池全部pin、执行中事务冲突、日志或数据页写入附近崩溃。每项只陈述当前版本实现与实际测试。

### Muduo 网络库阅读

从EventLoop线程归属开始，串起Poller→Channel→TcpConnection→Buffer；解释跨线程任务投递与唤醒，处理短写、慢客户端和生命周期。高水位回调是通知，应用要自己决定暂停、拒绝或关闭策略。

能定位函数、解释约束、自己重写一个小实验，分别是三个层次。未修改原库时，表述“阅读并验证线程模型”，不是“实现了整个网络库”。

### BusTub 课程项目

按固定版本查看实际目录、测试和未实现接口。页管理的page_id/frame映射、pin/dirty/替换器、PageGuard所有权都是高价值主题；B+树、执行器与事务的具体要求以该版本为准。

不要发布或冒充尚未完成的课程实现，也不要把通过部分单测说成所有隐藏测试通过。面试更看重你解释边界、定位失败和验证修复的能力。

## 可直接填写的证据页

```text
项目 / commit / 环境：
我负责的模块：
框架已有能力：
入口 -> 关键函数 -> 输出：
两个关键数据结构及不变量：
正常输入与边界输入：
曾观察到的错误（无记录则写未验证）：
复现命令与实际日志：
根因和排除的假设：
修改范围 / 为什么正确 / 取舍：
修复前后测试 / 性能测量口径：
当前限制 / 下一步 / 回滚方式：
```

两分钟讲稿只讲背景、职责、一个技术点和一个证据；十分钟加入调用链与边界；三十分钟深入失败与并发。AI可以追问、审查逻辑和帮助组织表达，但不应替你虚构函数、成绩、岗位经历或已运行测试。
