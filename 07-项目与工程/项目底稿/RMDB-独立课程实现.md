## 业务与职责

**使用场景：**数据库课程实验，通过一个能处理 SQL 的教学系统理解记录存储、执行器、索引、锁、事务和日志的协作。评价重点是功能正确性与解释能力，不是生产数据库规模。

**个人主责：**题目 1–11 的学生实现，主讲三组：存储管理、查询执行、事务与恢复。类型、聚合、排序和功能型索引作为横向补充。十一题全部完成与全部从零编写是不同含义。

**框架范围：**类声明、页面/RID 等基础结构、部分 SQL 分析和计划结构、基本建表与初始插入执行器、教师测试、第三方库。扩展 `lex.l/yacc.y` 属于源语法修改；生成的解析文件不另算手写模块。

**后续维护：**项目历史说明记载 AI 在 `bbf8466` 修复索引扫描推进、句柄生命周期及回归覆盖。它们不并入本人原始题目成果。本次只更新面试资料，未修改 RMDB 代码。

## 核心调用链

### SQL 查询

```text
客户端发送 SQL
  -> 服务端入口与课程协议
  -> Parser: 语法树
  -> Analyze: 表/列/类型与语义检查
  -> Planner: 扫描、连接、投影、排序等计划
  -> Executor: 逐步消费记录
  -> Record / Index: 定位 RID、读取记录
  -> BufferPool: 命中或选择空闲/可淘汰 frame
  -> DiskManager: 文件页读写
  -> 输出记录与列信息 -> 客户端
```

网络层是系统入口，不因此把整套高性能网络库列为个人实现。重点说明执行器如何消费下层数据，而不是只背层次名。

### 更新与回滚

```text
UPDATE 目标记录
  -> 执行器取得表级排他锁；冲突按 no-wait 中止
  -> 保存旧记录，计算新记录与索引键，做约束检查
  -> 记录更新日志、维护事务写集
  -> 更新基表及相应索引
  -> COMMIT: 提交处理、日志刷新、结束事务
  或 ABORT: 逆向撤销写集、恢复记录与索引、释放锁
```

具体写入顺序以各执行器为准，避免用一张概念图替代对日志、索引、记录修改顺序的检查。`executor_update.h` 可见日志写入及刷新路径。

## 技术选型与三个不变量

选型解释是对现实现的技术分析，不声称当时做过未留档的 A/B 实验。

| 方案 | 教学场景下的理由 | 代价与进一步追问 |
| --- | --- | --- |
| 定长记录 + RID | 偏移计算直接，位图管理槽位，易建立存储不变量 | 变长字段、碎片与跨页记录需要另设计 |
| LRU + pin | 近期性近似工作集，固定页面的生命周期清楚 | 扫描污染；全 pin 时应返回失败而非淘汰使用中的页 |
| BNLJ | 无额外哈希结构，适配已有拉取式执行器 | 右侧仍会多次扫描；块大小影响 I/O 与内存 |
| 简化有序索引 | 先实现唯一约束、范围访问和执行链联通 | 插入移动开销、内存占用、恢复重建，扩展性弱于完整页式树 |
| no-wait | 冲突立即中止，省去等待环和死锁检测 | 热点下回滚重试多，公平性和吞吐需另测 |
| 基础 REDO/UNDO | 让事务日志与启动恢复先形成闭环 | 多次崩溃、幂等、截断日志和复杂交错仍需验证 |

必须掌握的三个不变量：

1. **页生命周期：**仍被使用的页面保持 pin；`page_id -> frame` 映射、替换器和 pin 数一致；脏页淘汰前写回。
2. **数据与索引：**一个成功 DML 后，基表记录与所有索引键一致；失败回滚同样维护这条约束。
3. **日志与恢复：**解释 WAL 所要求的持久化顺序，并逐条核对实际刷新点；“代码调用 write”不自动证明掉电耐久性，还要检查同步到存储的语义。

## 三个深挖主题

### 主题一：缓冲池状态转换

解释命中、未命中、脏 victim、空闲 frame、全部 pin 五种情况。把 page table、free list、replacer 和 `pin_count/dirty` 画在同一页。

最小验证设计：容量为 2，固定两页后请求第 3 页；释放一页并修改为脏页，再触发淘汰；重新读取核对数据。记录实际返回值、页号和磁盘内容。这里是待执行设计，不是已通过测试结论。

### 主题二：唯一索引与事务回退

同一行更新可能改变多个索引键。需要先想清唯一性冲突发生在哪里，先前已修改的索引如何回退，旧值由谁保存。

最小验证设计：建立复合唯一索引，插入两行，尝试把其中一行更新为冲突键；随后做顺序扫描、索引访问和事务回滚核对。对空范围、单元素范围、端点等值额外测试。

索引分裂/合并的接口存在，但 `split/coalesce/redistribute/adjust_root` 等在此实现中简化或留空。答辩从有序容器的实际行为出发。后续 `IxScan::next()` 修复是维护历史，若复习它，可讲“阅读了该修复”，保留来源。

### 主题三：日志恢复能力的准确范围

当前 `RecoveryManager::analyze()` 读取日志并区分 committed、aborted、active；`redo()` 只重做已提交事务；`undo()` 逆序处理 active 事务并刷新数据页。

这与 ARIES 的 repeat history、脏页表、pageLSN、CLR、检查点体系有区别。“函数名包含 analyze/redo/undo”不等于算法就是 ARIES。

验证设计：提交后重启、未提交写入后重启、恢复过程中再次中断、日志尾部截断、重复恢复。每次检查基表、索引和事务结果。未跑完整故障矩阵前，只说基础恢复路径，保留异常场景限制。

## 高频追问

| 面试官追问 | 回答锚点 |
| --- | --- |
| 你是从零写数据库吗？ | 基于教师框架独立完成指定任务，指出已有插入/建表和骨架 |
| Page 与 frame 有什么区别？ | 磁盘逻辑页与内存槽位，映射和生命周期分别管理 |
| 为什么 pin 与 LRU 都需要？ | pin 保证使用期，LRU 在可淘汰集合里选 victim |
| BNLJ 有什么收益？ | 左块容纳多条记录，减少右表重复扫描次数；成本看块与输入规模 |
| 复合索引如何编码和比较？ | 各列类型/长度/偏移、按列比较；不要把数值裸字节排序当一般正确答案 |
| 唯一性冲突时基表已改怎么办？ | 按实际顺序分析，补最小反例，不假定多步操作天然原子 |
| 为什么没有死锁检测？ | no-wait 不排队等待冲突资源，代价转化为中止重试 |
| 有记录锁接口就实现行锁隔离了吗？ | 看调用点和锁覆盖，当前 DML 的表级路径更粗 |
| no-wait 是乐观锁吗？ | 仍是悲观加锁协议，只是冲突不等待 |
| REDO/UNDO 就是 ARIES 吗？ | 对照当前事务分类和重放策略，指出缺失机制 |
| 崩溃恢复后索引怎么办？ | 说明当前重建与恢复辅助操作，实际测试一致性 |
| 最想继续改什么？ | 先补正确性和崩溃测试，再考虑页式索引、优化器或并发能力 |
