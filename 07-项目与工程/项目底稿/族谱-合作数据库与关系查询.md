## 业务与职责矩阵

系统用于维护多个族谱的成员、亲子和婚姻关系，支持成员检索、祖先/后代查看和两人关系路径查询。核心难题不只是 CRUD，而是把关系数据约束好，并控制图遍历的正确性、成本与更新可见性。

| 归属层次 | 建议职责 | 源码入口 | 交付内容 |
| --- | --- | --- | --- |
| 本人主责 | 三张核心业务表及约束 | `sql/schema.sql` | 成员身份、同族谱关系、唯一和基本合理性约束 |
| 本人主责 | 亲子图加载和祖先/后代查询 | `app.py` 的 `_load_pedigree_graph`、`ancestors`、`tree` | 双向邻接、分层遍历、去重、深度和分页结果 |
| 本人主责 | 关系路径查询 | `app.py` 的 `relation` | 亲子与婚姻边、带标签路径、搜索预算 |
| 本人主责 | 查询 SQL、索引及模拟数据 | `sql/indexes.sql`、`sql/queries.sql`、`scripts/generate_data.py`、`sql/import_data_psql.sql` | 执行计划、导入统计与边界用例；实际测试结果另附 |
| 共同参与 | 六表整体评审、成员/关系 CRUD、模板结果对接 | `app.py` 的成员和关系路由 | 参数、事务、结果字段、写入后可见性 |
| 其他协作者建议主责 | 登录会话、用户/族谱协作、邀请、页面和部署备份 | 公共鉴权、`templates/`、`static/`、部署脚本 | 查询模块消费其登录与族谱上下文 |

个人主责从收到合法的族谱/成员上下文开始，到返回查询数据结束；鉴权现实现仍需核对，不以职责划分代替安全检查。

## 六表模型与约束

```text
app_user -> pedigree（创建人）
app_user <-> pedigree_user <-> pedigree（协作关系）
pedigree -> member
member <-> parent_child <-> member（有向亲子关系）
member <-> marriage <-> member（配偶关系）
```

| 表 | 核心含义 | 本人建议参与程度 |
| --- | --- | --- |
| `app_user` | 登录用户 | 了解字段与接口，账号模块由协作者主做 |
| `pedigree` | 族谱元信息 | 共同参与，与核心表关联 |
| `pedigree_user` | 用户与族谱的协作关系及角色 | 共同讨论契约，权限逻辑由协作者主做 |
| `member` | 姓名、性别、生卒年、代次和成员 ID | 主责 |
| `parent_child` | 族谱内父母角色与子女关系 | 主责 |
| `marriage` | 配偶对与婚姻信息 | 主责 |

值得主讲的约束：

- 亲子/婚姻使用 `(pedigree_id, member_id)` 复合外键，约束双方属于同一族谱，不只检查 member_id 存在。
- 亲子关系禁止自指，每个子女每种父母角色唯一；配偶 ID 规范排序，并对关系对作唯一约束。
- 触发器检查已知父母出生年早于子女，以及角色性别等条件。它挂在亲子关系写入路径，后续修改成员出生年/性别不会自动复查既有关系。
- 出生年份缺失时没有完整的多节点环检测；自指限制和 BFS 去重都不等于数据库中的亲子关系全局无环。

`pedigree_user` 有角色值也不等于完整 RBAC。当前成员资格检查与 owner/editor/viewer 的具体写权限检查需要分别验证。

## 真实请求链路

### 祖先查询

```text
GET /members/<id>/ancestors
  -> Flask 路由、登录与族谱范围检查
  -> _load_pedigree_graph(pedigree_id)
       缓存命中: 取该进程的亲子邻接映射
       缓存未命中: PostgreSQL 读取亲子边，构建父/子两个 Map
  -> 向父节点逐层 BFS，visited 去重，限制层数
  -> 内存结果排序与分页
  -> 批量读取当页成员详情
  -> Jinja 模板输出
```

后代查询 `/members/<id>/tree` 使用向子节点的映射。在线主路径是 Python BFS；`sql/queries.sql` 的递归 CTE 是查询示例，`sql/export_branch.sql` 使用 CTE 导出分支，二者分别陈述。

### 两人关系查询

```text
/relation
  -> 校验选择成员与查询范围
  -> 读取缓存亲子图 + 本次查询婚姻边
  -> 构建带关系标签的无向图
  -> 两端搜索 + 深度/访问预算
  -> 相遇后拼接路径并反转反向边标签
  -> 返回关系链或无结果/预算信息
```

主路径没有 Redis。Flask 默认签名 Cookie 会话也不是服务端 Session 存储；这些是公共模块概念，避免跨项目混淆。

## 算法与缓存边界

| 功能 | 现实现 | 限制 |
| --- | --- | --- |
| 祖先 | 逐层 BFS，全局 visited；默认 20 层，上限 50 | 同一祖先多条路径会去重；这是成员集合查询，不是枚举所有血缘路径 |
| 后代 | 逐层 BFS，全局 visited；默认 10 层，上限 30 | 全图加载和遍历成本仍存在 |
| 分页 | 每页 50，先遍历/排序后切片，再批量读详情 | 减少详情查询和展示量，不等于数据库端分页限制了全部遍历 |
| 关系路径 | 双队列搜索；访问预算 50000，默认深度 15，上限 30 | 每轮各弹一个节点、首次相遇停止，最短路径有反例；深度限制不是总路径长度保证 |
| 亲子图缓存 | `@lru_cache(maxsize=32)`，按族谱缓存邻接图 | 32 指缓存项/族谱数，不是节点数；无 TTL/主动失效，多进程各自持有 |

“可遍历 30 代的输入”与“全部 30 代在固定延迟内查完”是两种结论。初次图加载约需读取对应族谱的亲子边；关系查询还构建婚姻邻接并保存搜索状态，空间随图规模变化。

## 技术选型

| 选择 | 合理性 | 代价与替代比较 |
| --- | --- | --- |
| PostgreSQL 邻接关系表 | 外键/唯一约束清晰，与账户和成员 CRUD 易组成事务 | 多跳查询另需 BFS 或递归 SQL，不自动得到图数据库能力 |
| Python BFS | 无权边按层遍历直观，便于深度/预算/关系标签处理 | 大图传输、Python 内存和缓存一致性成本 |
| 递归 CTE | 可把多跳访问放入数据库，减少应用搬运 | 需设计终止、去重、执行计划；在线路径当前未采用 |
| 进程内 LRU | 减少重复加载同一族谱亲子边 | 写后陈旧、多进程不一致、按条目而非字节限额 |
| pg_trgm GIN | 支持 `ILIKE '%关键字%'` 的候选匹配 | 写入维护和空间成本，低选择性查询未必受益 |
| CSV + COPY | 模拟数据批量导入比逐条应用请求更直接 | 约束顺序、失败回滚、序列值和数据校验仍需处理 |

这张表是针对现实现的解释，不代表曾部署图数据库、压测所有方案或验证全部收益。

## 三个深挖主题

### 完整性：跨族谱与长环是两个问题

复合外键解决“成员存在但属于另一族谱”；角色唯一约束解决重复父/母角色；自指约束只排除一节点环。缺失年份下的多节点环仍需全局检查。

建议验证：在测试事务中依次尝试跨谱关系、自指、重复角色、父母年龄冲突，以及关系已存在后修改成员年份/性别；记录具体约束或触发器结果并回滚。对未知年份构造长环，分别观察写入和查询终止。

### 正确性：双端搜索并非看到交点就够

独立等价控制流检查发现以下无向图反例，编号是测试节点，不是业务成员资料：

```text
边: 0-1, 0-6, 1-2, 1-3, 1-6, 2-5, 2-6, 3-4, 5-6, 5-7
起终点: 0 -> 7
交替单节点扩展并首交点停止: 0-1-2-5-7，共 4 条边
普通 BFS 最短路径:             0-6-5-7，共 3 条边
```

该检查是算法控制流的独立复现，不是 Flask/PostgreSQL 集成测试。还需在实际 `relation` 路由中用相应输入复测。

深度也有语义问题：链 `0-1-2-3`，两端各允许深度 2，拼接后可能返回 3 条边。应明确定义“每侧搜索深度”还是“最终路径最多几跳”。

改进顺序：先建立普通 BFS oracle 和反例集；再实现按完整层扩展及正确终止条件，或在当前小规模直接使用单向 BFS；最后测搜索预算和标签反转。当前未修复，不写成已保证最短路径。

### 一致性：缓存更新与 SQL 索引

当前没有 `cache_clear`、TTL 或更新通知。删除成员/修改亲子边后，热缓存可能仍保留旧图；关系查询又实时读取婚姻边，可能混合不同时间版本。

改进可以选择写后失效或按族谱版本缓存。单进程清理不足以覆盖多 worker；TTL 也只是限制陈旧时间，不等于强一致。先明确业务允许的陈旧窗口，再选方案。

索引方面，亲子父方向有重复列索引，部分与主键重合；成员 `(pedigree_id, member_id)` 索引与唯一约束索引重复。应先查看实际数据库索引和执行计划，再评估删减，避免为“索引越多越快”辩护。覆盖列也不保证永远不回表，Index Only Scan 还依赖可见性信息。

## 高频追问

| 问题 | 回答锚点 |
| --- | --- |
| 为什么六张表不是一张成员大表？ | 用户与族谱多对多、成员、亲子、婚姻职责分离，减少重复 |
| 全局 member_id 唯一为什么还要复合外键？ | 同时约束关系记录的 pedigree_id 与成员所属谱一致 |
| 数据库保证所有亲子关系无环吗？ | 自指/年龄规则与全局无环不同，缺失年份仍有边界 |
| BFS 的 visited 会丢信息吗？ | 适合唯一成员集合；列举全部不同路径需要另一语义和预算 |
| 双向 BFS 保证最短吗？ | 看按层扩展与终止条件；当前交替单节点版本有反例 |
| 查询是否主要用递归 CTE？ | 在线祖先/后代是 Python BFS；SQL 示例/导出有 CTE |
| 分页后最多只遍历 50 人吗？ | 否，先遍历/排序再分页，只批量获取当前页详情 |
| LRU 缓存了多少人？ | maxsize=32 指族谱图数量，内存还取决于每个图大小 |
| 修改关系后何时可见？ | 当前热缓存可能陈旧；写后失效/版本机制为后续设计 |
| 为什么用 GIN？ | pg_trgm 支持包含式姓名检索，结合选择性与执行计划评估 |
| 10 万数据是不是用户？ | 模拟成员记录，不是登录用户，也不是同时在线规模 |
| 优化提升多少？ | 没有对照报告就只讲索引和算法设计，补测后再报告数字 |

| 代次 | 每谱 30 代 | 数据字段跨度；非所有深度查询已测性能 |

生成脚本使用固定随机种子 42。统计 CSV 证明文件规模；实际 COPY 是否全部成功仍应以测试库 `COUNT(*)` 和约束检查为准。

索引/性能验证必须固定数据库版本、机器配置、导入数据、冷/热缓存和查询参数。可在导入完成的测试库运行只读分析示例：

```sql
SELECT COUNT(*) AS members FROM member;
SELECT COUNT(*) AS parent_edges FROM parent_child;
SELECT COUNT(*) AS marriages FROM marriage;

EXPLAIN (ANALYZE, BUFFERS)
SELECT child_id
FROM parent_child
WHERE pedigree_id = 1 AND parent_id = 1;
```

`1` 为示例参数，先选数据中真实且有代表性的 ID。`EXPLAIN ANALYZE` 会实际执行语句；以上是 SELECT，测试仍应控制资源。准备小谱、大谱、叶节点和高分支节点，分开记录图加载、遍历和详情查询耗时。
